# Replica 목적 기준 전체 코드 평가

검토일: 2026-09-26. 브랜치: `codex/sol-terra-implementation-bundle`. 커밋: `fece800d20292f30ce526ed16f96e7457e0816b6`.

이 평가는 기업명 입력 → 공개 기능 조사 → 범위가 명확한 핵심 기능의 실제 구현 → 새로운 입력의 실행·평가 → 사람이 써볼 수 있는 결과물과 설명 가능한 평가 결과라는 목적을 기준으로 한다. 투자 실사·기술평가 등 최종 활용 기관에 따른 판정 기준은 공통 엔진의 요구사항과 구분했다. 사용자가 제공한 Bain 사례는 목적 설명으로 사용했으며 보도 내용의 사실 검증은 이번 코드 리뷰 범위가 아니다.

**판정: 실제 기능 재현 실험을 운영할 기반은 갖춘 MVP다. 기업명만 입력해 중간 보완 없이 최종 평가와 재사용 가능한 결과까지 일관되게 내는 시스템은 아직 아니다. 가장 큰 공백은 특수 파일 처리보다 실행 경로, 조사 범위의 보존, 상태형 업무의 검증, 회사 전체 실험 결과의 연결에 있다.**

### 1. 기본 실행 경로와 종료 규칙이 목표와 충돌한다 — 목적상 우선순위 높음, 문서·라우팅 확인

완료 조건: 동일한 회사 평가 요청이 에이전트의 해석에 따라 '2차에서 종료', '파일 사용 불가', '실제 번들 구현'으로 갈리지 않는다. 요청 시 전체 실행은 이미 승인된 것으로 처리한다.

### 2. 2차에서 확정한 기능 범위를 빼도 whole_workflow가 된다 — P1, 추가 재현

[second_pass.py:579](/Users/cho/replica-mvp/src/replica_mvp/second_pass.py:579)의 단계 대응 검증은 `first_pass.workflow.steps`만 읽는다. `second_pass.workflow.steps`에서 새로 확인한 단계는 검사 대상이 아니다.

재현: 1차의 두 단계에 2차가 '답변과 인용 저장·후속 조회' 단계를 추가한 `refined` claim을 만들고, 선택 시나리오의 `out_of_scope`에는 그 저장·조회 기능을 제외한다고 적었다. 기존 두 단계만 대응해도 `scope=whole_workflow`, `PENDING`, 평가 gap 0개로 승인됐다.

최종 모델 기반 구현 검토가 이를 발견할 가능성은 있다. 이 재현은 실제 Judge가 잘못된 구현을 승인했다는 주장이 아니라, 누락을 막아야 하는 사전 범위 검사와 부분 범위 표기가 작동하지 않는다는 증거다.

조치: 구현 전 확정된 워크플로를 기준으로 단계 대응을 검사하고, 1차에서 추가·수정·삭제한 내용과 근거를 보존한다. 의도적인 한정 실험은 허용하되 제외 범위를 결과에 남긴다. 기업 전체 제품이나 모든 주변 기능을 재현하라는 요구는 아니다.

완료 조건: 2차에서 확인한 핵심 단계를 누락한 계약은 보완 요구 또는 명시적 부분 범위가 된다. 1차 단계가 비어 있다는 이유로 자동으로 전체 재현 범위가 되지 않는다.

### 3. 상태형 업무의 동일 요청 재전송을 평가할 수 없다 — P2, 추가 재현

### 4. 회사의 전체 기능 결과를 연결하는 목록이 없다 — 목적상 미완, 추가 재현

[second_pass.py:527](/Users/cho/replica-mvp/src/replica_mvp/second_pass.py:527)는 ready/build만 실행 대상으로 반환한다. 이것은 구현 대상 선택으로는 타당하다. 그러나 [하네스 결과 구조:288](/Users/cho/replica-mvp/src/replica_mvp/agent_harness.py:288)도 그 부분집합만 포함하고 원래 회사의 모든 claim 결과를 연결하지 않는다.

재현: ready 하나와 partial 하나가 있는 research에서 registry는 claim 하나만 가진다. 모든 claim이 명시적으로 blocked이면 `company research has no ready build claims` 오류로 끝나며 run 디렉터리가 만들어지지 않는다. 원본 research에는 사유가 남으므로 조사 데이터 자체가 사라진다는 뜻은 아니다.

보고서가 아직 없다는 점은 이미 알려진 계획 범위다. 필요한 것은 미구현 보고서를 다시 결함으로 세는 일이 아니라, 나중에 보고서가 성공 사례만 보고 결론 내리지 않도록 결과 입력을 마련하는 것이다.

조치: 모든 claim ID에 조사 판정, 실행·미실행 사유, 선택 경로, 구현 결과 경로를 연결하는 회사 단위 목록을 만든다. 실행 대상이 0개인 조사도 근거 부족·접근 불가라는 유효한 평가 결과로 종료한다. 원본 research와 실행 결과를 결속한다.

완료 조건: 전체 5개 중 2개만 시험했으면 그 분모와 나머지 3개의 사유가 명확하다. 우리 도구의 실행 실패를 대상 기업의 기술 장벽으로 해석하지 않는다.

### 5. 질문형 체험은 연속 대화 상태를 연결하지 않는다 — P2, 입력 조립 재현

조치: 상태형 기능의 체험 방법을 해당 계약에 연결한다. 우선 CLI에서 같은 실행 상태를 유지하고 후속 입력을 보내는 방법이면 충분하며, 웹 UI는 필요하지 않다. 모든 기능을 question_answer 형식으로 통일할 필요도 없다.

완료 조건: 사용자가 구현 코드를 수정하지 않고 새 입력을 주고, 해당 기능이 요구하는 연속 동작·최종 저장 결과까지 관찰할 수 있다.

### 6. 구현 난도·경쟁력 원천을 설명할 관측이 아직 얕다 — 목적상 미완, 코드·과거 기록 확인

[resources.py:72](/Users/cho/replica-mvp/src/replica_mvp/resources.py:72)는 미측정 항목을 null로 보존한다. 이를 0이나 무료로 표시하지 않는 것은 올바르다. [bundle_evaluation.py:817](/Users/cho/replica-mvp/src/replica_mvp/bundle_evaluation.py:817)의 자동 수집은 주로 최종 평가 시간과 Judge 사용량이며, 개발 자원은 Builder의 기록을 받아 보존한다.

Delphi 보존 기록의 개발 측정은 호출 수·버전·일부 지연 시간 등이 혼재하고 경제적 비용은 대부분 unknown이다. 따라서 '몇 번 시험했는지'와 '다른 팀이 어떤 자원으로 대체할 수 있는지'는 아직 같은 수준으로 측정되지 않는다.

OSS/API/자체 데이터 의존성 및 버전 기록은 있지만, 그것만으로 해당 기업의 경쟁력이 코드·데이터·업무 통합 중 어디에 있는지 입증하지는 않는다. 한 경로의 성공·실패가 기업 전체에 대한 결론이 되어서도 안 된다. 현재 문서와 Judge의 경계 규칙은 이 점을 상당 부분 올바르게 명시한다.

조치: 먼저 실행 환경·모델, 실험의 입력 범위, 개발·평가 시간, 수정 횟수, 사람 개입, 실제 사용한 데이터·외부 기능을 동일한 형식으로 기록한다. 필요한 평가 질문에 한해 단순한 대안과 비교하거나 특정 의존성을 제거한 실험을 별도로 설계한다. 모든 회사에 여러 경로·절제 실험을 강제할 필요는 없다.

완료 조건: 재현 범위·품질·자원·의존성·미확인을 구분해서 설명할 수 있다. 과금 정보가 없으면 미측정으로 유지하며 실행 가능한 결과물 생성까지 막지 않는다.

## 지금 유지할 강점

- 1차 후보·배정 범위·병합/제외 사유 검증은 후보가 조용히 사라지는 문제를 줄인다.
- 원본 계약과 구현·평가 산출물을 해시로 연결한다.
- Operator/Builder 개발과 봉인 평가를 분리하고, Builder의 성공 주장만으로 최종 재현 성공을 주지 않는다.
- 새 입력, 반복, 변형 관계, 실제 파일 보존, 공개 예시의 독립 실행을 지원한다.
- 번들은 프롬프트만 저장하는 경로와 달리 실제 구현 코드를 실행한다. 과거 Delphi에도 모델+검색, 작업 실행·저장, 모델+SQLite 구현과 새 입력 실행 기록이 있다.
- 재현 성공과 원제품 전체의 동일성을 구분하고, 알 수 없는 자원을 0으로 만들지 않는다.

Delphi 9/8 보존 결과는 각각 4/6, 5/7, 5/6이며 모두 부분 재현으로 기록돼 있다. 새 커밋에서 다시 실행한 결과가 아니고, 이 프로젝트 전체의 재현 성공률도 아니다. 기존 Delphi 계약의 범위가 자동으로 확장된 것도 아니다.

## 코드 구조와 유지보수 평가

책임별 모듈, 표준 라이브러리 중심 구현, 실패·해시·상태 전이 테스트는 장점이다. 다만 회사 번들·JSON 부품·기존 프롬프트라는 세 경로의 입력·평가·공개 계약이 서로 다르고, 관련 지침이 AGENTS·README·여러 Skill에 분산돼 있다. 이번 범위 검증과 동일 입력 오류처럼 단계 간 계약을 연결할 때 생기는 문제가 단일 함수 내부 오류보다 중요하다.

`agent_harness.py`는 1,578행, `bundle_evaluation.py`는 1,087행으로 검증·수명주기·파일 처리·공개를 함께 맡는다. 길이 자체를 결함으로 세지 않는다. 다음 변경이 잦은 경계(회사 입력 검증, 평가 실행, 결과 공개)를 수정할 때 책임을 분리하고 공통 계약 검사를 일치시키는 정도가 적절하다. 지금 엔진 전체를 합치거나 전면 재작성할 근거는 없다.

실제 Agent의 생성·직접 메시지·재개는 에이전트 도구에 의존하며 대부분의 자동 테스트는 제어 메타데이터나 fixture를 사용한다. 294개 테스트 통과는 전체 기업 평가가 무인으로 완료됐다는 증거가 아니다. 실제 지원 모델·직접 통신·설치 의존성의 사전 확인과 신규 전체 실행 증거가 필요하다. 이번 리뷰에서 실제 spawn 지원 여부를 실행 검증하지 않았다.

## 앞선 파일 관련 지적의 우선순위 재조정

- 재개 중 구현 파일의 대소문자·링크 별칭 덮어쓰기: 유효한 결함이지만 현재 목표의 새 실행 경로를 막는 주된 문제로 보지 않는다. 재개·입력 교체 기능 수정 시 처리한다.
- 입력 교체 실패 후 기존 파일 삭제: 같은 이유로 재사용·복구 작업에 묶는다.
- 심볼릭 링크 저장 검사: 현재 범위를 단순하게 유지하려면 지원 확대 대신 검증할 수 없는 링크를 거부하는 접근으로 충분하다.
- 다른 claim의 fragment를 원본으로 인정: 자동 조사 결과 합치기에서도 생길 수 있어 지금 조사 검증 작업에 포함한다. fragment 내부 claim_id 일치 확인이 필요하다.

## 구현 순서와 수용 기준

1. **기본 전체 실행 경로 확정.** 회사 요청의 번들 경로, 중간 종료 정책, 지원 입력·의존성 지침을 정렬한다. 실제 기능이 파일·검색을 필요로 한다는 이유로 JSON 데모로 줄이지 않는다.
2. **조사 범위와 평가 계약 연결.** 2차 확정 단계·근거·제외 범위를 사용하고 fragment 식별자를 검증한다. 상태형 동일 요청 재전송 검증을 허용한다.
3. **실제 사용 가능한 결과물 확인.** 한 기능을 코드 수정 없이 새로운 입력으로 실행하고, 필요한 상태·저장·후속 동작을 확인한다. 코드/명령/입력 예시/결과 위치/필요 환경을 제공한다. 같은 로컬 환경에서의 검증이면 우선 충분하며 Docker나 웹 UI를 요구하지 않는다.
4. **전체 기능 결과와 관측 연결.** 실행 못 한 기능도 포함하고, 실패 유형과 미측정 자원을 보존한다. 이 결과에서 보고서를 생성한다.
5. **새 회사 또는 새 조사 버전으로 실제 전체 실행.** 과거 고정 자료를 수동 보완해서 맞춘 결과와 구분한다. 새 계약을 구현 전에 동결하고, 별도 입력을 사람이 직접 실행해 볼 수 있어야 한다. 실패한 기능이 있어도 그 실패를 설명하는 회사 평가 결과는 완성돼야 한다.

목표 산출물의 최소 묶음은 **실행 코드·실행 명령·새 입력 예시·실제 입출력/저장 결과·평가 근거·지원 범위/제외/미확인·자원/의존성·회사 전체 기능 결과 목록**이다. 보고서 형식이나 사용 기관이 달라져도 이 묶음은 공통으로 필요하다.
