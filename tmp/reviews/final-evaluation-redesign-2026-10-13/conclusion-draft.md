# 최종 평가 자체의 비용 절감 — 토론 결론

2026-10-13. 001제안 → 002Claude검토 → 003수정 → 004Claude재검토를 완료했다. 004의 N1/N2 문구 정정과 B2-a/B2-b 조건을 아래에 반영해 설계 토론을 종료한다. 사용자의 요청은 테스트 범위·판정 품질을 유지하면서 첫 기업 평가 한 번의 총비용을 크게 낮추는 방안을 다시 검토하는 것이다. 재실행 낭비 절감과 구별한다. 본 문서는 설계 권고이며 구현·성능 검증·사용자의 채택 승인이 아니다. 코드 변경과 평가 재실행은 하지 않았다.

## 권고

가장 우선할 두 가지는 **관측한 작업 구간을 한 번에 계획하여 실행하기(B1)**와 **평가 역할 전반의 반복 입력·캐시 쓰기 비용 개선(C1)**이다. 둘은 병행한다. 작은 TTL 실험이 B1의 선행 관문이 되지 않는다.

지금은 모델이 이름 입력→다음 호출에서 이메일 입력→다음 호출에서 제출→다음 호출에서 대기처럼 행동을 한 개씩 선택한다. B1은 현재 화면에서 확인한 이름·이메일·제출을 한 번의 응답으로 계획하고 코드가 순서대로 실행한다. 관측 근거가 있는 대기 조건도 계획에 포함할 수 있다. 각 행동 후 실제 화면과 오류를 확인·기록하되, 이미 예상한 단순 필드 변화는 선언된 사후조건과 코드로 대조하고 계속한다. 제출 등 의미적 결과를 만드는 행동은 계획의 마지막에 두며 그 뒤에는 선언된 대기만 허용한다. 새 결과를 해석해야 하는 분기, 새 조건부 필드, 비예상 변화가 나오면 모델에 돌려준다. 원자 행동 수와 평가 범위를 줄이지 않으며 독립 Judge의 의미 판정을 유지한다.

| 우선순위 | 변경 후보 | 비용을 줄이는 부분 | 판단 |
|---|---|---|---|
| 1, 병행 | 관측된 폼/작업의 다중 행동 계획, 제출과 관측 가능한 대기 | 단순 행동 사이 tester 재호출 | 중심 구현안. 두 행동 제한이 아닌 사전·사후조건으로 범위 결정 |
| 1, 병행 | 짧은 캐시 TTL 및 안정된 고정 입력, CLI 동적 시스템 정보 배치 검토 | tester·Judge·코드 검사 호출당 반복 입력과 쓰기 | 역할별 영수증 실측 후 채택. 호출별 격리 유지 |
| 2 | 전송용 화면·이력·Judge 증거의 복원 가능한 중복 제거 | 호출당 입력량 | 원본·순서·삭제·재등장·오류·부재 증거 유지, 기존 중복 제거와 구별 |
| 조건부 후속 | 같은 평가에서 검증한 조작 절차를 후속 사례에 재사용 | 반복 메뉴 이동·폼 탐색/계획 | 별도 학습 실행 없이 첫 실제 사례에서 얻은 절차만 후보. 초기비용 포함해 순절감 확인 전 보류 |
| 별도 비교 | 기존 역할별 저가 tester 모델 설정 활용 | 호출 단가 | 설정 지원은 이미 있음. 현재 모델 구성으로 새 기준선부터 만들고 실패 탐지·완주율 비교 |
| 유지 | 완료 사례 체크포인트·평가 설정 고정 | 중단/재시작 때 중복 평가 | 중요한 별도 최적화이나 이번 한 번 평가의 절감액에 섞지 않음 |

B2 절차 재사용은 성공 결과를 재사용하는 기능이 아니다. 이번 사례의 새 입력으로 UI를 다시 조작하고 결과를 새로 수집해야 한다. 구현자가 만든 성공 스크립트에 최종 평가를 의존시키지 않는다. 오류·fallback·사후조건 불충족으로 끝난 구간은 재사용 후보로 기록하지 않는다. 재사용한 구간을 증거에 표시하며, 사례 지시가 다른 UI 경로를 요구하면 재사용하지 않는다. 추가 계획자/라우터 LLM을 만들지 않고, 기존 tester 응답이 계획과 제한된 후보 선택을 담당한다. 준비·검증·카탈로그 문맥·추가 출력·불일치 fallback까지 비용으로 센다.

## 비용 근거와 한계

채택된 최근 3건은 22사례·85기대조건, 총502모델호출이다. 모두 과거 CLI 정가 환산 기록이며 실제 청구액이 아니다. tester에는 Sonnet/Opus가 섞여 있고 O3 적용 전이라 현재 코드의 정확한 A/B 기준선이 아니다.

|---|---:|---:|
| tester | 401 | $8.208604 |
| Judge | 22 | $2.940087 |
| 코드 검사 | 3 | $1.469645 |

tester만 절반으로 낮추면 전체는 약30% 줄어든다. 전체를 절반으로 줄이려면 tester만으로는 약83.5%를 줄여야 하므로, 큰 폭의 감축을 논의할 때 다른 평가 역할의 반복 입력 비용도 함께 봐야 한다.

401 tester 호출 중 클릭197회, 입력82회, 대기 선택71회다. 대기 내부 polling은 여기에 포함되지 않는다. wait와 입력 뒤 연속 행동을 묶은 엄격한 휴리스틱 후보는168회/$3.4255604지만, 안전하게 제거 가능한 호출이나 절감의 상한이 아니다. 모델별 비용과 문맥량이 달라 호출 수 비율을 곧바로 비용 비율로 쓰지 않는다.

tester/Judge/코드 검사의 1시간 캐시 쓰기 귀속액은 기존 CLI 단가를 역산하면 $10.881288이다. 호출·토큰 배분이 같고 쓰기 배수만2→1.25라면 $4.080483(전체의29.78%)가 줄어드는 **조건부 산술**이다. 캐시 만료/읽기/출력/모델 변경의 영향은 반영하지 않았으므로 실측 절감률로 쓰지 않는다. 004의 17초 대기 예시만으로 5분 캐시가 만료되는 것은 아니다. 해당 접두부를 마지막으로 읽은 뒤의 실제 경과시간과 요청 간 간격으로 판단해야 한다. 캐시 비활성화는 읽기 토큰도 정가로 바꾸므로 이 수치와 다르다. B1과 C1의 절감률을 더하지 않고 결합한 실행의 영수증으로 총액을 구한다.

기존 전체약$44에는 8번의 최종 평가약$36.9가 포함되어 있었다. 이번에는 채택3번의$13.7을 한 번의 평가 비용 구조를 설명하는 자료로 썼다. 한도 중단과 평가기 변경으로 생긴 재실행 비용을 이번 절감 효과로 포장하지 않는다.

## 품질 보존과 검증

- 사례·85기대조건·입력 변형 범위·독립 Judge·코드 검사 범위를 유지한다. UI 조작 뒤 실제 결과를 확인한다. 발송함 기록만으로 실제 외부 발송을 충족했다고 하지 않는다.
- 계획 안의 실제 노드 동일성과 대상 유일성을 확인한다. 같은 이름의 새 노드로 바뀌거나 관측 ref를 재할당해도 기존 대상을 그대로 취급하지 않는다.
- 원자 행동마다 입력·중간 관측·스크린샷·오류·부작용 근거를 저장한다. 증거 저장 실패 시 다음 행동 전에 즉시 중단하고 증거 불완전·미평가로 표시하며 통과로 집계하지 않는다. 이미 확보한 증거는 보존한다. 예상 밖 이동/필드/오류에서도 멈추고 실행된 접두부를 표시한다.
- 대기는 관측 근거와 제한시간이 필요하다. 제출성 행동은 계획당 한 번으로 제한한다. 결과가 모호하면 자동으로 재제출하지 않고 다음 모델 입력에도 이미 실행된 부작용을 명시한다. 모델 호출 예산과 원자 행동 예산을 분리한다.
- 무모델 로컬 시험으로 노드 교체/동일라벨 모호성/조건부 필드/긴 값/업로드/부분 실패/대기 초과/중복 효과/증거 손실/예산 중단을 확인한다. 실패를 심은 사례가 새 방식에서 잘못 통과하지 않아야 한다. 조용히 거부된 입력, 잠깐 나타났다 사라지는 오류, 응답의 삭제·재등장도 포함하고 오류 변화가 기록되는지 확인한다. fallback과 불필요한 중단 비율을 잰다. 과거 Judge 판정 일치를 정답으로 삼지 않는다.
- 이후 동일 계약·모델·입력 생성 조건과 사례별 초기 상태를 맞춘 비교를 한다. 작은 시험은 도입 판단의 선별이며 전체 품질 보존의 증명이 아니다. 모든 완료·실패·fallback·준비·입력 생성·앱 내부 호출을 집계한다. 실제 브라우저/저장 인프라비는 아직 계측되지 않았음을 따로 표시한다.
- 순수 TTL 변경은 프롬프트·모델·스키마가 동일한지와 실제 영수증 TTL, 출력 스키마 준수를 확인한다. TTL만으로 입력 의미를 바꾸지는 않지만 샘플링 출력이 항상 같다고 주장하지 않는다. 시스템 정보 배치/프롬프트/모델을 바꾸는 실험에는 출력과 실패 탐지도 비교한다. 실험 유효 설정을 기록하고, 한 평가를 진행하는 중 설정을 바꿔 체크포인트를 깨지 않는다.

## 기각한 주장과 재검토 조건

002의 '42%가 흡수 상한', '20~30%가 현실적인 감소', '다중 행동이면 history도 자동 축소'는 근거가 부족해 채택하지 않는다. 고정 cache-read 토큰 수만으로 캐시 내용이나 미스 원인을 특정할 수 없다. cwd 영향은 공식 문서와 맞는 가설이지만 현재 safe-mode 호출의 실제 경계는 검증이 남았다. `num_turns=2`를 API 두 번 호출로 읽는 해석도 기각한다(해당401건은 usage.iterations에 message1개).

사례/회사자료/화면 데이터를 system으로 올리지 않는다. 공유 작업 디렉터리보다 호출 격리를 유지하면서 `--exclude-dynamic-system-prompt-sections`를 검토한다. 각 CLI가 독립적이므로 이전 화면 없이 delta만 보내는 방법은 채택하지 않는다. 원문을 복원할 수 있는 요청 내부 압축부터 검토한다. 임의 코드 실행, 결과 캐시, 사례 축소, 오류를 숨기는 화면/리소스 제거, 별도 LLM 라우터, 여러 사례 Judge의 무조건 합치기는 이번 권고에서 제외한다.

B2는 B1 측정 뒤 같은 평가 내 반복 구간에서 준비비·추가문맥·fallback을 포함한 순절감과 품질 보존이 입증될 때 채택한다. '첫 평가에는 거의 효과가 없다'도 '크게 절감된다'도 아직 입증되지 않았다.
