테스터 모델, 관측·대기 방식, 생성 입력 재사용이 함께 바뀌었다. 따라서 한 변경의 독립 효과나 다른 기업에서의 일반적 절감률은 아니다. 사례 완료는 둘 다 6/7이다. 이후에는 기대 결과 미평가 2개가 없어졌지만 새 기준과의 품질 동등성을 별도로 증명한 실험은 아니다.

과거 구현 세션의 호출당 최대 입력 문맥은 약 27.1만 / 20.5만 / 19.9만 토큰이었다. 이는 캐시 읽기를 포함한 문맥 크기이며 모두 새로 청구된 토큰이나 모두 낭비라는 뜻은 아니다. 다만 큰 문서·과거 출력·개발 기록을 반복 유지할 구조였다는 점은 확인된다.

현재는 시나리오 중복 축소, 짧은 현재 상태 기록, 필요한 파일만 읽기, 자동 압축 설정이 들어 있다. 새로운 구현 실행에서 실제 문맥 크기·비용 감소는 아직 검증하지 않았다. 다음 실행에서 호출당 문맥 크기와 역할별 비용을 계측하고, 같은 내용을 다시 읽거나 수정 이력을 재작성하는 구간부터 줄인다.

## 10. [중간 / 개발 기록] 기록의 양보다 재실행 가능성

14개 개발 시도 기록이 있지만 일부 명령은 임시 scratchpad 경로, 생략 기호, 의사 명령이다. 현재 제출 검사는 구현자가 작성한 `status=passed`, 명령 문자열, `exit_code=0`을 확인한다. 실제 실행기의 원본 결과를 검증하는 구조는 아니다. 개발 기록의 시간 순서가 맞지 않는 항목도 있다.

체크 스크립트와 입력을 보존하고 실제 argv·작업 폴더·소스 해시·시각·종료 코드·출력 참조·실모델/대역 여부를 실행기가 기록하도록 한다. 에이전트는 변경 이유와 해석만 덧붙인다. 이것이 자동 재시험과 비용 집계에도 유리하다.

## 11. [높음 / 최종 전달] 사람이 쓰는 결과물과 시험한 결과물을 일치

이 Delphi 실행은 각 기능의 원래 영어 앱을 시험했다. 이후 사용자가 보는 통합 앱에는 iframe 결합과 번역 처리가 있다. 같은 앱 코드라도 최종 탐색 경로·번역·통합 표시가 시험 당시와 동일하지 않다.

현재 저장소에는 새 실행용 회사 앱 조립과 base path 계약이 추가돼 있다. 따라서 통합 기능 자체가 전혀 없는 것은 아니다. 다만 해당 경로의 실제 회사 실행 검증은 아직 없고, 기존 Delphi 번들에는 이전 임시 통합 방식이 적용돼 있다.

제출 번들·통합 셸·번역의 버전을 묶어 같은 결과물을 제공하고, 최종 회사 메뉴에서 기능에 들어가 입력·결과를 확인하는 짧은 통합 검증을 둔다. 기능끼리 데이터를 억지로 연결할 필요는 없다. 회사 공통 메뉴 안에서 각각 작동하면 된다.

또한 비용, 된 것·안 된 것, 제외 사유와 함께 사례를 누르면 실제 입력 → 기대 결과 → 관측 결과 → 판정 → 화면 순서를 볼 수 있는 결과 페이지가 필요하다. 현재 Markdown·JSON·스크린샷은 근거로 남아 있지만 사용자가 한 번에 읽고 추적하기 어렵다. 영상 제작보다 이 연결을 먼저 완성하는 편이 낫다.

1. 평가의 근거 검증, 제외·미검증 전파, 외부 효과 기준을 고친다. 기존 결과를 다시 해석할 때 원본을 덮어쓰지 말고 정정 보고서를 남긴다.
