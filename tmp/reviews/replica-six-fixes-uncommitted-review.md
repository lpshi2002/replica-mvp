# 6개 항목 수정 후 작업 트리 검토

검토 기준: `codex/sol-terra-implementation-bundle`, HEAD `fece800` 위의 미커밋 변경 20개 파일. 목적은 기업명에서 출발하여 범위가 명확한 실제 기능 구현·평가·직접 실행 가능한 산출물과 회사 전체 결과를 얻는 것이다. 제품 코드 수정이나 신규 기업 실험은 수행하지 않았다.

**수정 방향은 목적에 맞고, 1·2·3번과 fragment 식별자 검증은 핵심 수정이 반영됐다. 회사 결과와 실험 기록도 추가됐지만, 실패 분류·사유 전달과 0개 기능 종료는 보완이 필요하다. 질문형 체험은 번들이 저장한 상태를 이어 가는 범위까지 해결됐고 대화 이력 자동 구성은 구현하지 않았다는 설명이 정확하다.**

검증: 전체 unittest 303개 통과(47.083초), `team-ai guard` 통과(내부 unittest 303개 포함), `git diff --check` 통과. 추가 검증은 임시 데이터·테스트용 구현으로 수행했다. 모델이나 실제 Agent를 실행하지 않았다. 아래 근거 파일의 working_diff_sha256가 검토한 미커밋 변경을 식별한다.

## 발견 사항

### 1. [P1] 최종 평가 이전에 멈춘 사유가 회사 결과에서 사라진다

[agent_harness.py:1625](/Users/cho/replica-mvp/src/replica_mvp/agent_harness.py:1625)의 `_company_results`는 공개 `replica-result.json`에서만 failure_category와 stop_reason을 읽는다. `RESEARCH_INCOMPLETE`, `CREATION_FAILED`, `EXECUTION_FAILED`, `EXECUTION_ABORTED`는 그 파일이 없을 수 있으므로 기존 registry·실행 상태의 사유를 별도로 읽어야 한다.

재현 결과:

- novel 사례 부족으로 시작을 막은 claim은 registry에 `research_gaps`가 있지만 회사 결과는 `not_executed_reason`, `failure_category`, `stop_reason` 모두 null이다.
- 모델 사용 불가를 사유로 기록한 테스트용 Agent 생성 실패도 회사 결과에서는 이유 없는 `experiment_incomplete`로 나온다. 실제 Agent 생성 시도가 아니라 생성 실패 기록 경로를 시험했다.

따라서 '회사 결과 파일만 읽어도 모든 미실행·중단 이유를 설명할 수 있다'는 완료 조건에 아직 못 미친다. 사유가 registry에서 삭제되는 것은 아니지만 새 보고서의 입력 파일에 전달되지 않는다.

조치: 단계별 저장 위치에서 사유를 모아 회사 결과에 연결한다. 조사 gap, Agent 생성/통신·환경·접근·예산 중단과 실제 구현·품질 실패를 구분하되, 상세 봉인 입력이나 정답을 개발 에이전트에게 공개하지 않는다. 필요하면 근거 파일의 경로와 해시를 연결한다.

완료 조건: 조사 미비, 생성 실패, 개발 중 접근 차단, 개발 실패, 프로토콜 중단 각각을 회사 결과만으로 원인과 실행 여부까지 구분할 수 있다.

### 2. [P2] 개별 사례의 시간 초과를 실험 자체의 차단으로 바꾼다

[agent_harness.py:1608](/Users/cho/replica-mvp/src/replica_mvp/agent_harness.py:1608)은 `case_timeout`을 무조건 차단 사유로 취급하며, [1641행](/Users/cho/replica-mvp/src/replica_mvp/agent_harness.py:1641)에서 회사 outcome을 `experiment_blocked`로 만든다.

재현: 환경·접근 문제 없이 특정 입력에만 늦게 응답하는 테스트용 구현을 평가했다. 6개 중 5개 통과, bundle 결과는 `partially_reproduced`, stop_reason은 `quality_or_evaluation_gap`이다. 그런데 회사 요약은 `experiment_blocked`다. 최종 Judge는 통제된 fixture로 대체했으며 실제 기업 성능을 평가한 것이 아니다.

사례 제한 시간 위반은 구현 또는 성능의 실패일 수 있고, 전체 예산 소진이나 도구 미가용과 같지 않다. 이미 완료한 일부 평가 결과를 '판정할 실험을 못 했다'는 종류로 집계하면 실제 결과 해석이 달라진다.

조치: 실험 수행 상태와 기능 재현 판정을 구분해 보존한다. 개별 case timeout만으로 전체 결과를 차단으로 바꾸지 말고, 전체 중단 사유와 실제 평가 진행 여부를 함께 사용한다.

### 3. [P2] 실제로 조사된 claim이 0개인 회사는 여전히 종료 오류가 난다

[second_pass.py:551](/Users/cho/replica-mvp/src/replica_mvp/second_pass.py:551)에 `or not claims`가 남아 있다. 새 처리는 'claim은 있지만 ready/build가 0개'인 경우만 지원한다.

재현: 기존 first-pass 테스트 자료에서 모든 후보를 사유와 함께 제외했다. `finalize_first_pass`는 `pass_1_complete`, `next_step=no_ai_claims`로 정상 완료됐다. 조사 상태를 pass_2_complete로 넘겨도 하네스 초기화는 `invalid company research contract`를 반환하고 회사 결과를 만들지 않았다.

조치: 필드 누락·잘못된 형식과, 정상 조사 결과인 빈 claims 배열을 구분한다. 실제로 기능을 발견하지 못한 회사도 `claim_total=0`과 조사 완료 상태로 끝나야 한다. 조사 자체가 미완료인 상태를 통과시키라는 뜻은 아니다.

### 4. [P2] 수정 횟수가 누적 시도 기록과 다른 범위를 가리킨다

[bundle_evaluation.py:702](/Users/cho/replica-mvp/src/replica_mvp/bundle_evaluation.py:702)는 `development_attempts`에는 이전 제출까지 합친 개수를 쓰지만, `correction_count`에는 현재 제출의 continuity만 쓴다.

재현: 첫 제출에 초기 구현+수정 1회, 두 번째 제출에 초기 구현을 기록했다. 실제 개발 시도 기록은 `(1,0), (1,1), (2,0)`인데 experiment_record는 `development_attempts=3`, `correction_count=0`, `sealed_submission=2`다.

현재 제출의 수정수로 해석하면 0은 맞다. 문제는 누적 필드와 같은 객체에 들어가면서 이름·설명으로 범위가 구분되지 않는다는 점이다. 전체 구현 난도 비교용 총 수정수로 사용하면 과소 집계된다.

조치: `current_submission_correction_count`와 누적 수정수를 분리하거나, 누적 record라면 보존한 전체 시도에서 수정수를 계산한다. 봉인 재제출 횟수는 수정 횟수와 별도로 유지한다.

## 추가 작업의 우선순위

1. 회사 결과의 사유·상태 분류와 빈 조사 결과 종료를 보완하고 해당 경로 회귀 테스트를 추가한다. 수정 횟수의 현재/누적 의미도 보고서가 사용하기 전에 정리한다.
2. 새 회사 또는 새 조사 버전으로 실제 전체 실행을 1회 한다. 새 계약을 구현 전에 동결하고, 사용자가 새로운 입력으로 코드 변경 없이 결과를 확인한다. 상태형 기능은 계약에 맞는 첫 동작 → 후속 입력 → 최종 저장 결과 → 재개까지 검증한다.
3. 그 실제 company-claims와 실행 증거를 입력으로 회사 보고서를 만든다. 실패·미실행·미측정도 포함한다. 구현 범위, 통과·실패, 근거, 시간·시도, 의존성, 남은 검증 질문을 연결하면 된다.

기존의 특수 파일·수동 입력 교체 문제 세 건은 이번 목표의 주된 차단 사유로 다시 올리지 않는다. 기존 research 호환이 엄격해진 것은 의미가 맞는 변경이며, 과거 결과는 보존하고 새 조사 버전에서 단계 대응을 보완해야 한다. 단순히 옛 JSON의 ready 표지만 고쳐 새 계약에 통과시키면 안 된다.

이번 결과는 작업 트리의 코드·정책·테스트 연결에 관한 검토다. 실제로 새로 생성되는 모든 산출물의 품질이 검증 완료됐다는 뜻은 아니다.
