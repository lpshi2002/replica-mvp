   기업이 공개한 기능 주장을 모으고, 논문·리포트·기술 문서에서 실현 근거를 확인한다. 이어 공개 방법을 직접 재현하고 핵심
   기능을 독립 구현하여, 어떤 조건에서 어디까지 기술적으로 가능한지와 아직 확인되지 않은 범위를 기록한다.

   결론의 대상은 기술이다. 기능의 구현 가능성, 측정 성능, 데이터·자원 요구량, 외부 의존성, 운영 한계를 평가한다. 금액·재무 자
   료가 없어도 작성할 수 있으며 기업가치나 투자 판단은 다루지 않는다.


   판정 범위. 기술적 가능성은 명시된 조건에서의 구현·검증 결과를 뜻한다. 법적 허용 여부를 판정하는 문서는 아니다. 외부 논문의 성
   공, 재현 성공, 독립 구현 성공은 각각 별도로 기록한다.


  작성 지침 · 노란 필드를 채우고 회색 지침은 최종 배포본에서 숨긴다. 이 문서는 빈 양식으로 실제 검증 결과를 포함하지 않는다. 항목이 맞지
  않으면 삭제 대신 “해당 없음 + 사유”를 쓴다.

 3-1. 목적과 검증 단위
목적은 기업의 소프트웨어 기능 주장을 검증 가능한 요구사항으로 바꾸고, 외부 기술 근거와 직접 실행 결과로 구현 가능
성을 판단하는 것이다. 한 주장(C-ID)은 독립적으로 합격·불합격을 판단할 수 있는 기능 또는 성능 조건 하나로 정의한다.

 3-3. 최종 기술 판정 기준

 판정                    필요한 근거와 의미

  가능                   명시된 범위의 모든 필수 기준을 독립 구현 시험에서 충족했다. 환경·규모·외부 의존 조건을 함께 적는
                       다.

  조건부 가능               실험으로 확인된 축소 범위 또는 추가 조건에서만 충족했다. 원래 요구사항과 달라진 조건을 명시한다.

  기준 미달                유효한 시험에서 필수 기준에 미달했다. “해당 구현·시험 조건에서 미달”로 한정하며 기술 전체의 불가
                       능으로 단정하지 않는다.

  판단 유보                미실행, 데이터·접근·설정 부족, 근거 충돌 또는 시험 무효로 결론을 확정할 수 없다. 해소 조건을 적는
                       다.

             기업 주장 C → 기업 출처 S / 기술 근거 E → 시험 T → 재현 R / 독립 구현 L → 최종 판정


 항목                    기록 원칙

 사실과 가정                기업 주장 / 외부 실증 / 직접 측정 / 검증자 가정을 구분한다. 가정은 기업의 구현 사실로 쓰지 않는다.

 자료 미확인                “미발견 / 접근 제한 / 출처 충돌 / 미실행 / 시험 무효”로 사유를 분리한다. 미발견을 비공개 확정이나
                       기능 부재로 해석하지 않는다.

 전체 결론                 전체 “가능”에는 모든 필수 주장 충족과 공통 환경에서의 종단 간 통합시험 통과가 필요하다. 통합 미시
                       험이면 기능별 판정만 확정한다. 미달·유보를 평균 점수로 가리지 않는다.


 작성 지침 · 판정은 조사 기준일, 대상 버전, 데이터·환경·규모 안에서만 유효하다. AI를 쓰지 않는 소프트웨어도 같은 흐름으로 검증하며, AI 전
 용 항목에는 해당 없음과 사유를 쓴다.
