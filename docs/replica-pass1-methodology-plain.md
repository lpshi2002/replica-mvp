# Replica 1차 수집 방법론 — 사람에게 설명하는 버전

## 한 문장으로

Replica의 1차 조사는 **기업이 외부 고객에게 실제로 제공한다고 공개한 AI 업무를 찾고, 고객의 처음 입력부터 최종 결과까지 이어지는 전체 흐름을 하나의 주장으로 정리하는 작업**이다.

기업이 AI를 어디에든 쓴다는 사실을 모으는 조사가 아니다. 사내 개발자가 코딩 에이전트를 쓴 사례, 일반적인 AI 업계 설명, 투자·성과 홍보는 Replica 대상이 아니다.

## 우리가 최종적으로 만들려는 것

우리가 필요한 것은 긴 기능 목록이 아니라 다음 세 가지다.

1. 고객이 어떤 상황에서 업무를 시작하는지
2. AI가 그 업무의 어떤 단계들을 수행한다고 회사가 직접 말했는지
3. 고객이 마지막에 어떤 완성된 결과를 받는지

세 가지를 한 **주장** 안에 함께 남긴다. 중간 단계는 주장을 잘게 쪼개는 기준이 아니라, 그 주장이 실제로 어떤 흐름인지 설명하는 내용이다.

별도의 `chain`으로 여러 주장을 연결하지 않는다. 고객 업무 전체가 주장 하나이고, 그 안의 순서는 `workflow.steps`에 기록한다.

## 수집하는 것과 수집하지 않는 것

### 수집한다

- 회사가 판매하거나 공개 제공하는 제품 기능
- 실제 고객 도입 사례에서 확인되는 기능
- 사용자가 넣는 자료에서 최종 업무 결과까지의 흐름이 드러나는 작업
- 모델, LLM, 에이전트, 머신러닝, NLP, 검색·생성 등 AI가 그 작업을 한다는 직접 표현
- 기능 사이의 순서와 전달물까지 출처가 설명한 경우 그 관계

### 수집하지 않는다

- “우리 직원들이 AI 에이전트를 쓴다”는 사내 활용
- “AI는 보험 사기를 탐지할 수 있다” 같은 일반 산업 설명
- 투자 유치, 고객 수, 보안 인증, 처리시간 단축 같은 사업·성과 정보
- AI라는 근거 없이 자동화된 규칙·템플릿·연동
- 사용자에게 나오는 결과가 없는 내부 구조나 기술 속성
- 출처가 말하지 않은 중간 단계와 연결 관계

사내 활용이 제품 구현의 힌트가 될 수는 있다. 그때도 고객 기능 주장으로 세우지 않고, 관련 고객 기능의 참고 근거로만 남긴다.

## 주장 하나가 통과하려면

주장 하나는 다음 네 질문에 모두 “예”라고 답할 수 있어야 한다.

### 1. 이 회사의 작업인가

출처가 회사, 회사 제품 또는 실제 고객 배포를 분명히 지목해야 한다. 회사 블로그에 실렸다는 이유만으로 회사 기능이라고 보지 않는다.

### 2. 외부 고객이 받는 기능인가

외부 사용자가 결과를 받는 공개 제품이거나 고객 배포여야 한다. 회사 내부의 개발·영업·지원·운영 업무는 제외한다.

### 3. 처음과 끝이 있는 실제 업무인가

고객이 넣는 자료나 요청과, 전체 흐름이 끝났을 때 받는 결과 또는 판단이 있어야 한다.

예를 들어 “AI 보험 플랫폼”은 작업이 아니다. “보험 제출 문서를 받아 정규화된 심사 요약을 돌려준다”는 작업이다.

### 4. 그 작업을 AI가 한다고 직접 적혀 있는가

회사나 제품이 AI 회사라는 사실만으로 추론하지 않는다. 해당 작업을 모델, LLM, 에이전트, 머신러닝 등이 한다는 문장이 필요하다.

“AI 기반 플랫폼이다”라는 문장과 몇 문장 뒤의 “제안서를 만든다”를 이어 붙여 AI 제안서 생성 근거로 쓰지 않는다. 적어도 E2E 업무의 핵심 작업 하나는 같은 직접 문장 안에서 AI 표현과 실제 작업이 함께 확인돼야 한다.

모든 중간 단계가 AI 작업일 필요는 없다. 다만 AI가 하는 단계와 그렇지 않은 단계는 구분하고, 전체가 같은 고객 업무로 이어진다는 사실도 출처가 설명해야 한다.

## 왜 전체 흐름을 한 주장으로 두는가

Replica가 복제하려는 것은 중간 기능 하나가 아니라 고객이 실제로 끝까지 수행하는 업무다. 따라서 출처가 하나의 고객 요청에서 여러 단계를 거쳐 최종 결과를 만드는 흐름을 설명한다면, 단계가 많아도 우선 하나의 주장으로 유지한다.

주장 하나는 **한 고객 목적, 하나의 시작 조건, 하나의 최종 업무 결과**를 기준으로 잡는다. 중간에 분류표, 추출 데이터, 점수, 초안처럼 확인 가능한 결과가 생겨도 다음 단계로 계속 전달되는 중간 산출물이라면 별도 주장으로 만들지 않는다.

예를 들어 보험 제출 업무가 다음처럼 공개돼 있다고 하자.

1. 이메일과 첨부파일을 분류한다.
2. 문서에서 보험 필드를 추출한다.
3. 인수 기준을 검사한다.
4. 심사 요약을 만든다.
5. 승인된 건을 Salesforce에 등록한다.

이 다섯 단계가 한 제출 건을 심사 완료 상태로 만드는 연속된 업무라면 하나의 “보험 제출 심사” 주장으로 둔다. 단계들은 그 주장 안의 작업 순서와 중간 확인 항목으로 기록한다.

테스트도 전체 흐름을 기준으로 정상 입력, 경계 입력, 정보가 부족한 입력을 각각 끝까지 실행한다. 중간 단계 검사는 원인 파악을 위한 보조 항목이고, 최종 통과 여부는 고객이 받아야 할 마지막 결과로 판단한다.

## 무엇을 하나로 보고 무엇을 나누는가

### 같은 주장으로 합친다

- 고객이 해결하려는 목적이 같다.
- 시작 요청과 최종 결과가 같다.
- 중간 결과가 다음 단계로 이어지는 한 번의 연속 업무다.
- 다른 페이지가 같은 전체 업무나 그 안의 일부 단계를 설명한다.
- 채널, 산업별 예시, 문서 종류만 다르고 핵심 흐름은 같다.

이 경우 상위 E2E 주장 하나에 여러 출처와 세부 단계를 모은다. 먼저 발견된 세부 주장이 있더라도 나중에 상위 흐름이 확인되면 상위 주장에 병합한다.

### 정말 별개의 업무일 때만 나눈다

- 고객이 별도로 시작할 수 있는 독립 업무다.
- 해결하려는 목적과 최종 결과가 다르다.
- 한쪽을 수행하지 않아도 다른 쪽을 완결할 수 있다.
- 출처도 두 기능을 각각 독립된 제품이나 사용 사례로 설명한다.

중간 출력이 따로 보이거나 따로 시험할 수 있다는 이유만으로 나누지 않는다. 반대로 같은 제품 안에 있다는 이유만으로 목적이 다른 업무를 억지로 합치지도 않는다.

### 내부 단계로만 둔다

다음 결과를 만들기 위한 추출, 분류, 검색, 비교, 검증, 전송은 전체 흐름의 단계로 기록한다. 고객이 그 단계 자체를 별도 업무로 요청하고 완결된 결과를 받는다는 근거가 있을 때만 독립 주장으로 인정한다.

## 조사 에이전트와 컨트롤러의 역할

회사 자료는 다섯 범위로 나누어 본다.

1. 공식 제품·기술·도움말·API·데모 자료
2. 기술·엔지니어링 블로그 전체
3. 발견된 제품명과 기능명의 추가 검색
4. 인터뷰·발표·채용·고객·파트너 자료
5. 공시·논문·특허·신뢰할 수 있는 보도

각 조사 에이전트는 자기 범위에서 다음을 즉시 남긴다.

- 출처가 설명하는 고객 업무 전체
- 시작 입력, 중간 단계, 최종 결과
- 회사·고객·AI 판단에 사용한 짧은 원문 근거
- 조사 중 우연히 발견한 샘플, 출력 예시, API, 스키마 같은 복제 단서
- 자기 범위만으로 결론 내릴 수 없는 보류 항목
- 명백한 탈락 항목과 이유

컨트롤러는 다섯 결과를 모두 본 뒤에만 다음을 결정한다.

- 같은 전체 업무의 중복 제거
- 세부 주장과 상위 E2E 주장의 병합
- 하나의 주장 안에 들어갈 단계와 정말 독립된 업무의 최종 경계
- 보류 항목의 승격, 근거 편입 또는 최종 탈락
- 사내 활용과 일반 산업 설명의 제거

조사 에이전트가 혼자 상위·하위 관계를 확정하지 않는 이유는 자기 범위 밖에 전체 흐름을 설명하는 출처가 있을 수 있기 때문이다.

## 보류는 탈락과 다르다

다음 항목은 한 조사 범위만 보고 버리지 않는다.

- 현재 출처에는 회사 귀속이 없지만 다른 출처에 있을 수 있음
- 현재 출처에는 고객 제공 근거가 없지만 제품 페이지에 있을 수 있음
- 현재는 기술 속성처럼 보이지만 다른 워크플로의 일부일 수 있음

컨트롤러는 모든 범위를 확인한 뒤 각 보류 항목을 반드시 다음 중 하나로 처리한다.

- 새 주장으로 승격
- 기존 주장의 근거로 편입
- 상위 E2E 주장의 단계 근거로 편입
- 이유를 남기고 최종 탈락

처리하지 않은 보류 항목이 하나라도 있으면 1차 조사를 완료할 수 없다.

## 근거를 어떻게 읽는가

각 주장에는 두 종류의 근거가 필요하다.

### 고객 제공 근거

어떤 회사·제품·고객 배포가 누구에게 기능을 제공하는지 보여준다. 사내 직원만 등장하면 통과하지 않는다.

### AI 작업 근거

어떤 AI 장치가 어떤 작업을 수행하는지 보여준다. AI 표현과 주장 작업이 같은 직접 문장에 있어야 한다.

주장 안의 단계 순서에도 출처 근거가 필요하다. “두 기능이 보기에 이어진다”는 추정만으로 하나의 E2E 업무라고 만들지 않는다.

## 1차 결과 숫자를 읽는 법

앞으로는 두 숫자를 구분한다.

- **발견 기록 수**: 조사 중 모은 기능 문구와 세부 작업 수
- **최종 주장 수**: 중복과 하위 단계를 상위 흐름에 병합한 E2E 업무 수

발견 기록이 많다고 기업이 그만큼 많은 독립 워크플로를 운영한다는 뜻은 아니다. 한 E2E 주장을 여러 페이지가 설명하거나 그 안의 여러 단계를 따로 홍보할 수 있다.

예를 들어 계약 조항 추출, 위험 판정, redline 생성은 각각 발견되더라도 한 번의 계약 검토를 완성하는 단계라면 최종적으로 하나의 계약 검토 주장에 들어간다.

## 1차에서 하지 않는 판단

1차는 다음을 판단하지 않는다.

- 복제가 쉬운가
- 사업 가치가 큰가
- 경쟁력이 강한가
- 우선순위가 높은가
- 실제 정확도가 회사 설명과 같은가

1차는 오직 “고객 대상 AI 업무라는 공개 근거가 있는가”와 “처음부터 끝까지 어디까지를 하나의 주장으로 볼 것인가”만 확정한다.

복제 가능성, 공개 데이터, 평가 방법과 최종 테스트 계약은 2차에서 E2E 주장별로 조사한다.

## 현재 Wordsmith와 FurtherAI 재정리 결과

현재 저장된 Wordsmith 37개와 FurtherAI 30개는 이 방법론이 적용되기 전에 만든 발견 기록이다. 숫자 자체를 독립 워크플로 수로 보면 안 된다.

저장된 출처와 인용을 이 방법론으로 다시 판정한 결과는 다음과 같다.

- Wordsmith: 발견 기록 37개 → 최종 고객 대상 AI E2E 주장 10개
- FurtherAI: 발견 기록 30개 → 최종 고객 대상 AI E2E 주장 12개

이 숫자는 새 웹 조사를 수행한 결과가 아니라 기존 근거를 현재 기준으로 정규화한 1차 판정이다. 원본 `research.json`은 아직 v1 발견 기록을 보존하고 있으며, 자세한 병합·제외 근거는 각 기업 요약 문서에 기록돼 있다.
