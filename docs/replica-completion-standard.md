# Replica 복제 실험과 실행 완료 기준

정리 기준일: 2026-09-08

2026-09-08 모델 변경: Codex 조율 Replica Agent와 Operator는 `gpt-6-astra`·`medium`을
사용한다. 이 문서에서 Sol이라고 부르는 역할의 책임은 그대로이며 모델만 변경했다.
Terra는 `gpt-5.6-terra`·`high`를 명시한다. 기존 실행의 모델·설정·증거는 덮어쓰지 않는다.

기능마다 Operator·Builder 한 쌍을 만들고 선택된 모든 기능의 쌍을 동시에 활성화한다.
기능이 N개면 N쌍이며, 앞 기능의 완료를 기다리는 고정 개수의 순차 묶음으로 실행하지
않는다. 쌍 등록과 상태 기록만 순서대로 처리하며, 실제 실행 환경의 Agent 수 제한으로
전체 쌍을 만들거나 활성화하지 못하면 그 제한을 실행 결과에 명시한다.
메시지 응답을 기다리는 Agent는 턴을 반환하고 같은 ID로 재개해 다른 기능의
실제 구현에 필요한 실행 자리를 확보한다.

이 문서는 Replica의 목표 수준, 단계별 책임, 결과물과 향후 수정 작업의 기준이다.
아래 요구사항을 문서에 반영했다고 제품 코드에 구현된 것은 아니다. 현재 구현에서
유지할 부분과 수정할 부분은 마지막의 「현재 구현과 수정 작업」에 구분한다.

## 목적

Replica의 목적은 서비스·애플리케이션 기업의 핵심 기술을 실제로 복제해,
쉽게 재현되는 고객 가치와 추가 자원이 필요한 부분을 확인하고 투자 실사의
판단 근거를 만드는 것이다. 공개 자료에서 확인한 고객 대상 기능 하나의 전체
워크플로를 공개적으로 구할 수 있는 OSS, API, 데이터와 코드로 구현한다.

외부 팀이 주어진 시간·비용 안에서 어떤 고객 작업을 어느 품질까지 재현했는지,
어디에서 실패했고 무엇이 부족했는지를 실행 증거로 설명해야 한다. 원제품 전체의
상용 서비스나 비공개 내부 구조를 동일하게 만드는 것을 기본 목표로 삼지 않는다.

복제에 성공한 결과는 다음 문장을 뒷받침할 수 있어야 한다.

> 2차 조사에서 준비한 경로로 핵심 고객 작업을 구현하고, 코드를 바꾸지 않은 채
> 새로운 유효 입력에도 실행했다. 그 결과로 재현한 범위와 품질, 투입 자원,
> 남은 격차와 판단할 수 없는 부분을 확인했다.

테스트 통과만을 위한 구현이나 특정 기업 이름에 맞춘 데모는 Replica가 아니다.
성공하더라도 원제품의 비공개 모델, 코드, 데이터, 품질, 규모 또는 운영 환경과의
동등성을 뜻하지 않는다.

기능의 기술적 대체 가능성과 기업 전체의 해자는 구분한다. 고객 관계, 유통,
데이터 권리, 업무 통합, 신뢰와 전환 비용은 별도 근거가 필요하다. 복제 성공만으로
해자가 없다고 결론 내리거나, 우리 실행의 실패만으로 해자가 있다고 결론 내리지
않는다.

## 복제품의 목표 수준과 UI

기본 목표는 처음 보는 대표 입력으로 핵심 고객 작업을 끝내고, 품질·비용·실패를
측정할 수 있는 복제품이다. 기능 개수나 화면 유사도를 기준으로 「제품의 80%」와
같은 완성률을 매기지 않는다. 고객이 구매하는 이유와 연결된 기능을 기준으로 본다.

- 실제 입력과 자산을 읽는다.
- 공개 claim의 전체 workflow를 실행한다.
- 고객이 받는 최종 산출물이나 후속 작업을 만든다.
- 구현 코드를 바꾸지 않고 새로운 유효 입력에도 다시 실행된다.
- 테스트와 특정 기업에 과적합되지 않았음을 평가로 확인한다.
- 실행 코드, 명령, 실제 입출력, 품질, 투입 자원과 한계를 함께 남긴다.

UI가 없어도 실행 명령이나 runner로 해당 고객 작업을 재사용할 수 있으면
`reproduced`가 될 수 있다. 고객 작업의 핵심이 화면 조작이나 상호작용에 있다면
그 부분은 2차 계약과 평가 범위에 포함한다. 기능과 무관한 회원가입·결제·관리
화면은 기본 요구사항이 아니다. 필요한 UI는 평가된 동일한 구현을 호출해야 하며,
UI 전용 응답이나 별도 데모 로직을 만들지 않는다.

상용 규모, 장기 안정성과 고객 시스템 통합은 투자 논점에 중요한 경우 별도 범위를
정해 검증한다. 작은 입력에서 작동한 결과를 대규모 운영 성능으로 확대하지 않는다.

## 복제 단위

복제 단위는 고객 대상 claim 하나의 전체 end-to-end workflow다.

```text
실제 입력
-> 공개 claim에 포함된 처리 단계
-> 고객이 받는 최종 산출물 또는 후속 작업
```

중간 단계가 따로 관찰되거나 테스트 가능하다는 이유만으로 별도 Replica로
쪼개지 않는다. 독립된 사용자, 입력, 고객 목적 또는 최종 산출물이 있을 때만
별도 workflow로 취급한다.

기업별 사실, 사람별 자료와 제품별 설정은 근거·입력 자산·설정으로 들어갈 수 있다.
공통 실행기, 평가기와 자산 준비기는 회사명, claim ID 또는 테스트 ID에 따라
동작을 바꾸면 안 된다.

## 단계별 역할과 인계

2차 조사는 복제를 시작할 수 있는 근거와 계약을 준비한다. 무엇을 어떻게 구현하고
어떤 기술·데이터를 사용할지, 더 단순한 대안이 있는지 조사하는 책임은 2차에 있다.
Sol이나 Terra에 이 조사 책임을 넘기지 않는다.

| 단계 | 책임 | 지켜야 할 경계 |
|---|---|---|
| 2차 조사 | 고객 작업, 기술·데이터·구현 경로·대안·제약·평가 근거를 조사하고 계약 준비 | 확인하지 못한 내용은 미확인으로 기록하며 구현 가능성을 임의로 단정하지 않음 |
| 인계 절차 | 조사 내용과 실행 대상 경로를 보존해 전달 | 하네스의 선택·요약 때문에 기능, 필수 입력, 구현 의도나 평가 기준을 축소하지 않음 |
| Sol Operator | 조사 결과를 파일·함수·명령·검사 순서로 구체화하고 Terra의 실패를 분석해 수정 지시 | 새로운 기술 접근을 임의로 조사하거나 고객 기능과 합격 기준을 낮추지 않음 |
| Terra Builder | Sol의 지시에 따라 구현·실행·개발 테스트를 수행하고 실측 증거 반환 | 독자적으로 재설계하거나 실행하지 않은 동작을 성공으로 기록하지 않음 |
| 평가·보고 | 정해진 기준으로 실제 결과·품질·투입 자원·격차를 검증하고 해석 | 구현 결과를 본 뒤 기준을 낮추거나 개발 테스트 통과를 최종 평가로 대체하지 않음 |

함수 구성, 실행 명령과 구현 오류 수정은 Sol/Terra의 정상적인 구현 책임이다.
조사에 없는 기술 접근이나 계약 변경이 필요하면 부족한 내용을 기록해 2차 보완
대상으로 돌린다. 동결된 원본과 기존 평가 기록을 덮어쓰지 않고, 보완된 계약으로
시작한 실험을 구분한다.

### 2차에서 준비하고 인계할 내용

- 고객이 수행하려는 핵심 작업, 실제 입력 조건과 최종 결과
- 조사된 구현 경로, 사용할 기술·데이터·의존성, 접근·라이선스 조건
- 조사된 대안이 있다면 적용 조건, 차이와 선택 근거
- 실행 대상으로 정한 경로 또는 경로 선택의 우선순위와 조건
- 고객 품질 기준, 반드시 지켜야 하는 조건, 중요한 실패와 비교 자료
- 공개 개발 예시, 평가에 사용할 수 있는 자산과 확인하지 못한 범위

2차에 이미 충분한 내용이 있으면 다시 조사하거나 형식만 늘리지 않는다. 부족한
조사만 2차에서 보완한다. 2차의 예상 난도·비용과 실행에서 측정한 값은 구분한다.

원제품과 다른 구현 방법도 2차에서 조사해 계약에 포함할 수 있다. 이 경우 같은
고객 작업과 품질을 충족하는지 비교한다. 쉬운 입력으로 바꾸거나 필수 처리 단계를
제거한 경로는 같은 기능을 재현했다고 취급하지 않는다. Sol/Terra는 인계된 경로를
임의의 규칙·템플릿·고정 응답으로 바꾸지 않는다.

Sol에는 해당 주장의 전체 2차 조사를 보존해 전달하고, Terra에는 실행에 필요한
workflow·findings·구현 경로·입출력·합격 기준을 보존해 전달한다. 봉인 평가의
입력·정답·reference facts를 Builder에게 숨기는 것과 조사 범위를 축소하는 것은
구분한다.

실행 단계는 그 계약을 바탕으로 다음을 만든다.

```text
2차 replication contract
-> Sol의 구체적인 구현·수정 지시
-> 실제 입력 자산 준비
-> Terra의 claim별 구현·실행·개발 테스트와 실측 기록
-> 재사용 가능한 실행 명령과 runner
-> 구현과 분리된 최종 평가
-> 실제 최종 산출물 저장
-> 재현 범위·품질·비용·남은 격차와 추가 실사 질문 보고
```

## 완료 조건

다음 조건을 모두 만족해야 `reproduced`로 기록한다. 복제품의 성공 판정과 복제
실험 자체의 완료 판정은 구분하며, 실험 종료 기준은 뒤에서 별도로 정의한다.

### 1. 실제 구현이 존재한다

- 2차 조사에 근거해 실행 대상으로 인계된 구현 경로를 실제로 실행한다.
- `oss_only`, `commercial_api`, `proprietary_data` 중 사용한 의존성 수준을 정확히
  기록한다.
- 구현 형태는 계약에 맞춰 `prompt_only`, `code`, `hybrid` 중 가장 작은 것으로
  정한다.
- 원제품의 내부 구현을 흉내 낼 필요는 없지만, 공개 claim의 전체 입력부터 최종
  출력까지의 흐름은 실제로 수행해야 한다.
- 구현 코드, 실행 진입점, 의존성, 필요한 환경변수와 실행 명령을 남긴다.
- 범용·제3자 API를 사용할 때는 그 의존성을 기록한다. 복제 대상 기업의 핵심
  API를 호출해 얻은 결과는 그 기업의 핵심 기술을 복제한 증거로 세지 않는다.

### 2. 실제 입력을 처리한다

- 텍스트 기능은 실제 문서나 실행 가능한 합성 문서를 읽어야 한다.
- 문서·이미지 기능은 실제 파일을 파싱하거나 계약에 포함된 경우 OCR해야 한다.
- 음성·영상 기능은 실제 미디어 파일을 모델이나 API에 전달해야 한다.
- 검색 기반 기능은 실제 corpus나 index에서 검색해야 한다.
- 외부 작업 기능은 실제 작업 객체나 안전한 로컬 sink에 결과를 전달해야 한다.
- 입력 설명만 문자열로 전달하고 파일·검색·모델·API를 사용한 것처럼 출력하면
  안 된다.
- 사용한 입력의 경로 또는 식별자, 미디어 타입, 해시, 출처와 사용 조건을 기록한다.
- 합성 입력은 실제 고객 입력의 어떤 특성과 난도를 포함하거나 제외했는지 기록한다.
  합성 예제에서의 성과를 실제 고객 데이터 전체에 대한 성과로 확대하지 않는다.
- 사람이 대신한 전처리, 자료 정리와 결과 수정은 숨기지 않고 투입 자원에 포함한다.

### 3. 전체 workflow를 수행한다

- 계약에 포함된 필수 단계가 실제 실행 기록이나 최종 산출물로 확인돼야 한다.
- 앞 단계의 결과가 다음 단계의 입력으로 실제 사용돼야 한다.
- 파일 처리, 검색, 모델 판단 또는 외부 작업이 필요한 workflow를 한 번의 고정
  응답으로 대체하면 안 된다.
- stateful workflow는 필요한 세션 상태를 보존하고, 입력 변화가 다음 행동에
  반영돼야 한다.

### 4. 고객이 받는 최종 산출물이 나온다

테스트 로그나 중간 상태만으로는 완료하지 않는다. claim의 `workflow.output`과
replication contract의 `output`에 해당하는 실제 파일, 결과 또는 후속 작업을
남긴다.

자동화의 결과를 안전한 로컬 sink나 테스트 환경에서 검증했다면 그 범위를 표시한다.
실제 고객 시스템과의 통합·전달까지 검증했다고 표현하지 않는다.

| 기능 | 최소 최종 산출물 |
|---|---|
| 생성·분석 | 완성된 텍스트, JSON, 보고서 또는 구조화 결과 |
| 검색 기반 대화 | 실제 자료를 검색해 만든 답변과 근거 인용 |
| 사람·프로필 기반 대화 | 승인된 자료로 구성한 재사용 가능한 persona와 새 질문에 대한 답변 |
| 인터뷰 | 답변에 따라 달라진 질문, 저장된 요약과 인사이트 |
| 업무 자동화 | 조건 판정, 발생 기록과 실제 후속 작업 payload |
| 음성 | 참조 음성을 사용해 생성한 재생 가능한 음성 파일 |
| 영상·아바타 | 실제 입력에서 생성한 재생 가능한 영상 파일 |

### 5. 다시 사용할 수 있다

- 구현 코드를 수정하지 않고 같은 계약을 따르는 새로운 입력을 처리할 수 있어야
  한다.
- 다른 사용자가 따라 할 수 있는 실행 명령이나 runner를 제공한다. 화면이나 서버가
  고객 작업의 필수 요소라면 계약에서 그 필요성과 검증 범위를 명시한다.
- 사람 Replica는 한 번 구성한 persona와 corpus를 여러 질문에서 재사용할 수 있어야
  한다.
- 파일 workflow는 파일명이나 저장 위치가 달라도 지원 형식과 계약이 같으면
  실행돼야 한다.
- 공개 claim 자체가 상호작용을 요구하면 runner나 대화형 CLI로 그 상태 변화를
  검증한다. 필요한 화면 조작은 계약에 따르고, 단순한 시각적 유사도는 별도로 다룬다.

### 6. 테스트와 기업에 과적합되지 않는다

- Builder는 봉인 테스트의 입력, 기대값, reference facts와 원제품 출력을 보지
  않는다.
- 구현은 테스트 ID, fixture 이름, 고유 숫자, 정답 문자열, 회사명 또는 claim ID를
  조건으로 분기하면 안 된다.
- 공개 개발 예시와 다른 내용·길이·순서·표현을 가진 novel 입력을 구현 전에
  준비하고 기대 동작을 동결한다.
- 단순히 이름이나 숫자만 바꾼 복사본을 novel 입력으로 세지 않는다.
- 테스트에 `novel` 같은 종류 이름이 있다는 사실만으로 일반화를 인정하지 않는다.
  어떤 자료·조건이 개발 예시와 달라졌고 어떤 결과가 나왔는지 확인한다.
- 의미는 같고 표현만 다른 입력, 무관한 필드가 추가된 입력, 순서가 바뀐 입력처럼
  결과가 유지돼야 하는 경우에는 metamorphic 검사를 포함한다.
- 입력의 핵심 사실이나 조건이 바뀌면 결과도 그 변화에 맞게 달라지는지 확인한다.
- 같은 workflow 계약에 다른 기업·사람·문서의 허용된 자산을 넣었을 때 공통
  실행기나 평가기를 수정하지 않고 실행할 수 있어야 한다.
- 특정 기업에 필요한 사실과 스타일은 근거가 있는 prompt, corpus, schema 또는
  config로 표현하고 공통 코드에 숨겨 넣지 않는다.
- 후보 생성과 판정은 별도 실행 단계로 둔다. 완전히 독립된 Judge가 아니면 그
  사실을 보고서에 기록한다.

### 7. 품질·투입 자원·결과와 한계를 함께 남긴다

보고서는 최소한 다음을 기록한다.

- 어떤 공개 기능과 전체 workflow를 복제했는지
- 어떤 OSS, API, 모델, 데이터와 코드를 실제 사용했는지
- 실제 입력과 생성된 최종 산출물
- 정상·경계·정보 부족·novel 입력의 결과
- 고객 기준의 충족 여부와 중요한 조건별 품질·실패 결과
- 개발·수정·데이터 준비·실행에 든 자원과 사람의 개입
- 원제품 또는 업무 기준과의 비교 근거 및 비교하지 못한 항목
- 재사용 실행 방법
- 원 기능과 비슷하게 재현된 범위
- 확인하지 못했거나 제외한 범위
- 어느 scenario에서 처음 재현됐는지

기록은 다음 기준을 따른다.

| 항목 | 필요한 기록 |
|---|---|
| 품질 | 2차에서 준비한 기준, 평가 입력의 수와 대표성, 조건별 결과, 중요한 오류의 종류·심각도 |
| 개발 노력 | 개발·수정 시도, 실제 작업 시간과 대기 시간, 사람이 개입한 작업과 시간 |
| 데이터 준비 | 자료 확보·정리·라벨링·전처리에 든 노력과 확인 가능한 비용 |
| 실행 자원 | 사용 모델·버전, 측정 가능한 토큰·API·컴퓨팅 사용량, 처리 시간과 재시도 |
| 비용 | 확인 가능한 개발·실행 비용, 산정 기준·시점·통화, 실측·추정·미측정 구분 |
| 비교 | 원본 출력이나 업무 기준의 출처, 입력·버전·조건, 원제품 측정값의 유무 |

알 수 없는 값은 미측정 또는 미확인으로 남기며 0으로 채우지 않는다. 구독형 CLI의
사용료가 별도 청구되지 않았다고 실제 실행 비용을 0으로 단정하지 않는다. 일부
핵심 비용이 미측정이면 경제성 판단도 제한한다. 기존 시도·결과·보고서 기록을
재사용하고 불필요한 중복 기록을 만들지 않는다.

원제품을 같은 입력으로 실행한 결과가 있으면 그 범위에서 직접 비교한다. 없으면
공개 주장이나 업무 기준에 대한 충족 여부만 평가하며 원제품 점수·일치율·비용을
만들어내지 않는다. 기존 `direct`, `public`, `claim_only` 근거 수준과 원본 관찰
기록을 활용한다. 사후 사용자 관찰을 동결된 독립 평가와 혼동하지 않는다.

전체 평균만으로 판단하지 않는다. 예를 들어 일반 질문과 최신·상충 문서 질문의
결과를 구분해 고객에게 중요한 조건에서의 격차를 드러낸다. 제한된 표본의 비슷한
점수를 원제품과 동등하다는 증거로 확대하지 않는다.

## 테스트 전용 또는 기업 전용 구현으로 보는 경우

다음 중 하나라도 해당하면 테스트가 통과해도 실제 복제로 인정하지 않는다.

- 테스트 문구, case ID, fixture 이름, 고유 숫자나 정답 문자열로 분기한다.
- 기대 결과를 그대로 반환하거나 테스트별 응답을 미리 저장한다.
- 회사명이나 claim ID를 보고 미리 작성한 구현 또는 출력을 선택한다.
- 특정 입력 파일명, 절대 경로, 시트 순서, 행 번호만 인식한다.
- 문서 검색을 주장하면서 실제 문서나 index를 읽지 않는다.
- OCR을 주장하면서 입력 이미지의 알려진 문장을 코드에서 반환한다.
- 적응형 인터뷰를 주장하면서 모든 입력에 같은 질문이나 고정 인사이트를 반환한다.
- 자연어 조건 판별을 주장하면서 하나의 예시 표현만 인식하는 규칙을 쓴다.
- 사람 Replica를 주장하면서 질문과 무관한 고정 말투 문장이나 인용을 반환한다.
- 음성 복제를 주장하면서 참조 음성을 사용하지 않고 일반 TTS 음성을 만든다.
- 상용 API scenario를 실행했다고 기록하면서 실제 API를 호출하지 않는다.
- 복제 대상 기업의 핵심 API 응답을 반환하고 그 핵심 기술을 복제했다고 기록한다.
- 출력 파일은 만들었지만 해당 입력이 결과 생성에 사용되지 않는다.
- 구현과 Judge가 같은 테스트 전용 규칙이나 정답 데이터를 공유한다.

결정론적 규칙이나 단순한 코드를 쓰는 것 자체는 문제가 아니다. 2차에서 조사해
계약에 포함한 방법으로 새로운 입력에서도 전체 workflow와 고객 품질 기준을
충족한다면 유효한 구현 경로다. 다만 Sol/Terra가 조사된 경로를 임의로 축소하거나
알려진 회사·샘플·테스트만 구현한 경우는 인정하지 않는다.

## 실행과 평가 분리

- Builder는 공개 계약, 공개 근거, 입력 형식과 개발 예시만 받는다.
- Evaluator는 봉인 테스트, 기대 동작과 reference facts를 별도 영역에 보관한다.
- 결정론적으로 판정할 수 있는 schema, 계산, 인용, 파일과 side effect를 먼저
  검사한다.
- 의미적 품질만 Judge가 평가한다.
- 생성형 결과는 문장이 완전히 같아야 한다는 공통 규칙으로 평가하지 않는다.
  2차 계약에 정한 사실·근거·금지 행동·고객 품질이 반복 실행에서도 유지되는지
  확인한다. 계산값·권한·중복 작업 방지처럼 결정성이 필요한 조건은 그대로 검사한다.
- 반드시 지켜야 하는 조건과 품질 측정 항목을 구분한다. 품질 목표와 허용 오류는
  실행 전에 정하고, 결과를 본 뒤 합격 기준을 낮추지 않는다.
- Builder의 개발 테스트와 실행 기록은 보존하되 최종 평가를 대신하지 않는다.
  평가 단계는 해당 구현의 해시와 실제 실행 결과를 결속해 판정한다.
- 같은 candidate를 같은 봉인 입력에 반복 제출해 정답을 추측하지 않는다.
- 한 scenario의 봉인 평가 제출은 최대 세 번이며, 실패 이유와 부족한 부분을
  기록한다.

Sol/Terra의 개발 수정 횟수와 봉인 평가 제출 횟수는 구분한다. 현재 Agent 경로의
초기 구현 1회와 최대 3회 수정은 개발 루프의 한도이며, 봉인 평가를 그만큼 추가로
허용한다는 뜻이 아니다. 시간·비용 예산과 종료 조건은 실행 전에 정하고,
실제 종료 사유는 실행 기록과 함께 남긴다.

## 사용자가 받는 결과물

| 결과물 | 내용 | 사용자가 확인할 수 있는 것 |
|---|---|---|
| 실행 가능한 복제품 | 코드·의존성·실행 명령과 사용 가능한 입력 자산 | 새 입력을 넣었을 때 실제로 작동하는가 |
| 실험 증거 | 공개 가능한 대표 입출력, 평가 요약, 시간·비용·수정 기록과 증거 연결 | 어떤 조건과 노력으로 그 결과가 나왔는가 |
| 판단 보고서 | 재현 범위, 품질 격차, 실패 원인, 미확인 사항과 추가 실사 질문 | 무엇이 쉽게 재현되며 어디를 더 확인해야 하는가 |

공개 입출력 예시는 봉인 평가와 별도로 준비한다. 평가 요약과 근거 연결은 제공하되
봉인 입력·정답·사례별 채점 결과는 Builder가 접근하는 공개 run에 복사하지 않는다.
구현에 실패했다면 남은 코드·부분 산출물의 사용 가능 범위를 표시하고 실행 가능한
완제품으로 소개하지 않는다.

### 최소 산출물의 구성

각 scenario의 결과는 논리적으로 다음 구성을 갖는다. 실제 경로와 JSON 필드는
기존 run·manifest·보고서 구조를 재사용해 구현하고, 비용 기록만을 위한 별도
플랫폼을 만들지 않는다. 아래는 목표 구성이며 현재 코드의 완성 상태를 뜻하지 않는다.

```text
공개 run/
├── replica.json
├── replica-spec.json
├── assets/                 # 재배포 가능한 입력 자산이 필요할 때
├── implementation/
│   ├── manifest.json
│   └── 실행 코드
├── artifacts/              # 최종 산출물이 파일일 때만
├── 공개 가능한 대표 입력·출력 예시
├── replica-result.json
├── completion-assessment.json
└── report.md

평가 전용 영역/
├── tests.json
├── test-suite-lock.json
├── replica_outputs.jsonl
├── results.jsonl
└── 평가 근거와 실행 기록
```

`implementation/manifest.json`에는 실행 진입점, 입력·출력, 의존성, 필요한
환경변수와 실행 명령이 있어야 한다. `implementation/`은 같은 계약의 새 입력을
다시 처리할 수 있어야 한다.

UI의 필요성은 앞의 「복제품의 목표 수준과 UI」와 2차 계약에 따른다. 이 기준만으로
별도의 브라우저 UI 생성이나 외부 배포를 추가하지 않는다.

## 판정 용어

| 판정 | 의미 |
|---|---|
| `reproduced` | 실제 구현이 전체 workflow를 수행하고 고객 품질·재사용·일반화 평가를 통과함 |
| `partially_reproduced` | 실제 구현과 산출물은 있으나 계약 일부 또는 재사용 조건을 충족하지 못함 |
| `not_reproduced_on_this_path` | 선택한 구현 경로와 입력으로는 재현하지 못함 |
| `execution_blocked` | 필요한 입력, 권한, 자격 증명 또는 실행 환경을 준비하지 못함 |

`IMPLEMENTATION_READY`는 구현 묶음의 구조와 파일을 검증한 하네스 상태다.
Terra가 개발 실행을 했을 수도 있지만 이 상태 자체가 최종 평가 통과나
`reproduced`를 의미하지는 않는다. 개발 테스트 통과와 최종 복제 판정을 구분한다.

모든 경로가 실패해도 기능 자체가 복제 불가능하다고 확대하지 않는다. 성공해도
원제품 전체 또는 비공개 구현과 동등하다고 표현하지 않는다.

## 실험 완료와 판단의 범위

복제품의 성공 여부와 실험의 완료 여부는 별도로 기록한다. 복제에 실패해도 사전에
정한 실험 범위를 수행했거나 예산·접근 조건 때문에 종료한 사유를 증거로 남겼다면
실험은 완료할 수 있다. 단순한 에이전트 종료나 파일 생성만으로 완료하지 않는다.

실험을 완료하려면 다음이 확인돼야 한다.

- 대상으로 삼은 고객 작업, 인계된 계약·경로와 실행 조건이 명확하다.
- 수행한 시도, 도달한 결과·품질, 투입 자원과 종료 사유를 확인할 수 있다.
- 평가하지 못한 항목과 그 이유가 구분돼 있다.
- 부분 결과와 실패도 포함해 보고서와 근거를 남겼다.
- 같은 조건으로 재실행할 방법 또는 재실행에 부족한 자원을 설명한다.

실패 사유는 구현 결함, 품질 미달, 데이터 부족, 접근 권한 부족, 환경 오류,
시간·비용 예산 소진, 2차 조사 부족 등으로 구분한다. 각 사유에 실행 증거나
조사 근거를 연결한다. 해결할 수 없는 접근 문제를 같은 방식으로 반복하거나,
예산이 소진됐는데 성공할 때까지 계속 수정하도록 강제하지 않는다.

보고서는 관찰한 사실, 근거가 있는 해석, 추가 검증할 가설과 판단 불가 항목을
구분해야 한다.

| 관찰 결과 | 가능한 판단 | 추가로 필요한 확인 |
|---|---|---|
| 주어진 자원으로 대표 입력의 고객 기준을 충족 | 해당 범위는 공개 기술로 재현 가능 | 다른 조건·운영 규모와 고객 전환 장벽 |
| 특정 조건에서만 원제품 대비 품질 격차가 확인됨 | 그 조건이 추가 실사의 우선 대상 | 격차의 원인과 고객에게 미치는 중요도 |
| 데이터·권한·환경·예산 때문에 평가하지 못함 | 현재 조건에서는 판단 불가 | 부족한 자원 확보 후 재평가 가능성 |
| 원제품 출력이나 운영 비용을 확보하지 못함 | 정해진 업무 기준 충족 여부만 평가 | 원제품과의 직접 품질·경제성 비교 |

조사 단계의 `moat` 점수는 기업이 주장하는 차별점과 조사 우선순위에 관한 정보다.
실행으로 확인된 기술 장벽이나 기업 가치 점수로 그대로 사용하지 않는다. 복제한
기능 수나 전체 통과율을 회사 전체의 「해자 비율」로 환산하지 않는다. 실제로
실행하지 않은 주장도 기업 보고서에 남기고 제외·미평가 사유를 밝힌다.

## workflow별 적용 예시

### 사람·프로필 기반 대화

허가되거나 공개적으로 사용할 수 있는 글, 인터뷰와 프로필을 실제로 읽어 persona,
system prompt와 검색 corpus를 구성한다. 완성된 Replica는 구현할 때 보지 못한
질문에도 자료에 근거해 답하고, 확인되지 않은 개인 사실은 추측하지 않으며, AI
Replica임을 사용자에게 표시해야 한다.

### PDF 요약

실제 PDF를 파싱하고 계약에 포함된 경우 OCR과 모델 요약을 실행해 요약 파일을
만든다. 구현할 때 사용한 PDF와 다른 문서에서도 실행돼야 하며, 지원하지 않는
암호화·손상·스캔 형식은 실패를 숨기지 말고 명확히 보고해야 한다.

### 외부 작업

임의의 계약 범위 내 조건과 이벤트를 처리하고 실제 후속 작업 payload를 안전한
로컬 sink 또는 승인된 외부 시스템에 기록한다. payload를 문자열로 출력만 하고
작업이 실행됐다고 기록하면 안 된다.

## 현재 구현과 수정 작업

최초 대조 기준은 `codex/sol-terra-implementation-bundle`의 `aee0f19`다.
2026-09-07에 `codex/replica-completion-test`에서 구현 부분을 수정했다.
사용자의 후속 지시에 따라 결과 보고서 개편은 이번 작업에서 제외했다.
아래 목표 전체와 이번에 구현·검증한 범위를 구분한다.

### 유지할 기반

- Sol에 전체 2차 조사를 전달하고 Terra에 workflow·findings·실행 계약을 제공한다.
- Sol의 실행 지시·수정 판단과 Terra의 구현·실행 책임을 유지한다.
- 조사 근거에 따른 파일·corpus·OSS·모델·API 사용과 다중 파일 구현을 허용한다.
- 실제 모델·검색을 사용한 일부 Delphi 구현과 개발 테스트 기록이 이미 있다.
  이를 단순한 JSON 데모나 미실행 파일로 취급하지 않는다.
- 파일 해시, 계약 결속, 봉인 평가 분리와 기존 원본 관찰·근거 수준을 재사용한다.

### 수정 순서와 완료 조건

| 순서 | 작업 | 완료 조건 |
|---|---|---|
| 1 | 이 문서의 목적·역할·완료 기준 반영 | 조사와 구현의 책임, 복제 성공과 실험 완료가 명확히 구분됨 |
| 2 | 기존 2차 조사와 인계 점검 | 필요한 내용이 충분하고 자동 선택·요약으로 기능이나 구현 의도가 축소되지 않음. 부족한 조사는 2차에서만 보완함 |
| 3 | 다중 파일 구현의 최종 평가·공개 연결 | Builder 피드백과 별도로 실제 실행을 검증하고, 평가된 구현과 결과·판정을 결속해 공개함 |
| 4 | 시간·비용·사람 개입 기록 | 기존 시도·결과 기록에서 확인 가능한 실측과 미측정 항목을 구분함 |
| 5 | 실험 완료·결과 보고 보완 | 실패·미평가를 포함해 재현 범위, 품질·비용 격차, 원인과 추가 실사 질문을 남김 |
| 6 | 기존 Delphi 기능 하나로 전체 흐름 검증 | 2차 → Sol → Terra → 새로운 입력의 최종 평가 → 실행 가능한 결과와 보고서가 실제 연결됨 |

### 2026-09-07 구현 작업의 반영 상태

- 2차의 명시적 경로 선택·우선순위를 사용하고, 없으면 조사 순서를 유지한다.
  Terra에는 봉인 정보를 제외한 대안 경로와 실행 계약을 보존한다.
- `agent-candidate-finalize`가 구조 검증에 이어 별도 프로세스의 최종 평가까지 실행한다.
  기본 Judge는 하네스의 모델 CLI이며, 같은 번들을 실제 실행·평가하고 기술 결과를 공개한다.
  명시적 `--bind-only`의 `IMPLEMENTATION_READY`에서는 새 하네스를 완료할 수 없다.
  `stdio_json`과 로컬 HTTP, 실제 파일 입력과 출력 파일 보존을 지원한다.
- Builder 개발 기록과 별도로 동결된 평가 입력·두 번의 출력·검사 결과·구현 검토를
  저장한다. 의미 품질·필수 값·변형 관계를 검사하고, 구현과 증거의 해시를 결속한다.
  새 입력의 차이, 기준 연결, Judge 또는 공개 예시가 부족하면 완전 재현으로 올리지 않는다.
- 기존 시도 기록에 시간·비용·사람 개입을 추가하고, 미측정은 null로 남긴다.
  접근 차단·조사 부족·예산 소진의 종료 사유를 보존한다. 관측한 의존성 버전과
  선언된 버전도 구분하며, 버전이 다르면 완전 재현 조건이 충족되지 않는다.
- 실패 후 `agent-bundle-retry`로 같은 쌍을 재개한다. 이전 코드·결과·자원을 보존하고
  개발 시작 시점과 전체 평가 예산·최대 3회 제출 한도를 유지한다. 같은 후보는 거절한다.
- 반복 실행과 공개 예시는 각각 새 세션에서 검증한다. 공개 예제는 봉인 자료·상태를
  물려받지 않는다. 새 파일 매핑과 연속 입력 세션으로 공개 번들을 재사용할 수 있다.
- 기존 Sol/Terra가 만든 Delphi 번들을 보존한 채 새 최종 평가와 공개 재실행을
  연결했다. 정상·경계·정보 부족·novel·변형 입력 6개가 통과했고 공개 번들도 새 질문에
  답했다. 이번에는 기존 구현 뒤에 평가를 준비했으므로 `partially_reproduced`로 남겼다.
  새 Sol/Terra Agent 쌍을 실행했다는 뜻은 아니다. 구현 전 동결은 신규 하네스 경로와
  통합 테스트에서 검증한다.
- 결과 보고서의 내용·형식, 회사 전체 미평가 claim 보고와 투자 판단 해석은 보류했다.
  기존 보고서 코드를 변경하거나 새 투자 판단 보고서를 생성하지 않았다.

구체적인 필드·명령과 제한은 [번들 실행 계약](./replica-bundle-execution.md)을 따른다.
실행 검증 자료는 `work/delphi/completion-implementation-check-2026-09-07/`에 있다.
기존 제한 Python 경로의 macOS 메모리 제한 오류도 수정했다. 프로세스 시작 시 이미
매핑된 가상 주소 공간을 기준으로 추가 메모리를 제한하며, 큰 임시 할당의 차단을 검증했다.
전체 229개 테스트와 `team-ai guard`를 통과했고, 기본 Codex CLI 평가기의 실제 판정과
토큰 사용량 수집도 확인했다. HTTP 시작 전 자산 준비, 느린 응답 제한, 공개·봉인 상태 분리,
동일 후보 재제출 거절, 재개 시 예산·증거 보존과 새 입력 실행은 회귀 테스트에 포함했다.

### 2026-09-08 세 기능의 실제 구현·실행 결과

`codex/replica-completion-test`에서 `work/delphi-ai/research.json`의 세 기능을
사용했다. 사용자가 승인한 부족한 조사 보완은 구현 시작 전에 별도
[2차 조사 입력](../work/delphi-ai/implementation-check-2026-09-08/research.json)에
반영했다. 원본 조사와 구현 전에 동결한 평가 기준은 유지했다.

기능마다 Astra medium Operator와 Terra high Builder를 실제 생성해 총 세 쌍을
실행했다. 초기 실행에서는 첫 기능의 시작 오류로 두 쌍만 겹쳤고, 복구 후에는
`peak_active_pairs: 3`을 확인했다. 고정 두 쌍 제한을 제거했으며, 세 기능과 열 기능의
모든 쌍을 앞 기능의 종료 없이 활성화하는 회귀 테스트를 통과했다. 새 실행은 모든
쌍의 등록·연결을 마친 뒤 전체 실행 세션을 시작하고 Operator들을 활성화한다.

이 환경의 동시 활성 Agent 한도는 root와 조율 Agent를 포함해 7개였다. 따라서
세 쌍의 실행 세션은 겹쳤지만 모든 Agent가 계속 동시에 추론한 것은 아니다.
응답을 기다리는 Agent가 턴을 반환하고 같은 ID로 재개했다. 열 쌍의 실제 모델
동시 실행은 검증하지 않았으며, 더 큰 실행에는 실행 환경의 수용량 확인이 필요하다.

각 기능을 두 번씩 별도 실행 단계에서 최종 평가했다. 아래는 두 번째 평가로
보존된 구현의 결과이며, 통과 수는 제품 완성률이 아니다.

| 기능 | 통과 | 판정 | 새 입력으로 공개 구현 재실행 |
|---|---|---|---|
| [자료 기반 대화](../work/delphi-ai/implementation-check-2026-09-08/agent-run/final-results/runs/claim-001/attempt-002-b5371e5b6207/replica-result.json) | 4/6 | `partially_reproduced` | 새 자료 검색, 답변·근거 인용·요청한 문체 확인 |
| [상황별 자동 작업](../work/delphi-ai/implementation-check-2026-09-08/agent-run/final-results/runs/claim-002/attempt-002-3f0147ff7544/replica-result.json) | 5/7 | `partially_reproduced` | 출력 산출물이 실행 디렉터리 안의 실제 파일인지 검증하는 단계에서 실패 |
| [인터뷰·인사이트 저장](../work/delphi-ai/implementation-check-2026-09-08/agent-run/final-results/runs/claim-003/attempt-002-5ccfd196b74c/replica-result.json) | 5/6 | `partially_reproduced` | 새 답변에 따른 후속 주제·요약 생성, 실제 SQLite에서 저장 ID·원문·요약 재조회 확인 |

그 뒤의 세 번째 제출을 위한 개발은 유효한 직접 피드백과 종료 기록을 완성하지
못해 세 기능 모두 `EXECUTION_ABORTED`로 끝났다. 자동 작업은 원래 개발 예산도
소진했다. 세 번째 후보는 최종 평가·공개되지 않았으며, 이전 부분 결과와 실패
기록을 보존했다. 하네스의 종료 상태는 `EXECUTION_COMPLETED_WITH_FAILURES`다.

시작 전 제어 정보 누락, 구현 묶음 검증, 의존성 버전 확인, 평가기에 전달하는
실행·산출물 근거를 보완했다. 같은 쌍의 제한된 복구는 기존 예산·식별자·기록을
보존한다. 이 수정이 기존 평가를 소급해 통과로 바꾸지는 않는다. Judge는
`same_session`으로 기록하며 완전히 독립된 평가라고 표현하지 않는다. 새 입력
재실행 역시 사후 관찰이며 동결된 평가의 통과 수에 더하지 않는다.

최종 코드 검증은 전체 237개 테스트와 `team-ai guard`를 통과했다.
[하네스 기록](../work/delphi-ai/implementation-check-2026-09-08/agent-run/agent-harness.json),
[새 입력 실행 기록](../work/delphi-ai/implementation-check-2026-09-08/fresh-input-results/execution-check.json),
[코드 검증 기록](../work/delphi-ai/implementation-check-2026-09-08/harness-verification.json)에
근거를 보존했다. 결과 보고서 개편과 투자 판단 보고서 작성은 계속 제외한다.

다음 구현 작업은 남은 고객 품질 조건, 자동 작업의 출력 파일 처리, 직접 피드백과
종료 절차의 안정성을 다룬다. 기존 평가 기준이나 예산을 낮추거나 초기화해 같은
실험을 성공으로 바꾸지 않는다. 조사 부족이 확인된 항목만 2차 보완 대상으로
돌리고, 보완 계약으로 시작하는 실행은 기존 실험과 구분한다.

  시나리오를 고른다. 새 계약을 추가할 때도 2차의 판단을 보존하고 Sol의 독자적인
  재조사로 대체하지 않는다.
- [인계와 최종화](../src/replica_mvp/agent_harness.py)의 `_builder_context`와
  `finalize_agent_candidate`는 구조·해시 검증 후 `IMPLEMENTATION_READY`에서 반환한다.
  CLI는 이어서 [번들 평가기](../src/replica_mvp/bundle_evaluation.py)의 별도 실행 단계를
  자동 호출한다. 개발 성공을 최종 평가 성공과 혼동하지 않는다.
- [실행 판정](../src/replica_mvp/agent_execution.py)과
  [피드백 계약](../src/replica_mvp/agent_protocol.py)에 고객 품질 기준, 투입 자원,
  종료 사유를 반영한다. 생성형 응답의 문장 동일성을 공통 성공 조건으로 강제하는
  부분을 점검하되, 반드시 결정적이어야 하는 조건은 유지한다.
- [완료 판정](../src/replica_mvp/completion.py),
  [기존 평가기](../src/replica_mvp/evaluation.py),
  [보고서](../src/replica_mvp/reporting.py),
  [공개 결과 생성](../src/replica_mvp/codex_operator.py)을 연결한다. 현재 제한
  Component용 검사를 다중 파일·모델·실제 자산 실행의 근거 없이 그대로 적용하지
  않는다. [원본 비교](../src/replica_mvp/experience.py)는 기존 근거 수준과 관찰
  기록을 확장해 사용한다.
- [리서치 지침](../skills/replica-research/SKILL.md),
  [Sol 지침](../.agents/skills/replica-operator-agent/SKILL.md),
  [Terra 지침](../.agents/skills/replica-builder-agent/SKILL.md), 대응하는
  `.claude/skills`와 실행 관련 문서는 실제 변경한 동작에 맞춰 정합성을 확인한다.
  문구만 바꾸고 코드의 고정 선택·검증 제약을 남겨두지 않는다.

기존 [실행 설명](./replica-execution-after-pass2.md)과
[현재 상태 문서](./replica-workflow-current-status.md)는 기존 구현을 이해하는
자료로 사용한다. 이 문서의 목표 기준과 다른 설명은 구현 변경에 맞춰 갱신해야 한다.
현재 JSON 전용 경로의 제약이나 테스트 실패를 Sol/Terra 다중 파일 경로 전체의
제약·실패로 일반화하지 않는다.
