## 0. 이 문서 사용법

1. 단계는 번호 순서대로 진행한다. 앞 단계의 **완료 기준**을 충족한 뒤 다음 단계로 넘어간다.
   단계 5(출처 재확인)만 다른 단계와 독립적이므로 언제든 병행할 수 있다.
2. 각 단계는 **목표 → 할 일 → 바꿀 곳 → 완료 기준 → 하지 않을 것** 순서로 적었다.
3. 단계에 필요한 결정은 7절 결정 목록에 모았다. 권장안이 있지만, 해당 단계를 시작하기 전에
   확정한다.
4. `src/`·`tests/`를 바꾸는 단계는 저장소 규칙을 따른다.
   - 시작 전: `context/project-direction.md`와 해당 단계의 실행 스킬 확인
   - 끝나기 전: 관련 테스트와 `PYTHONPATH=src python -m unittest discover -s tests` 통과, `git diff --check` 및 Git 변경 파일 확인
5. 단계가 끝나면 이 문서의 진행 기록(8절)에 날짜, 커밋, 남은 문제를 한 줄로 적는다.

## 1. 목표와 위치

### 1.1 Replica가 답하는 질문

Replica는 기술평가 보조 제품의 핵심 실험 기능이다. 인수 실사는 기술평가에 포함되는 용도이며,
방법은 Bain식 인수 실사의 기능 재현을 따른다. 대상 기업의 핵심 AI 기능 시제품을 만들고
사람이 직접 써 보며 두 가지를 판단한다.

- 기술 구현 난도와 경쟁사·신규 진입자의 대체 가능성
- 경쟁력의 원천이 코드인지, 데이터·고객 업무 결합인지

따라서 우선순위는 다음과 같다.

1. 사람이 원본과 같은 방식으로 복제품을 써 볼 수 있다.
2. 복제 정도를 원본 근거로 미리 정한 기준으로 잰다.
3. 복제에 든 비용과 사람 개입을 난도 데이터로 남긴다.
4. 일반 모델만으로도 되는 부분과 복제품이 더한 부분을 구분한다.

사람과 AI가 함께 만드는 것도 정상 경로다. 사람 개입은 오염이 아니라 난도 데이터다.

### 1.2 Replica는 "판단 계층"이다

Replica의 차별점은 앞단과 뒷단에 있다.

- 앞단: 고객 대상 AI 주장 선별, 근거 연결, 재현 계약
- 뒷단: 구현 전에 고정한 기준으로 평가, 기업 단위 판단

가운데 구현 단계는 교체 가능하게 둔다. 단일 구현자, 사람+AI 대화, Ralph식 루프 중 무엇으로
만들어도 같은 계약과 같은 평가를 거치면 된다. 구현 단계를 정교한 다중 에이전트 프로토콜로
키우는 데는 더 투자하지 않는다. 어떤 구조를 기본값으로 할지는 단계 6의 비교 결과로 정한다.

## 3. 외부 비교와 참고 연구

### 3.1 Ralph-to-Ralph와 비교

Ralph-to-Ralph는 URL을 받아 SaaS 제품 전체를 복제·배포하는 자율 파이프라인이다.
Inspect → Architecture → Build → QA 네 단계를 watchdog 스크립트가 돌린다.

| 축 | Ralph-to-Ralph | Replica (이 로드맵 적용 후) |
|---|---|---|
| 입력 | 제품 URL, 로그인된 원제품 계정과 API 키 | 기업의 고객 대상 AI 주장과 공개 근거 |
| 단위 | 기능 50개 이상의 작은 PRD 항목 | 고객 업무 흐름 하나 = claim 하나 |
| 출력 | 배포된 제품 전체 | claim별 재현 결과와 복제품, 기업 단위 판단 |
| 정답 기준 | 원제품. QA가 헷갈릴 때만 원제품을 열어 본다 | 2차가 구현 전에 공개 근거로 고정한 확인 기준 |
| 테스트 작성자 | 구현자. PRD에 테스트 명세를 넣지 않는다 | 2차 (구현 전) |
| 검증 독립성 | QA가 버그를 직접 고치고 `qa_pass`도 직접 정한다 | 판정을 구현과 분리 |
| 비용·시간 | 단계별 토큰 비용, 예산 상한, 전체 시간 상한, 정체 감지 | 단계 3에서 도입 |
| 역할 구조 | 단계마다 에이전트 1개, 파일로 상태 전달, 기본 Codex `low` | 단계 6에서 결정 |
| 설명력 | 기능별 pass/fail | `step_coverage`, 고객이 잃는 것, 근거 수준, 기준선 대비 차이 |

Ralph의 공개 성과(Resend, 약 4시간, 기능 52개, 사람 개입 0, 비용 $30~60)는 제작자 자기보고다.
Resend는 AI 품질이 핵심인 제품도 아니다. Ralph는 "만들어진다"는 것을 보여 주지만
"경쟁력이 어디서 오는가"에는 답하지 않는다.

**가져올 것**

| Ralph 장치 | 파일 | Replica 적용 단계 |
|---|---|---|
| 단계별 토큰 비용 기록, 예산 상한, 시간 상한, 정체 감지 | `ralph/ralph-watchdog.sh` | 단계 3 |
| 에이전트의 통과 표시를 믿지 않고 watchdog이 직접 `check/test/build`를 다시 돌리는 관문 | `ralph-watchdog.sh`의 `verify_workspace_contract` | 단계 3 |
| 구현자가 확인하지 못한 것을 적는 인계 기록 | `ralph/build-prompt.md`의 `qa-hints.json` | 단계 3 |
| 덮어쓰지 않는 시도 이력, 실패한 수정의 반복 금지 | `ralph/qa/footer.md`, `qa-ralph.sh` | 단계 3 |
| 결정적 문서 스크래퍼, 페이지별 출처 주석, 수집 범위 관문 | `scripts/scrape-docs.py`, `inspect-spec.md` | 단계 5 |
| 원제품을 실제로 써 보며 관찰, 원제품을 정답 기준으로 사용 | `ralph/inspect-spec.md`, `ralph/qa/base.md` | 단계 7 (선택) |

**가져오지 않을 것**

- 사람 개입 0을 목표로 두는 것. Replica는 사람이 써 보고 판단하는 것이 목적이다.
- QA가 고치고 합격도 정하는 구조. 판정은 구현과 분리한다(봉인은 필요 없다).
- 제품 전체 복제와 배포. 인증·설정 화면 같은 실사와 무관한 부분에 예산이 쓰인다.
- Ralph와 성능 비교 실험. 입력 단위(로그인된 제품 전체 vs claim)가 달라 비교가 성립하지 않는다.

## 4. 원칙

1. 사람이 써 볼 수 있는가를 1순위 기준으로 삼는다.
2. 확인 기준은 원본 근거로 구현 전에 정하고, 구현을 본 뒤 바꾸지 않는다. 봉인은 하지 않는다.
3. 판정은 구현과 분리한다. 형식은 코드로, 내용은 별도 세션의 AI 판정자가 보고, 사람이 일부를 검토한다.
4. 평가하지 못한 case는 `NOT_EVALUATED`로 남긴다. 실패로 바꾸지도, 분모에서 빼서 성공률을 부풀리지도 않는다.
5. 체험 가능과 평가 완료를 구분한다. 자료가 부족해도 제작은 진행하되 판단 보류를 결과에 남긴다.
6. 비용·시간·사람 개입은 그 조건에서 성공한 경로의 비용이다. 기업의 본질적 난도나 최소 비용으로 해석하지 않는다.
7. 실패나 실행 차단은 모방 불가능의 증거가 아니다.

### 단계 1. 2차 계약 개편

**목표**: 2차가 사용 방식을 계약에 보존하고, 사람이 바로 써 볼 수 있는 체험과 구현 전 확인 기준을 함께 만든다.

**할 일**

1. Skill 지침 수정 (`skills/replica-research/agents/replica-second-pass.md` 5~7절)

     - `origin: company`이면 `sources`에 URL과 발췌가 있는가
     - build claim에 `experience`, `setup`, `user_input`, 샘플 입력이 있는가
     - 확인 기준 테스트 3종이 있고 각 기대 결과에 정답 출처가 있는가
   - 평가 데이터(`novel`, `metamorphic` 등)가 부족하면 멈추지 않고 부족한 점을 기록한다.

`src/replica_mvp/second_pass.py`, `tests/test_second_pass.py`

### 단계 2. 체험·평가 실행기와 일반 모델 기준선

**목표**: 세 형태의 복제품을 사람과 테스트가 같은 방식으로 실행하고, case별 결과와 기준선 대비 차이를 공개한다.

**할 일**

1. 체험 실행 (`src/replica_mvp/experience.py`)
   - `single`: 입력 하나 → 결과 하나. 매번 새로 실행한다.
   - `conversation`: 한 세션에서 턴을 이어 간다. 상태(대화, 진행률, 대기 중 승인 등)를 세션 폴더에 파일로 남긴다.
     `demo-session/`의 `play.py` 방식(`--fresh`, 이어하기, `--raw`)을 기준으로 삼는다.
   - `batch`: 파일 여러 개 → 표나 보고서 하나.
   - 파일 입력은 경로로 받는다. JSON 안에 텍스트로 넣지 않는다.
   - 화면은 CLI 세션으로 시작한다(D2).
2. 확인 기준 실행기 (`src/replica_mvp/bundle_evaluation.py`)
   - 형태별 실행기 3개가 사용자 입출력 수준의 테스트를 복제품에 넣는다.
   - `conversation`은 case마다 설정·자료·세션을 같은 초기 상태로 복구하고, case 안에서는 상태를 유지한다.
     마지막 응답만 보지 않고 종료 상태(수집된 정보, 진행률, 승인·실행 여부)를 확인한다.
   - 액션이 핵심인 claim은 "실행했습니다"라는 문장이 아니라 관측 가능한 결과(예: `outbox/` 기록)로 판정한다.
     이런 claim에서는 부수효과 검사를 선택으로 내리지 않는다.
3. 판정
   - 형식(필수 항목, 파일 생성, 표 구조)은 코드로 판정한다.
   - 내용은 AI 판정자가 판정한다. 판정자 모델, 세션 독립 여부를 기록한다(D6).
   - 판정자가 없거나 실패하면 해당 case는 `NOT_EVALUATED`다.
   - 결과는 `reproduced` / `partially_reproduced` / `not_reproduced`. 제외한 단계가 있으면 최대 `partially_reproduced`.
     `NOT_EVALUATED` case가 핵심 조건이면 판단 보류를 함께 표시한다.
4. case별 결과 공개
   - 봉인용 필터(`bundle_evaluation.py:949` 부근)를 기본 경로에서 제거한다.
   - case마다 입력, 복제품 출력, 통과 여부, 판정 이유, 정답 출처를 공개한다.
   - 봉인 평가는 D3에 따라 선택 옵션으로 남기거나 제거한다.
5. 일반 모델 기준선 (SkillClone 적용)
   - 같은 확인 기준 테스트를 "공개 설명과 `setup`만 받은 일반 모델"에도 돌린다(D8).
   - 결과에 기준선 통과율과 복제품 통과율을 나란히 기록한다.
   - 해석 규칙: 차이가 작으면 "코드 우위 작음", 차이가 크면 차이를 만든 요소(데이터·절차·도구)를 적는다.
     기준값은 정하지 않고 단계 4 결과를 보고 정한다.

**바꿀 곳**: `src/replica_mvp/experience.py`, `src/replica_mvp/bundle_evaluation.py`, `src/replica_mvp/bundle_runtime.py`(필요 시),
`src/replica_mvp/cli.py`(`experience` 명령 인자), `tests/test_experience.py`, `tests/test_bundle_evaluation.py`

**완료 기준**
- 세 형태 각각 작은 예제 복제품으로 다음이 확인된다.
  - 사람이 CLI로 실행해 샘플 입력으로 결과를 볼 수 있다.
  - 확인 기준 실행기가 같은 복제품을 돌려 case별 결과를 낸다.
- `conversation` 예제에서 case 사이 상태가 섞이지 않고, case 안에서는 이어진다는 테스트가 있다.
- 판정자 없음 → `NOT_EVALUATED`, 핵심 조건 미평가 → 판단 보류가 테스트로 확인된다.
- 공개 결과에 case별 입력·출력·이유가 있다.
- 기준선 결과가 복제품 결과와 같은 형식으로 저장된다.

**하지 않을 것**: 웹 화면, `event` 전용 실행기(D1에서 따로 두기로 정한 경우에만 추가), 변형 case 자동 생성

### 단계 3. 측정 장치 (Ralph watchdog에서 가져옴)

**목표**: 복제에 든 비용·시간·재시도·사람 개입을 claim마다 기록하고, 예산을 넘으면 멈춘다.

**할 일**

1. 기록 채우기 (`src/replica_mvp/resources.py`)
   - 이미 있는 `measurements`, `human_interventions`, 예산(`time_limit_seconds`, `cost_limit`) 구조를 그대로 쓴다.
     새 스키마를 만들지 않는다.
   - 단계별(조사 / 구현 / 평가 / 기준선) 벽시계 시간, 재시도 횟수를 기록한다.
   - 토큰은 CLI가 보고하는 경우에만 기록하고 출처를 남긴다. 보고하지 않으면 "측정 안 됨"으로 둔다(0으로 쓰지 않는다).
   - 구독 과금은 실행 비용으로 환산하지 않는다(현재 규칙 유지).
   - 사람 개입은 누가, 언제, 무엇을 했는지(지시, 코드 수정, 입력 준비, 판정)를 남긴다.
     구현을 도운 기록과 최종 평가를 한 기록을 구분한다.
2. 예산 상한과 정체 감지
   - 시간 상한을 넘으면 구현을 멈추고 `BLOCKED`와 이유를 남긴다.
   - 같은 실패가 연속 N회(권장 3회) 반복되고 결과가 바뀌지 않으면 정체로 보고 멈춘다.
3. 결정적 실행 관문
   - 평가 전에 코드가 직접 확인한다: 깨끗한 폴더에서 복제품이 설치·실행되고 체험 샘플 입력으로 결과를 내는가.
   - 실패하면 평가하지 않고 구현 단계로 돌려보낸다. 구현자의 "완료" 표시만 믿지 않는다.
4. 시도 이력과 인계 기록
   - 수정 시도는 덮어쓰지 않고 이어 붙인다(시도 번호, 무엇을 바꿨는가, 결과).
   - 다음 시도 전에 이력을 읽고 같은 수정을 반복하지 않는다.
   - 구현자는 제출 시 "확인하지 못한 것"을 적는다. 판정자와 사람 체험에서 이 목록을 먼저 본다.
5. 실패 원인 분류
   - 실패와 차단을 조사 부족 / 계약 전달 실패 / 구현 결함 / 평가 불가 / 접근·환경·예산 제약 중 하나로 표시한다.

**바꿀 곳**: `src/replica_mvp/resources.py`, `src/replica_mvp/single_agent.py`, `src/replica_mvp/bundle_evaluation.py`,
관련 Skill 문서(구현자 인계 기록 항목), `tests/`의 해당 테스트

**완료 기준**
- 예제 실행 한 번으로 claim 결과에 단계별 시간, 재시도, 사람 개입, 토큰(또는 "측정 안 됨")이 남는다.
- 시간 상한 초과와 정체가 각각 테스트로 멈춘다.
- 실행 관문 실패 fixture가 평가로 넘어가지 않는다.

**하지 않을 것**: 달러 비용 추정(가격표 곱하기)을 실제 비용처럼 보고하는 것. Ralph는 고정 단가로 추정하지만 Replica는 출처 있는 값만 쓴다.

### 단계 5. 출처 스냅샷과 재확인 (병행 가능)

**목표**: 1·2차 조사의 출처가 실제로 주장을 뒷받침하는지 층별로 확인한다.

**할 일**

1. 1·2차가 끝나면 저장된 모든 출처 URL을 다시 가져와 날짜와 함께 저장한다(조사 시점 스냅샷).
   Ralph처럼 결정적 스크래퍼를 쓰고, 파일마다 원래 URL을 남긴다.
2. 링크 작동: 404, 403, 시간 초과를 기록한다.
3. 발췌 존재: 저장된 발췌가 가져온 본문에 실제로 있는지 문자열로 확인한다. LLM을 쓰지 않는다.
4. 사실 일치: AI 근거 인용이 주장을 뒷받침하는지 LLM이 판정하고, 판정 20~30건을 사람이 검토한다.
5. 2차 지침에 "출처는 적게, 확실히"를 넣는다.
6. 유료 페이지·가져오기 실패는 실패가 아니라 "확인 불가"로 남긴다.

**바꿀 곳**: 새 모듈 또는 `project.py`·`second_pass.py`의 finalize 단계(구현 시 결정), `skills/replica-research/` 지침, 해당 테스트

**완료 기준**
- 발췌가 없는 가짜 페이지와 가져오기 실패 fixture가 둘 다 통과하지 못한다.
- Delphi research에 적용해 층별 결과(링크 / 발췌 / 사실 일치)가 나온다.

**하지 않을 것**: 실패한 출처를 자동으로 다른 출처로 바꾸는 것

---

### 단계 6. 구현 구조 비교와 기본 경로 결정

**목표**: 단일 구현자와 Operator/Builder 중 기본 경로를 근거로 정하고 라우팅 문서를 정리한다.

**할 일**

1. 같은 claim(Delphi 3개), 같은 모델, 같은 예산, 같은 확인 기준으로 두 경로를 각각 실행한다.
2. 비교 항목: 확인 기준 통과율, 기준선 대비 차이, 시간, 토큰, 재시도, 사람 개입, 실패 원인 분류, 중단 여부
3. 결과를 `docs/implementation-structure-comparison-<날짜>.md`에 적는다. n=3이라 방향 판단용이며 통계적 결론이 아니라고 명시한다.
4. 결정(D7)에 따라 라우팅을 바꾼다.
   - 단일 구현자가 같거나 나으면: 기본 경로를 단일 구현자로 바꾼다. Operator/Builder는 선택 경로로 남기거나 제거한다.
   - Operator/Builder가 분명히 나으면: 현재 기본 경로를 유지하고, 어떤 claim에서 나았는지 조건을 적는다.
5. 사람+AI 제작 경로를 공식 경로로 문서화한다(D4). 같은 계약·평가·측정을 거친다.

**바꿀 곳**: 비교 보고서, (결정 시) `CLAUDE.md`, `AGENTS.md`, `.claude/skills/`·`.agents/skills/`의 라우팅 관련 Skill, `README.md`

**완료 기준**
- 비교 보고서가 있고, D7이 확정되어 진행 기록에 남아 있다.
- 라우팅 문서들이 서로 같은 기본 경로를 말한다.

**하지 않을 것**: Operator/Builder 프로토콜 확장(C8 등). 비교 전에는 투자하지 않는다.

---

### 단계 7. 원제품 관찰 (선택)

**목표**: 원제품에 접근할 수 있는 claim에서 같은 입력으로 원본과 복제품을 비교한다.

**할 일**

1. 체험 계정·공개 데모·API가 있는 claim만 대상으로 고른다. 약관을 확인한다.
2. 개발용 관찰 입력과 최종 확인 입력을 나눈다. 최종 확인 입력은 구현 중에 원본에 넣지 않는다.
3. 같은 입력·설정으로 원본과 복제품 출력을 기록하고 차이를 case별로 남긴다.
4. 생성 문장은 문자열 일치가 아니라 과업 기준으로 비교한다.
5. 결과에 근거 수준 `direct`를 쓸 수 있는 claim이 늘었는지 기록한다.

**완료 기준**: 대상 claim이 1개 이상 있으면 원본 대비 차이 기록이 결과에 붙는다. 없으면 "대상 없음"을 기록하고 넘어간다.

**하지 않을 것**: 원제품에 계속 의존하는 복제품을 독립 재현으로 세는 것(Integuru식 호출 대행)

---

### 단계 8. 두 번째 회사 적용

**목표**: 계약과 실행기가 Delphi에만 맞춰지지 않았는지 확인한다.

**할 일**

1. `work/harvey/research.json`(9개 claim)을 새 계약으로 재분류한다. 파일 입력(docx, pdf)과 `batch` 형태가 들어 있어 Delphi와 보완적이다.
2. 단계 4와 같은 절차(구현, 평가, 기준선, 측정, 사람 체험, 보고서)를 적용한다.
3. 단계 4에서 정하지 못한 기준선 해석 기준값을 두 회사 결과로 정한다.
4. 필요하면 CheckList·EvalPlus 방식의 변형 case를 추가한다(원본 조건에 맞는지 먼저 확인).

**완료 기준**: Harvey 보고서가 단계 4와 같은 항목을 갖추고, 두 회사에서 공통으로 나온 계약·실행기 문제를 정리했다.

## 6. 하지 않을 것 (전체)

- 봉인 평가를 기본 경로로 되돌리는 것
- 구현 단계에 역할·프로토콜을 추가하는 것(단계 6 결론 전)
- 제품 전체 복제·배포
- 사람 개입을 오염으로 취급해 결과에서 빼는 것
- 확인 기준을 구현 결과를 본 뒤 바꾸는 것
- 기업 공개 문구나 AI 판정자의 확신만으로 기대 결과를 만드는 것
- 제한된 공개 범위의 재현을 원제품 전체와 동등하다고 표현하는 것
