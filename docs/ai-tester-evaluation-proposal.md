# AI 테스터 평가 방식 제안

> 2026-10-05 후속 사용자 정정: 기업 입력 이후 사례 작성·구현·AI 시험·판정·보고·체험 제공까지 자동 수행한다.
> AI 테스터는 사람이 직접 사용할 복제품의 같은 사용자 작업 경로를 시험한다. 사람 검토·채점은 선택이며 실행 완료를 막지 않는다.
> 아래의 사람 검토를 필수로 둔 문구는 과거 제안이다. 현재 기준은 [프로젝트 방향 5절](../context/project-direction.md)을 따른다.

> 작성일: 2026-10-02
> 상태: 논의 중인 제안. 확정되지 않았고 로드맵·초안·코드에 반영하지 않았다.
> 관련 문서: `docs/replica-roadmap.md` (단계 0·1·2, D1·D2·D6), `docs/pass2-interaction-redesign.md` (3.1·3.4절)

## 1. 요약

Replica를 "JSON 프로그램을 코드로 채점"하는 구조에서
"원본처럼 쓰는 복제품을 AI 테스터가 대본대로 써 보고, 코드는 관측 가능한 결과만 확인"하는
구조로 바꾸자는 제안이다. 확정되면 로드맵 D1(상호작용 형태 3종)과 단계 2의 형태별 실행기 3개를
대체한다.

## 2. 배경: 복제품이 왜 "JSON 하나 → JSON 하나" 모양인가

명시된 곳:

- `docs/replica-bundle-execution.md`: 복제품은 `stdio_json`(stdin JSON → stdout JSON) 또는
  `http_json`(로컬 서버에 POST)이어야 한다.
- `skills/replica-research/agents/replica-second-pass.md`: 계약 템플릿의 기본값이
  `"transport": "stdio_json"`이고, 테스트는 입력 하나짜리 normal / boundary /
  insufficient-information 3개다.
- `src/replica_mvp/experience.py`: 체험 형태가 `question_answer` 하나로 고정돼 있다.
  첫 파이프라인 커밋(`dccdf79`, 2026-08-16 "Build JSON-only Replica artifact pipeline")부터 그대로다.

원인 판단(추론): 평가를 코드로 자동화하려고 출력 JSON 필드를 `equals`/`contains`로 검사하는
방식을 먼저 설계했고, 복제품 형태가 그 평가 형식에 맞춰졌다. `team-ai context`로 찾았을 때
이 틀을 정한 회의나 결정 기록은 없었다. 의도적인 설계라기보다 초기 편의가 굳은 것으로 본다.

정정해 둘 점: 평가는 대화를 부분적으로 지원한다. case에 같은 `session` 이름을 붙이면 한 세션에서
순서대로 실행되고 상태가 유지된다. 다만 각 턴은 여전히 JSON 하나 → JSON 하나이고, 2차 지침이
테스트를 입력 하나짜리로만 만들게 해서 거의 쓰이지 않는다.

## 3. Ralph-to-Ralph는 어떻게 하나

`namuh-eng/ralph-to-ralph`의 `b756d3d` 커밋을 받아 확인했다.

| 항목 | Ralph | Replica 현재 |
|---|---|---|
| 기능 명세 | 자연어. `behavior`(사용자가 조작하면 무슨 일이 일어나는지, 직접 써 보고 관찰한 것), `ui_details`, 원제품 스크린샷 (`ralph/inspect-spec.md`) | `input`/`output` 필드, JSON 런타임 |
| 복제품 형태 | 원제품과 같은 웹앱(화면 + API) | JSON을 주고받는 프로그램 |
| 테스트 | 명세에 넣지 않는다고 명시("DO NOT include test specs in prd.json"). 구현자가 단위·E2E 테스트를 직접 쓴다 | 2차가 구현 전에 고정 |
| 검증 | QA 에이전트가 실제 브라우저로 클릭하며 써 본다(`ever snapshot`/`click`). API는 `curl`로 확인한다. 헷갈리면 원제품을 열어 비교한다 (`ralph/qa/base.md`) | 코드가 출력 JSON 필드를 검사하고, AI 판정자가 내용을 본다 |
| 상호작용 분류 | 없음. 원제품이 대화형이면 복제품도 대화형이다 | `single`/`conversation`/`batch`를 정하려는 중(D1) |

Ralph에 틀 문제가 없는 이유: 사람처럼 써 보는 에이전트가 검증하므로 코드가 출력 형식을 검사할
필요가 없다.

Ralph가 대가로 치르는 것 (Replica 로드맵 원칙 2·3이 피하려는 것):

- 테스트가 구현 전에 고정되지 않는다. 구현자가 자기 테스트를 쓴다.
- QA가 버그를 직접 고치고 합격(`qa_pass`)도 스스로 정한다. 판정이 구현과 분리돼 있지 않다.
- 정답 기준이 원제품이라 로그인된 원제품 계정이 필요하다. Replica는 대부분 공개 근거밖에 없다.

## 4. 제안

Replica 원칙(테스트는 구현 전 고정, 판정은 구현과 분리)은 지키고, 형식 제약만 없앤다.

1. 복제품의 인터페이스는 자유롭게 둔다. 원본 사용 방식을 따르는 CLI나 간단한 웹이다.
   실행 방법을 manifest에 적는다.
2. 2차는 테스트를 구현 전에 자연어 대본으로 고정한다.
   "사용자가 이렇게 넣으면 → 이걸 봐야 한다" 수준이다.
3. 별도 세션의 AI 테스터가 대본대로 복제품을 직접 써 보고 기록을 남긴다.
4. 코드는 관측 가능한 결과만 검사한다. 파일 생성, `outbox/` 기록, 변경 금지 저장소, 기록의 진위 등이다.

### 4.1 전체 흐름 비교

| 단계 | 지금 | 반영 후 |
|---|---|---|
| 2차 계약 | `input`/`output` 필드, `stdio_json` 런타임, 입력 하나짜리 테스트 3개 | 사용 방식 설명, 준비물(`setup`), 자연어 테스트 대본, 기대 결과마다 정답 출처 |
| 복제품 | JSON 입출력 프로그램 | 원본 사용 방식을 따르는 CLI나 간단한 웹 |
| 사람 체험 | `experience` 명령의 질문-답변 하나 | 복제품을 그대로 실행해서 씀 |
| 평가 | 코드가 JSON 필드를 검사하고, AI 판정자가 출력만 읽고 판정 | AI 테스터가 대본대로 실행·기록하고, 코드가 기록과 부수효과를 검증하고, 판정자가 기록을 보고 판정 |

## 5. 로드맵 단계별 변경

### 단계 1 (2차 계약)

- `interaction.type` 허용값 검사가 필요 없다. 사용 방식은 "사용자가 무엇을 넣고 무엇을 보는지"를
  출처와 함께 자연어로 적는다.
- 테스트는 대본 형식으로 쓴다.
  - 준비: 설정과 파일
  - 단계: 사용자 행동 → 봐야 할 것
  - 종료 상태: 파일이나 `outbox/`에 남아야 할 것
- `conversation`은 턴이 여러 개인 대본일 뿐이라 따로 분류하지 않는다.
- 유지하는 것: 정답 출처, normal / boundary / insufficient-information 3종, `step_coverage` 범위 축소 기록.
- 코드 검증은 대본마다 단계와 정답 출처가 있는지, 파일 입력이 실제 파일인지 정도로 줄어든다.

### 단계 2 (실행기와 판정)

형태별 실행기 3개 대신 테스터 실행기 하나를 만든다. case마다 다음 순서로 실행한다.

1. 깨끗한 복사본에 복제품과 자산을 놓는다.
2. 별도 세션의 AI 테스터에게 대본과 실행 방법을 준다.
3. 테스터가 명령 실행, 입력, 화면 확인을 하고 입력·출력 기록을 vault에 남긴다.
4. 코드가 확인한다.
   - 모든 단계를 시도했는가
   - 판정 근거로 인용한 출력이 실제 기록에 있는가 (출처 발췌 검사와 같은 방식)
   - 파일, `outbox/`, 변경 금지 저장소가 기대대로인가 (기존 before/after 스냅샷 재사용)
   - 테스터가 구현 파일을 바꾸지 않았는가 (해시 비교)
5. 판정 분리를 위해 테스터는 기록만 하고, 판정은 기록을 읽는 별도 판정자가 하는 편이 낫다.
   비용은 늘어난다.

그 밖의 변화:

- 일반 모델 기준선(D8)이 쉬워진다. 같은 테스터가 같은 대본으로 "공개 설명만 받은 일반 모델"과
  대화하면 되므로, 복제품과 기준선을 같은 방식으로 측정한다.
- 사라지는 것: JSON 경로 assertion, JSON 필드 기반 metamorphic 비교, `experience.py`의 질문-답변 프로필.
- 기존 JSON 복제품도 버리지 않는다. JSON CLI도 인터페이스의 한 종류라서 테스터가 그대로 실행할 수 있다.

### 단계 3 (측정)

- 테스터 비용을 평가 단계 비용으로 기록한다.
- "깨끗한 폴더에서 실행되는가" 관문은 테스터가 샘플 입력 하나로 먼저 돌려 보는 smoke 실행으로 바꾼다.

### 단계 4·6·8

절차는 같다. 단계 4 Delphi 파일럿이 새 실행기의 첫 검증이 된다.

## 7. 새로 생기는 위험과 대응

| 위험 | 대응 |
|---|---|
| 테스터가 실행하지 않은 것을 했다고 보고 | 판정 근거를 기록에서 인용하게 하고, 인용이 실제 로그에 있는지 코드로 확인 |
| 테스터가 복제품을 돕거나 재시도해 통과시킴 | 실행 규칙을 고정하고, 재시도를 기록하며, 구현 파일 해시를 비교 |
| 판정이 너그럽거나 엄격하게 흔들림 | D6의 사람 검토 20~30건으로 오합격·오탈락 비율 측정 |
| 비용·시간 증가 | case 수 × 반복 횟수만큼 AI 세션이 든다. 반복 실행을 기본 2회에서 1회로 줄일지 결정 필요 |
| 테스터의 임의 명령 실행 | 현재 판정자는 `Read` 도구만 쓴다(`bundle_runtime.py`의 `native_model_judge`). 테스터는 셸 실행이 필요하므로 복사본 폴더와 기존 제한 실행 환경 안에서만 돌린다 |

## 8. 판단

- 장점: "사람이 원본처럼 써 볼 수 있다"는 1순위 목표와 직접 맞는다. 형태별 실행기가 필요 없어
  단계 2가 오히려 단순해질 수 있다. 기준선 측정도 자연스럽다.
- 약점: 결정적 채점이 줄어 AI 판정 의존이 커진다. "인용이 기록에 있는가"를 코드로 검사하는 장치와
  사람 검토가 필수가 된다.
- 불확실한 점: 테스터 실행기의 실제 구현량. `bundle_evaluation.py`에서 지울 코드와 새로 쓸 코드 중
  어느 쪽이 클지는 설계를 더 해 봐야 안다.
