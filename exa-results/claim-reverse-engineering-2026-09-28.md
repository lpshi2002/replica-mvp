# 기업 주장 기반 기능 재현: 유사 연구·도구와 Replica 강화 방향

조사 기준일: 2026-09-28  
조사 방식: Exa로 후보 발굴 및 원문 조회, 논문 원문·학회 논문집·원본 GitHub 저장소로 교차 확인. 아래의 적용 우선순위와 설계안은 조사자의 제안이며 구현하거나 실험한 결과가 아니다.

## 1. 결론

**유사한 로직은 이미 존재한다.** 공개 설명에서 기능을 추론하고 재구현하는 쪽은 SkillClone, 명세에서 독립 구현을 만들고 원본 출력으로 검증하는 쪽은 RepoZero, 문서에서 구현 요구사항을 보존하는 쪽은 ReproAgent·PaperCompiler, 재현 결과를 별도 평가하는 쪽은 PaperBench가 특히 가깝다. 도구 중에서는 Ralph-to-Ralph와 Greenfield가 직접 비교할 만하다. 각 근거와 차이는 아래 원문 링크에 연결했다.

다만 이번에 확인한 공개 자료에서는 **기업의 고객 대상 AI 주장을 발굴하고 → 기능별 공개 근거를 정규화하고 → 재현 계약을 만들고 → 독립 구현·평가를 수행하고 → 실행하지 못한 주장까지 포함하여 기업 단위 결과를 내는 구성 전체**가 동일한 상용 제품은 확인하지 못했다. 이는 이번 검색 범위에서의 관찰이지, 경쟁 제품이 없거나 학술적 신규성이 입증됐다는 뜻은 아니다.

따라서 차별화 가설은 단순한 코드 생성보다 **주장과 시험 조건 사이의 근거 추적, 평가의 신뢰성, 제한된 조건에서 재현됐다는 사실을 과장 없이 설명하는 능력**에 두는 편이 설득력 있다. 이 판단은 아래 선행 연구·도구와 현재 설계의 비교에서 도출한 것이다.

## 2. 현재 Replica와 비교할 기준

비교 기준은 읽기에 성공한 [Replica Research 지침](/Users/cho/replica-mvp/skills/replica-research/SKILL.md)의 설계다. 현재 제품 코드의 구현 상태나 실행 성능까지 점검한 것은 아니다.

| 단계 | 확인한 설계 |
|---|---|
| 주장 수집 | 해당 회사의 실제 고객 대상 기능인지, 입력과 출력이 있는 일인지, 그 일에 AI를 쓴다는 직접적인 출처가 있는지 확인한다. |
| 기능 단위 | 고객이 받는 하나의 전체 작업 흐름을 하나의 claim으로 유지한다. 중간 처리 단계가 있다는 이유만으로 별도 기능으로 늘리지 않는다. |
| 재현 조사 | 데이터·API, 공개 구현·논문, 평가 자산, 접근 조건, 구현 경로 등을 조사하여 제한된 재현 계약을 만든다. |
| 구현·평가 | Builder에 비공개 정답을 노출하지 않고 구현과 평가를 분리한다. 정상·경계·정보 부족 사례와 불변·사실 변경 관계를 다룬다. |
| 결과 해석 | 실행 차단과 실제 재현 실패를 구분하고, 모든 조사 claim을 결과에 남긴다. 공개 범위의 기능 재현을 원제품 전체 동등성으로 표현하지 않는다. |

이 설계에는 이미 비공개 평가, 역할 분리, 계약 고정, 입력 변형 시험이 포함돼 있다. 따라서 아래 제안은 그 장치를 새로 추가하자는 것이 아니라 **각 장치가 올바른 근거와 충분한 시험으로 작동하도록 강화하자는 것**이다.

## 3. 우리와 가까운 논문

### 3.1 SkillClone — 공개 설명에서 관측·재구현까지 가장 직접적으로 연결

**논문:** Behavioral Skill Reconstruction: Reconstructing Hidden Functionality from LLM Agent Skills. 2026년 arXiv 공개 연구.  
**원문:** [논문](https://arxiv.org/abs/2608.04192) · [본문 v2](https://arxiv.org/html/2608.04192v2)

공개된 skill 설명에서 입력·출력 인터페이스의 가설을 세우고, 정상적인 작업 요청에 대한 응답을 관찰하고, 실행 가능한 대체 구현을 생성한다. 이후 원본과 복제 구현이 다르게 응답하는 입력을 활용해 수정하고, 별도의 미관측 입력에서 평가한다. 비공개 skill 파일을 읽는 대신 관측 가능한 동작으로 기능을 복원한다는 점이 핵심이다.

**우리와의 공통점:** 공개 설명 → 기능 가설 → 실행 가능한 대체 구현 → 검증이라는 순서다. 특히 기업의 기술적 주장을 기능 단위로 바꾸려는 문제와 가깝다.

**다른 점·한계:** 원본 skill에 실제 입력을 보내고 출력을 얻을 수 있어야 한다. 연구 대상도 선별된 skill의 규칙·테이블·절차·알고리즘이다. 따라서 마케팅 페이지만 읽어 전체 SaaS를 동일하게 재현할 수 있다는 증거로 사용할 수 없다. 연구의 평가자가 가진 기준 구현과 내부 기능 지식도 공개 회사 조사자가 자동으로 얻을 수 있는 것은 아니다.

**가져올 부분:** 접근 가능한 데모·API에 대한 관측 루프, 두 구현의 차이가 드러나는 입력 선택, 그리고 기반 모델 자체의 능력과 추가 skill이 제공하는 능력을 분리하는 비교다. 후자는 우리 구현이 회사 고유의 기능을 재현한 것인지, 일반 모델이 이미 할 수 있는 작업을 수행한 것인지 해석할 때 유용하다.

### 3.2 RepoZero — 명세에서 재구현한 뒤 원본 동작으로 채점

**논문:** RepoZero: Can LLMs Generate a Code Repository from Scratch? 2026년 arXiv 공개 연구.  
**원문:** [논문](https://arxiv.org/abs/2605.07122) · [본문](https://arxiv.org/html/2605.07122v3) · [코드](https://github.com/JesseZZZZZ/RepoZero)

API 명세와 제한된 공개 예제를 제공하고, 에이전트가 저장소를 새로 구현하도록 한다. 원본 저장소가 출력 정답의 기준이 되며, 공개하지 않은 테스트에서 결과를 비교한다. 언어를 바꿔 구현하도록 하는 조건과 격리된 평가로 원본을 그대로 이용하는 지름길을 제한한다. ACE라는 코드·테스트 반복 구조에서는 테스트 에이전트가 원본 실행으로 정답을 확보하고 구현 에이전트가 오류를 수정한다.

**우리와의 공통점:** 계약에서 독립 구현을 만들고, 구현자가 보지 못한 사례로 평가한다는 점에서 Replica의 후반부와 매우 가깝다.

**다른 점·한계:** 이미 정해진 API 명세와 원본 기준 구현이 존재한다. 기업의 모호한 주장을 찾아서 명세를 정하는 전반부는 다루지 않는다. 또한 결정적인 라이브러리 출력 비교 방식을 자유로운 자연어 생성 결과에 그대로 적용할 수 없다.

**가져올 부분:** 테스트 입력의 유효성, 기준 출력의 안정성, 원본에 다시 위임하지 않는 독립성, 실제 출력 차이를 기반으로 한 수정이다. 단순히 실행에 성공했다는 사실과 요구 동작을 재현했다는 사실을 분리하는 평가 설계가 중요하다.

### 3.3 PaperBench — 재현 평가의 신뢰성을 설계할 때 핵심

**논문:** PaperBench: Evaluating AI’s Ability to Replicate AI Research. ICML 2025.  
**원문:** [학회 논문집](https://proceedings.mlr.press/v267/starace25a.html) · [본문](https://arxiv.org/html/2504.01848v2) · [공개 코드 저장소](https://github.com/openai/preparedness)

논문을 보고 코드를 처음부터 작성하고 결과를 재현하는 과제를 평가한다. 원 논문의 저자와 함께 계층적인 평가 기준을 만들며, 구현 에이전트에게 그 채점 기준을 공개하지 않는다. 제출된 저장소를 새로운 환경에서 다시 실행한 뒤 코드 구현, 실행, 결과 일치 여부를 구분해 평가한다. 자동 평가자 자체를 사람의 판단과 비교하는 JudgeEval도 제시한다.

**우리와의 공통점:** 문서 기반 재구현, 비공개 기준, 구현과 평가의 분리다.

**다른 점·한계:** 논문은 마케팅 문구보다 명세가 풍부하며, 평가 기준 작성에 원저자의 도움이 있다. 이 조건을 기업 공개자료 조사에서도 확보했다고 가정해서는 안 된다.

**가져올 부분:** claim의 각 기준과 검증 증거 연결, 새 환경에서 제출물 재실행, 평가자의 잘못된 합격 판정 측정이다. 현재 Replica에도 분리가 설계되어 있으므로 추가 역할 수보다 평가 품질을 측정하는 데 활용할 가치가 크다.

**주의:** PaperBench의 간소화 버전인 **Code-Dev는 코드 개발 평가에 집중하고 결과 재현을 위한 실행 단계를 생략한다.** 다른 논문이 이 벤치마크에서 높은 점수를 얻었다고 해서 실제 실험 결과까지 그 비율로 재현했다고 해석하면 안 된다.

### 3.4 ReproAgent — 조사한 요구사항이 구현 과정에서 사라지지 않도록 유지

**논문:** ReproAgent: Contract-Guided Paper-to-Code Reproduction. 2026년 공개; arXiv 메타데이터에 Findings of EMNLP 2026 채택 표기.  
**원문:** [논문](https://arxiv.org/abs/2608.24291) · [본문](https://arxiv.org/html/2608.24291) · [코드](https://github.com/kernel-14/ReproAgent)

Prepare → Plan → Generate → Repair 전 과정을 동일한 구현 계약으로 연결한다. 논문이 명시한 요구사항과 관련 저장소에서 얻은 구현 근거를 서로 다른 채널로 보존하고, 작업 묶음과 파일별 책임에 연결한다. 수정 단계에서도 처음 고정한 계약을 기준으로 누락과 불일치를 찾는다.

**우리와의 공통점:** 조사 결과를 계약으로 만들고, 여러 구현 단계를 지나도 같은 요구사항을 유지하려는 구조다.

**다른 점·한계:** 주된 비교 실험은 PaperBench Code-Dev이므로 코드 충실도 개선의 근거로 읽어야 한다. 원제품의 실제 출력 동등성을 입증한 연구는 아니다.

**가져올 부분:** 원문 근거 → 요구사항 → 담당 구현 → 검증 기준의 연결을 끝까지 유지하는 방식이다. Replica의 계약이나 직접 에이전트 프로토콜을 없애고 새 프레임워크로 교체하기보다, 기존 산출물 사이의 연결이 빠졌는지 검사하는 데 적용하는 것이 단순하다.

### 3.5 Paper2Code / PaperCoder — 문서에서 저장소를 만드는 구현 구조

**논문:** Paper2Code: Automating Code Generation from Scientific Papers in Machine Learning. ICLR 2026. PaperCoder는 논문이 제안한 시스템명이다.  
**원문:** [학회 논문](https://proceedings.iclr.cc/paper_files/paper/2026/file/41b6674c28a9b93ec8d22a53ca25bc3b-Paper-Conference.pdf) · [코드](https://github.com/going-doer/Paper2Code)

논문을 읽고 계획, 세부 분석, 의존성에 따른 코드 생성을 수행하는 다중 에이전트 시스템이다. 자동 평가와 논문 저자의 평가 등을 통해 구현 충실도를 살핀다. 문서에서 전체 저장소로 넘어가는 구현 경로의 참고자료다.

우리의 주장 발굴·진위 근거 확인과는 거리가 있고, 현재도 구현 에이전트가 있으므로 우선순위는 계약 보존과 평가를 다루는 앞선 연구들보다 낮다. 논문에서의 코드 충실도, 실행 가능성, 실제 결과 일치 평가는 구분해서 읽어야 한다.

### 3.6 IReEn — 입력·출력만으로 동작을 복원하는 기초 연구

**논문:** IReEn: Reverse-Engineering of Black-Box Functions via Iterative Neural Program Synthesis. 2020년 공개 연구.  
**원문:** [논문](https://arxiv.org/abs/2006.10720) · [워크숍 논문](https://openreview.net/pdf?id=HyLGEHFzqzM)

내부를 보지 못하는 함수의 입력·출력 사례로 후보 프로그램을 생성하고, 충족하지 못한 제약을 이용해 반복적으로 개선한다. 코드의 문자열이 같은지보다 관측되지 않은 입력에서 기능적으로 일치하는지를 다룬다는 점이 중요하다.

Karel 환경의 제한된 프로그램을 대상으로 하므로 기업 제품 재현 성능으로 일반화할 수는 없다. 그러나 한 번의 추측으로 구현을 확정하지 않고, 관측과 실패 사례를 이용해 수정한다는 원리는 참고할 만하다. 유한한 입력 시험의 통과는 모든 가능한 입력에 대한 동등성 증명과 다르다.

## 4. 비슷한 도구·앱

아래는 원본 공개 저장소의 설명을 확인한 결과다. 이번 조사에서 설치·실행하거나 도구가 주장하는 성능을 독립 검증하지는 않았다. 포크 저장소는 별도 제품으로 세지 않았다.

| 도구 | 확인된 처리 흐름 | Replica와 겹치는 부분 | 중요한 차이 |
|---|---|---|---|
| [Ralph-to-Ralph](https://github.com/namuh-eng/ralph-to-ralph) | SaaS URL과 문서에서 요구사항을 추출하고 제품을 구현·시험·배포하는 파이프라인 | URL → 제품 이해 → 구현 → QA. 서버와 API 기능도 대상으로 한다. | 제품 복제가 목적이다. 고객 대상 AI 주장만 선별하거나, 회사별 모든 주장에 대해 재현·미실행 판정을 내리는 구성은 확인되지 않았다. 해커톤의 데모 성과는 제작자 자기보고다. |
| [Greenfield](https://github.com/prime-radiant-inc/greenfield) | 소스·문서·SDK·실행 관측 등에서 동작 명세, 테스트 벡터, 합격 기준, 출처 기록을 생성 | 증거 수집 → 동작 명세 → 검증 기준이라는 조사·계약 구간 | 명세 생성에서 멈추며 구현은 별도 팀이 수행한다. 소스 접근을 포함할 수 있어 공개 주장만 쓰는 조건과 동일하지 않다. |
| [Atlas MCP](https://github.com/geo-mena/atlas-mcp) | 소스·UI·HTTP·문서 수집 → 사실 통합 → OpenAPI/MCP 코드 골격·테스트 → 출력 비교 | 여러 증거를 합쳐 실행 계약과 검증 수단을 만든다. | 레거시 시스템 분석용 MVP다. 공개 예시는 합성 데이터 기반이며, 실제 대기업 배포 성과로 해석할 수 없다. 코드 골격 생성이 전체 백엔드 재구현을 뜻하지 않는다. |
| [Integuru](https://github.com/Integuru-AI/Integuru) | 브라우저 네트워크 기록 → 요청 의존성 분석 → 원래 플랫폼을 호출하는 통합 코드 | 관측을 통해 API 사용법과 작업 흐름을 알아낸다. | 원서비스를 계속 호출한다. 회사의 기능을 독립 구현한 것과 다르다. 공개 저장소는 초기 버전이며 현재 제품과 같다고 가정할 수 없다. |

**비교 판단:** Ralph-to-Ralph는 단순 화면 복제 도구로 분류하면 안 된다. 반대로 Integuru로 동일한 사용자 결과를 얻더라도, 그 결과가 여전히 원서비스에 의존한다면 독립 재현 성공으로 세면 안 된다. Greenfield는 전체 경쟁 제품이라기보다 명세 추출·검토 단계의 직접적인 설계 참고자료다.

## 5. 현재 기능 강화에 도움이 되는 연구

아래 적용 방법은 논문의 직접 주장과 구분한 Replica용 제안이다.

| 강화 지점 | 연구와 확인한 방법 | Replica에 제안하는 적용 | 적용 조건·주의 |
|---|---|---|---|
| 근거 있는 주장 추출 | [VeriScore — Findings EMNLP 2024](https://aclanthology.org/2024.findings-emnlp.552/): 문맥을 반영하고 검증 가능한 주장만 추출 | 주체·수식 조건·입력 범위가 요약 과정에서 바뀌지 않는지 확인 | 세부 사실은 claim 내부의 근거로 두고, 전체 사용자 기능을 여러 claim으로 과분할하지 않는다. |
| 조사에서 부족한 근거 식별 | [AVeriTeC — NeurIPS 2023](https://proceedings.neurips.cc/paper_files/paper/2023/hash/cd86a30526cd1aff61d6f89f107634e4-Abstract-Datasets_and_Benchmarks.html): 주장 → 질문 → 근거 있는 답변 → 판정 | 각 미해결 계약 항목을 검색 질문으로 만들고, 답을 찾지 못하면 부족 상태를 유지 | 문서가 주장을 뒷받침하는 것과 실제 제품이 그 기능을 수행한다는 실험 증거는 다르다. |
| 명세가 구현 중 약해지는 문제 | [PaperCompiler — 2026 arXiv](https://arxiv.org/abs/2609.02272): 출처와 지원·추론·위임·미해결 상태, 비약화 요구사항을 명세에 보존 | 직접 확인된 요구와 구현상 선택을 구분하고, 근거 없는 단순화를 탐지 | 논문 명세에서의 방법을 기업 주장에 맞춰 검증해야 한다. 코드 생성 평가 향상을 원제품 재현율로 바꾸지 않는다. |
| 계약의 지속성 | [ReproAgent](https://arxiv.org/abs/2608.24291): 요구사항과 참고 근거를 구현·수정 전 과정에서 유지 | research와 계약, 구현 책임, 시험 기준의 참조 누락 검사 | 기존 직접 Operator/Builder 통신과 비공개 평가 경계를 유지한다. |
| 동작 범위에 대한 시험 | [CheckList — ACL 2020](https://aclanthology.org/2020.acl-main.442/): 최소 기능, 불변성, 변화 방향을 시험 | 기존 불변·사실 변경 시험을 도메인별 입력 변환으로 확장하고 변환의 타당성도 확인 | 입력을 바꿔도 정답이 같다는 전제가 실제 계약에 맞아야 한다. |
| 약한 테스트에 대한 과적합 | [EvalPlus — NeurIPS 2023](https://proceedings.neurips.cc/paper_files/paper/2023/hash/43e9d647ccd3e4b7b5baab53f0368686-Abstract-Conference.html): 생성·변이 입력과 기준 구현 비교로 테스트 강화 | 정상 예제 외에 유효한 경계·변형 입력을 만들고, 잘못된 구현을 잡는지 확인 | 기준 구현이나 검증된 정답이 필요하다. LLM이 만든 기대값을 자동으로 정답으로 취급하지 않는다. |
| 실제 동작 차이에서 개선 | [SkillClone](https://arxiv.org/abs/2608.04192), [IReEn](https://arxiv.org/abs/2006.10720): 입력·출력 관측과 반복 재구현 | 원제품 접근이 가능한 기능에 한해 개발용 차등 관측·수정 루프 추가 | 최종 비공개 테스트를 수정을 위한 데이터로 재사용하지 않는다. |
| 반복 실행의 안정성 | [τ-bench — 2024](https://arxiv.org/abs/2406.12045): 최종 상태 기반 채점과 여러 시도에서의 일관성 | 같은 조건에서 새 세션으로 반복하고 성공률·비용·지연을 함께 기록 | pass^k는 k번 모두 성공하는 신뢰성과 관련된다. 한 번이라도 성공하는 pass@k와 구분한다. |

관련 구현: [VeriScore](https://github.com/Yixiao-Song/VeriScore), [CheckList](https://github.com/marcotcr/checklist), [EvalPlus](https://github.com/evalplus/evalplus). τ-bench는 여기서 원 논문의 평가 개념을 참조한다. [기존 τ-bench 저장소](https://github.com/sierra-research/tau-bench)는 자체적으로 오래된 과제임을 알리고 후속 저장소로 안내하므로, 그대로 최신 평가 세트라고 채택하지 않는 편이 맞다.

## 6. 우선순위 제안

### 우선 1: 주장, 구현 선택, 시험 정답의 출처를 연결

현재 계약에 있는 정보를 활용해 각 핵심 요구사항에 원문 위치, 근거 상태, 검증 기준을 연결한다. 예를 들어 고객에게 제공되는 출력은 직접 확인된 요구일 수 있지만, 그 출력을 만들기 위해 우리가 선택한 검색 방식은 구현 가설일 수 있다. 이 둘을 같은 확실성으로 기록하지 않는다.

참고 방법은 [PaperCompiler](https://arxiv.org/abs/2609.02272)와 [ReproAgent](https://arxiv.org/abs/2608.24291)다. 현 단계의 제안은 큰 새 프레임워크 도입이 아니라 기존 계약의 참조와 누락을 검사하는 것이다.

가장 중요한 질문은 **“이 테스트의 기대 결과를 무엇으로 알았는가?”**다. 원제품 관측, 명시적인 공개 규칙, 검증된 독립 데이터, 관계만 확인하는 시험을 구분한다. 모두 충족하지 못한 기대값은 추가 조사 대상이다.

### 우선 2: 테스트가 틀린 구현을 실제로 탈락시키는지 평가

[PaperBench](https://arxiv.org/html/2504.01848v2)의 평가자 검증과 [EvalPlus](https://proceedings.neurips.cc/paper_files/paper/2023/hash/43e9d647ccd3e4b7b5baab53f0368686-Abstract-Conference.html)의 테스트 강화에서 가져올 방향이다. 숨겨진 테스트라는 사실만으로 충분한 평가가 되지는 않는다.

도입 예시로, 항상 같은 답을 내는 구현, 출력 형식만 맞추는 구현, 일부 필수 필드를 빼는 구현을 시험해 평가기가 이를 탈락시키는지 확인한다. 동시에 올바르다고 별도로 검증한 결과를 잘못 탈락시키는지도 살핀다. 이것은 Replica 평가기를 점검하기 위한 제안이며, 위 논문이 이 모든 대조 실험을 동일하게 수행했다는 주장은 아니다.

자유로운 생성 문장은 문자열 일치만으로 평가하지 않고, 필수 사실·출처 연결·정보 부족 처리처럼 확인 가능한 조건을 분리한다. 의미 평가가 필요한 항목은 소규모 사람 검토 또는 별도 기준과 비교해 잘못된 합격·불합격을 측정한다.

### 우선 3: 원제품에 접근할 수 있을 때만 관측 기반 검증 추가

[SkillClone](https://arxiv.org/abs/2608.04192)과 [RepoZero](https://arxiv.org/abs/2605.07122)의 장점은 기준 동작과 대체 구현을 같은 입력으로 비교한다는 데 있다.

우리에게 허용된 데모·API 접근이 있는 기능에서는, 가능한 여러 동작 가설이 서로 다른 결과를 내는 개발용 입력을 선택하고 원제품에서 관측한다. 이 관측으로 명세를 보강한 후 구현과 비교한다. 공개 페이지밖에 없는 기능에는 이 수준의 원제품 비교를 했다고 표시하지 않는다.

개발용 관측과 최종 비공개 평가를 분리한다. 새로운 관측으로 계약이 바뀌면 조사 버전과 계약 버전을 갱신하고 다시 고정해야 한다. 이미 본 출력에 맞춰 기존 합격 조건을 조용히 바꾸는 방식은 사용하지 않는다.

### 우선 4: 일반 모델 대비 추가 기능과 재현 비용을 측정

[SkillClone](https://arxiv.org/html/2608.04192v2)의 기반 모델 대비 추가 기능 구분과 [τ-bench](https://arxiv.org/abs/2406.12045)의 반복 안정성을 참고할 수 있다.

같은 데이터·모델·도구 접근 조건과 명시적인 자원 제한 아래에서 일반 모델 사용, 단순 공개 구현, Replica 구현을 비교하는 실험을 제안한다. 한 번 성공한 결과뿐 아니라 반복 실행, 실제 파일 처리, 정보 부족 입력, 비용과 지연을 확인한다. 연구의 모델·비용 수치를 그대로 우리 제품의 예상 성능으로 사용하지 않는다.

재현에 실패했을 때는 명세 부족, 데이터·서비스 접근 부족, 실행 환경·예산 문제, 실제 동작 불일치의 어느 쪽인지 남긴다. 공개 범위에서 재현에 성공해도 회사 전체의 데이터 우위·운영 품질·사업 경쟁력이 사라진다고 결론 내릴 수는 없다.

## 7. 적용 예시: 문서에서 정보 추출 후 결과물을 만드는 기능

다음은 특정 기업의 실제 주장이나 측정 결과가 아닌 가상의 설계 예시다. 시험 관계는 대상 claim의 실제 계약에 맞는지 먼저 검증해야 한다.

| 입력 변화 | 확인할 동작 | 해당 아이디어 |
|---|---|---|
| 관련 없는 문단의 순서만 변경 | 추출해야 할 핵심 사실은 유지 | CheckList의 불변성 |
| 원문의 유효한 날짜 값만 변경 | 결과의 해당 날짜도 변경 | CheckList의 변화 방향 |
| 원문에서 필수 금액을 삭제 | 근거 없이 값을 생성하지 않고 정보 부족을 표현 | 현재 Replica의 정보 부족 계약 |
| 원제품과 복제 구현에 동일한 새 문서를 제공 | 정해진 필수 필드와 근거의 차이 비교 | SkillClone·RepoZero의 차등 검증 |
| 항상 같은 결과를 내는 대조 구현을 제출 | 평가에서 탈락 | 평가기의 오류 탐지 능력을 점검하는 제안 |
| 새 세션에서 여러 번 반복 | 우연한 성공과 안정적인 성공 구분 | τ-bench의 반복 신뢰성 |

기능 단위는 문서 입력에서 최종 결과물까지 그대로 유지한다. 문서 읽기, 정보 추출, 결과 생성이라는 내부 단계별 확인을 추가하더라도 이를 자동으로 세 개의 독립 claim으로 늘리지는 않는다.

## 8. 결과에 구분해서 표시할 세 가지

아래는 새로운 판정 체계의 강제 도입이 아니라, 현재 결과를 설명할 때 권하는 의미 구분이다.

| 표시할 사실 | 의미 | 이것만으로 결론 내릴 수 없는 것 |
|---|---|---|
| 회사 주장과 출처를 확인함 | 회사가 고객에게 해당 기능을 제공한다고 실제로 설명한다. | 실제 성능이 그 설명과 같다는 것 |
| 공개 계약 범위에서 기능을 재현함 | 명시한 입력 범위와 평가 조건에서 대체 구현이 검증을 통과했다. | 원제품과 동일한 내부 구조 또는 전체 성능 |
| 원제품의 관측 동작과 비교함 | 같은 입력에 대해 사전에 정한 기준으로 원제품과 비교했다. | 모든 가능한 입력에서의 동등성 또는 회사 전체 경쟁력 부재 |

이 구분은 [PaperBench](https://arxiv.org/html/2504.01848v2)의 평가 수준 구분과 [RepoZero](https://arxiv.org/abs/2605.07122)·[SkillClone](https://arxiv.org/abs/2608.04192)의 기준 동작 접근 조건을 Replica의 보고에 적용한 해석이다.

## 9. 읽기·검토 순서

현재 기능 강화가 목적이라면 **PaperCompiler → ReproAgent → PaperBench → RepoZero → CheckList/EvalPlus** 순서로 보는 것을 제안한다. 먼저 근거가 구현으로 제대로 전달되는지, 이어 평가가 무엇을 증명하는지 확인하는 순서다. 원제품의 데모·API를 사용할 수 있는 대상이 많다면 **SkillClone**을 첫 순서로 올린다.

경쟁·유사 도구의 구현을 살펴볼 때는 **Ralph-to-Ralph → Greenfield → Atlas**가 유용하다. Integuru는 원서비스 호출을 유지하는 관측·통합 계층의 참고자료로 별도 취급한다. 이는 기능 관련성에 따른 조사자의 우선순위이며, 제품 성능을 비교 실험한 순위가 아니다.

## 10. 조사 범위와 남은 한계

원문과 저장소 설명으로 위 구조와 출처를 확인했지만, 각 도구를 설치하거나 벤치마크를 재실행하지 않았다. 학회 논문집에서 출판 상태가 확인된 연구, arXiv 공개 연구, 저자 저장소의 자기보고를 구분했다. ReproAgent의 채택 상태는 arXiv 저자 메타데이터 표기를 기준으로 기록했다. 서로 다른 벤치마크 점수를 한 표에 놓고 성능 순위로 환산하지 않았다.

프로젝트 내부 비교는 읽기에 성공한 Replica Research 지침을 기준으로 한다. 추가 로컬 참고 파일 읽기 요청 하나는 도구가 “요청의 보안 상태를 결정하지 못해” 차단하여 해당 내용은 확인하지 못했다. 프로젝트 코드의 현재 완성도에 대한 진단으로 해석해서는 안 된다.

동일한 전체 구성의 상용 경쟁 제품을 확인하지 못한 점은 공개 검색의 한계다. 특정 제품의 신규성·독점성 또는 기업의 기술적 진입장벽 부재를 입증하는 조사로 사용할 수는 없다.

### 11.1 현재 측정에서 먼저 메워야 할 부분

현재 구조에서 성능 개선을 논하기 전에 계측의 빈칸을 줄여야 한다.

- `src/replica_mvp/resources.py`에는 `active_time`, `waiting_time`, `preparation_time`, `human_time`, `economic_cost`, `tokens` 필드가 있지만 `unknown_resources()` 경로에서는 실제 값이 비어 있다.
- `src/replica_mvp/single_agent.py`는 구현 agent 내부의 반복 횟수와 agent 토큰 사용량을 측정하지 않는다고 명시한다.
- `src/replica_mvp/bundle_runtime.py`는 최종 evaluator의 `input_tokens`, `output_tokens`, `cached_input_tokens`를 일부 기록하지만 research/Operator/Builder 전 구간의 비용을 연결해서 보지는 못한다.
- bundle evaluation의 `cost_limit`는 경제 비용이 실제로 계측되지 않으면 검증 가능한 제한으로 동작하기 어렵다.

따라서 최소한 claim별로 다음 지표를 남기는 것이 좋다: **재현 성공률, correction count, phase별 active/waiting time, 전체 tokens, 실패 유형 분포, 성공한 재현 1건당 자원·비용**. 이 계측이 있어야 모델 변경, agent 구조 변경, 검색 품질 개선, evaluator 개선 중 무엇이 실제 효과를 냈는지 분리할 수 있다.

### 11.2 Single Agent vs Operator/Builder 비교 실험

현재 레포에는 이미 단일 agent baseline과 Operator/Builder 구조가 함께 있으므로 새로운 benchmark를 만들기 전에 두 구조를 통제된 조건에서 비교할 수 있다.

**실험 A — 구조 자체의 효과**

- 같은 모델 능력과 reasoning effort
- 같은 도구 접근
- 같은 replication contract
- 같은 총 token/time budget
- 차이는 single agent인지 Operator/Builder인지뿐

이 실험은 협업 구조 자체가 주는 효과를 본다.

**실험 B — 실제 운영 구성의 효과**

- 현재 제품에서 실제 사용하는 각 agent의 모델과 reasoning effort를 그대로 사용
- 같은 claim set에서 end-to-end 성공률, 시간, 토큰, correction 수, 실패 유형을 비교

이 실험은 구조뿐 아니라 현재 운영 설정 전체가 실제로 어느 정도 자원을 써서 어느 정도 성능을 내는지 본다. 두 실험을 분리해야 “다중 agent라서 좋아진 것”과 “더 강한 모델·더 많은 추론 예산을 써서 좋아진 것”을 구분할 수 있다.

### 11.3 Adaptive / Corrective Search

현재 2차 조사는 모든 bucket을 확인하되 깊이를 조절하는 구조가 있으므로, 이를 단순 `deep/shallow`보다 한 단계 더 계측 가능한 방식으로 만들 수 있다. 각 검색 시도에 아래 메타데이터를 남긴다.

```json
{
  "target_gap": "replication_contract[0].evaluation.cases",
  "query_intent": "find a public benchmark or deterministic acceptance rule",
  "evidence_gain": "partial",
  "source_quality": "primary",
  "next_action": "search official docs for edge-case behavior"
}
```

`evidence_gain`은 `filled | partial | none`처럼 단순하게 유지한다. `none`이 반복되면 같은 검색어를 계속 늘리기보다 소스 유형을 바꾸거나 해당 계약 필드를 unresolved로 남기는 쪽이 낫다. Adaptive-RAG는 검색량 조절에, CRAG는 이미 가져온 근거의 품질을 평가하고 검색을 교정하는 데 참고할 수 있다.

### 11.4 검증된 Workflow Memory

재사용해야 할 것은 특정 회사의 답이나 sealed evaluator에서 드러난 정답이 아니라, 여러 claim에서 반복되는 **절차**다. 예시는 다음과 같다.

- PDF/문서 비교: 텍스트 추출 → 표·이미지 별도 확인 → 필드별 근거 위치 기록 → 산출 결과와 원문 대조
- 구조화 추출: 계약 필드 → 필요한 원천 데이터 → 변환 규칙 → 누락 처리 → source mapping
- 외부 API: 인증 방식 → rate limit → 입력·출력 schema → side effect 여부 → 재시도·오류 처리
- 파일 산출물: 실제 내용 → MIME/확장자 → checksum 또는 크기 → 저장 위치 → downstream에서 다시 열리는지 확인

ACE와 Agent Workflow Memory는 이런 절차를 과거 성공 사례에서 추출해 다음 실행의 작업 문맥으로 사용하는 방향의 근거가 된다. 단, 성공 사례에서 우연히 맞은 프롬프트를 그대로 누적하지 말고 validator를 통과한 절차만 재사용하는 것이 좋다.

### 11.5 Validator 피드백 구조화

현재 correction loop의 품질은 agent가 실패 원인을 얼마나 정확히 전달받는지에 크게 좌우된다. SWE-agent의 agent-computer interface 관점과 MAST의 실패 분류를 결합하면 validator가 다음처럼 반환하도록 설계할 수 있다.

```json
{
  "category": "evaluation_gap",
  "field": "replication_contract[0].evaluation.cases",
  "problem": "acceptance criterion c-03 has no runnable check",
  "owner": "second_pass_research",
  "allowed_fix": "add an evaluation case or evidence-backed deterministic assertion"
}
```

이렇게 하면 Builder가 조사 부족을 코드로 덮거나, research agent가 구현 버그를 다시 검색하는 식의 잘못된 수정 루프를 줄일 수 있다.

### 11.6 난도가 높은 claim의 Test-Time Scaling

모든 claim에 여러 구현 후보를 만드는 것은 비용이 크다. 대신 첫 구현이 반복적으로 public/development validation을 통과하지 못하거나 계약이 복잡한 claim에만 S* 방식의 test-time scaling을 적용하는 편이 적합하다.

예를 들어 후보 2~3개를 만들고, 공개된 development test·계약 assertion·정적 검증으로 비교한 뒤 하나만 sealed evaluation에 제출한다. sealed 평가 결과를 보고 다시 후보를 고르는 구조는 평가 누출이 되므로 피한다.

### 11.7 적용 순서

| 순서 | 개선 | 이유 |
|---:|---|---|
| 1 | phase별 시간·토큰·실패 유형 계측 | 개선 효과의 원인을 구분하기 위한 전제 |
| 2 | single agent vs Operator/Builder 통제 실험 | 다중 agent 구조의 실제 기여도를 확인 |
| 3 | GEPA식 prompt 개선 + SWE-agent식 validator feedback | 반복 실패가 많은 지점을 직접 줄임 |
| 4 | Adaptive-RAG + CRAG 방식의 검색 조절 | pass 2의 검색 비용과 증거 품질을 함께 개선 |
| 5 | 검증된 workflow memory | 반복되는 성공 절차를 재사용해 탐색 비용을 줄임 |
| 6 | 어려운 claim에 제한적으로 S* 방식 후보 비교 | 구현 품질을 높이되 비용 폭증을 막음 |
| 7 | AFlow류 workflow 자동 최적화 | 신뢰할 수 있는 개발 지표가 충분히 쌓인 이후에만 의미가 있음 |

가장 먼저 필요한 것은 **instrumentation과 baseline**이다. 이 두 가지 없이 프롬프트, 모델, 다중 agent 구조, 검색 전략을 동시에 바꾸면 성능 변화가 어디서 생겼는지 알 수 없다. 먼저 현재 구조를 측정하고 single-agent 기준선을 고정한 뒤 나머지 개선을 한 축씩 적용해야 더 좋은 결과가 실제 아키텍처 개선 때문인지 검증할 수 있다.

## 12. 체험 중심 개편안이 구현됐을 때의 Ralph 비교와 논문 적용

비교 전제는 [2차 계약 개편 초안](/Users/cho/replica-mvp/docs/pass2-interaction-redesign.md)의 확정된 제안이 구현됐다는 가정이다. 실제 코드가 그렇게 바뀌었다는 뜻은 아니다. 초안에서 미정인 웹/CLI 화면, 이벤트 형태, 봉인 평가의 완전 삭제 여부, 판정 모델은 확정된 것으로 간주하지 않는다. 2차 근거 조사와 기존 구현 경로는 유지된다고 본다. 이 절은 앞선 현행 설계 분석과 구분한 후속 설계 비교다.

이번 후속 확인은 Exa 도구가 현재 세션에 노출되지 않아 원본 GitHub 문서·프롬프트와 논문 페이지를 직접 조회했다. Ralph를 설치·실행하거나 두 시스템의 성능을 비교 실험하지 않았다. 아래 효과와 우선순위는 설계 제안이다.

### 12.1 두 시스템이 가까워지는 부분과 남는 차이

**초안 적용 후에는 둘 다 관측·문서를 바탕으로 사람이 사용할 복제품을 만든다. 차이는 원기업 내부 구조를 알아내느냐보다, 재현 결과를 어떤 근거와 조건으로 해석하느냐에 있다.** Ralph도 관측 근거에 따른 아키텍처 설계, 기능·실제 백엔드 확인, 실패 기록과 수정 루프를 가진다.

| 비교 축 | Ralph의 확인된 설계 | 초안 적용 후 Replica | 평가 목적에서의 의미 |
|---|---|---|---|
| 출발점 | 제품 URL, 문서, 접근 가능한 실제 제품의 사용·관찰 | 기업의 고객 대상 AI 주장과 근거를 수집하고 claim별 재현 준비 | Replica는 회사 주장과 실험 대상의 연결을 설명하기 좋다. |
| 원본 접근 | Inspect 지침은 로그인된 원제품과 API 접근을 전제하고 실제 사용을 요구 | 공개 근거와 샘플로도 진행하며 `direct/public/claim_only` 유지 | 원제품을 관찰한 Ralph 실행이 문서만 읽은 Replica 실행보다 동작 근거가 강할 수 있다. |
| 작업 단위 | 작은 PRD 항목으로 나누어 구현·QA | 고객의 전체 업무 흐름을 한 claim으로 두고 `step_coverage` 기록 | 구현은 작은 작업으로 나누어도 최종 평가는 전체 흐름으로 유지할 수 있다. |
| 구현 방식 | PRD·문서·스크린샷에 근거한 아키텍처 결정 후 Build·QA | 기존 구현 경로에 `interaction`, `setup/user_input`, 필수 `experience` 추가 | 둘 다 합리적인 대체 구현을 선택할 수 있다. 내부 구조 일치를 차별점으로 둘 필요가 없다. |
| 체험 | 실행 가능한 앱·API·필요한 SDK, 배포·브라우저 확인 | 단발·대화·일괄 처리와 실제 파일 입출력 체험 | Replica의 체험 화면 형태는 미정이므로 완성된 SaaS UX까지 보장한다고 해석하지 않는다. |
| 개발과 평가 | Build 테스트 후 별도 QA 단계. QA도 버그를 직접 수정하고 재시험 | 사전 공개 기준, 개발 중 확인, 자동 판정, 사람의 최종 판단 | 별도 역할·세션이 있다는 것과 구현에 쓰지 않은 입력으로 검증했다는 것은 다르다. |
| 결과 기록 | 기능별 pass/fail/partial, QA 단계·버그·수정 이력 | case별 입출력·판정 이유, 단계 누락, 근거 수준, 시나리오 의존성 | Replica가 비교 가능한 평가 도구가 되려면 미평가 핵심 조건도 최종 결과에 반영해야 한다. |
| 자원과 난도 | README에 실행 비용 상한·재시작·정체 감지 장치 설명 | 사람 개입을 난도 데이터로 기록하는 방향 | 어느 쪽도 이번 비교에서 실제 자원 측정의 완전성을 검증하지 않았다. 비용 상한과 전체 재현 비용 보고는 다르다. |

Ralph 근거: [Inspect](https://github.com/namuh-eng/ralph-to-ralph/blob/main/ralph/inspect-spec.md), [Architecture](https://github.com/namuh-eng/ralph-to-ralph/blob/main/ralph/architecture-prompt.md), [QA 기능 검사](https://github.com/namuh-eng/ralph-to-ralph/blob/main/ralph/qa/base.md), [QA 기록·수정](https://github.com/namuh-eng/ralph-to-ralph/blob/main/ralph/qa/footer.md), [README](https://github.com/namuh-eng/ralph-to-ralph).

초안의 체험 개선은 평가 타당성을 높인다. 하지만 동일한 공개 예제 통과와 주관적 체험만 남으면 Ralph의 제작·QA 흐름에 결과 설명을 더한 수준에 머물 수 있다. 차별화 효과를 확인하려면 원본과의 비교, 재현 범위, 반복 안정성, 의존성, 자원 소모가 실제 결과에 남아야 한다.

### 12.2 초안에 직접 적용할 가치가 높은 연구

아래의 ‘논문 방법’은 원문에 근거한다. ‘초안 적용’은 해당 방법을 Replica에 맞춘 제안이며 논문이 기업 모방 가능성 평가를 검증했다는 뜻은 아니다.

| 연구 | 논문에서 참고할 방법 | 초안 적용 위치와 구체 제안 | 적용 한계 |
|---|---|---|---|
| [SkillClone](https://arxiv.org/abs/2608.04192), [RepoZero](https://arxiv.org/abs/2605.07122) | 공개 인터페이스·관측 응답에서 재구현하고 원본 동작과 비교 | 2차 조사와 3.3 체험에 원본 관측을 연결. 같은 입력·설정에서 원본과 복제품의 차이를 기록하고 개발용 관측과 최종 확인 입력을 구분 | 원본 접근이 있어야 차등 비교 가능. 제한된 skill/API 결과를 전체 SaaS로 일반화하지 않는다. 생성 문장은 문자열 일치 대신 과업 기준이 필요하다. |
| [τ-bench](https://arxiv.org/abs/2406.12045) | 동적 대화, 도구 사용, 종료 시 상태 비교, 반복 성공의 신뢰성 | 3.4 conversation 실행기에 세션 상태와 종료 조건을 둔다. 인터뷰의 수집 정보·진행 상태, 액션의 승인·실행 여부를 확인 | 고정 대본 한 개만으로 모든 대화 경로를 대표할 수 없다. 데이터베이스 정답을 만들 수 없는 과업에는 별도 평가 기준이 필요하다. |
| [PaperBench / JudgeEval](https://arxiv.org/abs/2504.01848) | 계층적 평가 기준과 사람 판정 자료를 이용한 자동 평가자 검증 | 3.4의 ‘내용은 AI가 판단’을 구체화. 핵심 조건별 근거·관측 결과·판정을 연결하고, 일부 결과를 사람이 검토해 AI의 오합격·오탈락을 측정 | 논문 저자와 만든 rubric을 사용하는 연구다. 기업 공개 문구만으로 같은 품질의 정답이 자동 확보되지는 않는다. |
| [CheckList](https://aclanthology.org/2020.acl-main.442/), [EvalPlus](https://arxiv.org/abs/2305.01210) | 행동별 최소 기능·불변·변화 시험, 추가 입력으로 약한 테스트 보강 | 3.4의 기본 3종에 기능별 의미 있는 변형을 추가. 파일 순서 변경, 핵심 수치 변경, 정보 삭제 등을 원본 조건에 맞게 설계 | 변형 관계의 타당성을 먼저 확인해야 한다. EvalPlus의 기준 구현을 일반 생성 과업에서도 당연히 확보할 수 있다고 가정하지 않는다. |

### 12.3 τ-bench를 적용하면 대화·이벤트 평가는 어떻게 달라지는가

크리에이터 인터뷰를 가정하면 ‘다음 질문을 출력했다’만 확인하지 않는다. 같은 세션에서 답변이 누적되는지, 사용자가 기존 답변을 정정했을 때 반영되는지, 필요한 정보가 없는 상태를 완료로 표시하지 않는지를 과업 기준으로 확인한다. 질문의 정확한 문구는 원본 계약이 요구하지 않는 한 고정하지 않는다. 이는 τ-bench의 상태·결과 기반 평가를 적용한 예이며 특정 Delphi 동작이 확인됐다는 뜻은 아니다.

고정 대본은 재현 가능한 회귀 시험으로 유지하되, 분기·정정·정보 부족을 다루는 작은 추가 시나리오를 둔다. 각 case 시작 시 설정·자료·세션을 같은 초기 상태로 복구하고, case 안에서는 대화 상태를 유지한다. 반복 성공은 한 번이라도 성공하는 `pass@k`와 구분한다.

이벤트형은 초안에서 미정이다. 어떤 형태로 표현하든 자동화 지시 → 이벤트 주입 → 승인 대기 또는 실행 → 관측 가능한 결과까지 검증해야 한다. ‘실행했습니다’라는 답변은 실행 증거가 아니다. 실제 외부 발송 대신 시험 환경을 쓰면 그 범위를 표시한다. 액션 자체가 핵심 기능인 claim에서는 부수효과 검사를 일괄 선택 사항으로 내리면 안 된다.

### 12.4 평가 구조는 가볍게 유지하면서 신뢰성을 보강하는 제안

1. **공개 개발 기준과 마지막 확인을 구분한다.** 초안처럼 기준·예제는 공개한다. 구현 버전을 고정한 뒤, 같은 범위의 새 입력으로 별도 확인한다. 확인 후 수정한 구현은 새 버전으로 기록하고 새 확인 입력이 필요하다. 최종 확인 종료 후 case를 공개할 수 있으므로 case별 투명성과 충돌하지 않는다.
2. **정답의 출처를 연결한다.** 원제품 출력, 명시적인 공개 규칙, 별도로 검증한 과업 정답, 타당성을 확인한 관계 시험을 구분한다. 공개 마케팅 주장이나 AI 판정자의 확신만으로 기대값을 만들지 않는다.
3. **체험 가능과 평가 완료를 구분한다.** 자료 부족 시 제작은 계속하되, 핵심 품질을 평가하지 못했다면 최종 결과에도 판단 보류를 표시한다. `NOT_EVALUATED`를 실패로 바꾸거나 평가된 소수 case만 분모로 삼아 전체 재현 성공으로 표시하지 않는다.
4. **핵심 조건을 작은 판정표로 만든다.** 전체 claim 아래 입력 처리·업무 결과·필수 제약·최종 산출물의 근거와 판정을 연결한다. 일부 주변 기능의 통과가 핵심 기능 실패를 상쇄하지 않도록 한다. 이것은 claim을 여러 개로 쪼개자는 제안이 아니다.
5. **사람의 체험을 비교 가능한 기록으로 남긴다.** 자유 체험은 유지하되 공통 과업에서 완료 여부, 사람이 대신 한 작업, 오류, 만족/불만족 이유를 적는다. 사람이 구현을 도운 기록과 최종 평가를 한 기록은 구분한다.

새 입력 확인의 중요성은 [AI Agents That Matter](https://arxiv.org/abs/2407.01502), 약한 시험의 보완은 [EvalPlus](https://arxiv.org/abs/2305.01210), 평가자 검증은 [PaperBench](https://arxiv.org/abs/2504.01848)에서 참고했다. 위 다섯 항목의 구체적인 운영 방식은 Replica용 제안이다.

### 12.5 더 좋은 결과와 더 적은 자원 소모를 위한 후속 연구

평가 대상인 복제품의 동작과 Replica 제작 파이프라인의 성능을 구분한다. τ-bench는 전자의 상호작용 평가에, 아래 연구는 주로 후자의 개선에 사용한다.

| 연구 | Ralph·초안과 연결되는 지점 | 적용 제안 |
|---|---|---|
| [GEPA](https://arxiv.org/abs/2507.19457) | Ralph의 QA 수정 이력과 초안의 case별 판정 이유 | 반복 실패를 바탕으로 조사·구현 지시를 개선. 회사 claim·출처·합격 기준은 최적화 대상에서 제외하고, 개발 과업과 최종 확인 과업을 나눈다. |
| [SWE-agent](https://arxiv.org/abs/2405.15793) | 파일·세션·표처럼 다른 체험을 도구로 실행 | 오류를 발생 단계·원인·허용 수정 범위로 전달하고 실행 인터페이스를 일관되게 만든다. 사람에게는 파일 업로드·대화를 제공하되 내부 어댑터는 구조화 메시지를 써도 된다. 단발 stdio 계약에 대화를 압축하지 않는다. |
| [Adaptive-RAG](https://aclanthology.org/2024.naacl-long.389/), [CRAG](https://arxiv.org/abs/2401.15884) | 기존 2차 조사를 유지하면서 근거 부족을 줄임 | 계약의 어느 빈칸을 채울지 정한 후 필요한 검색·관측을 선택한다. 같은 근거를 반복 수집하면 검색 경로를 바꾼다. 두 논문의 QA 방법을 조사 파이프라인으로 확장하는 제안이다. |
| [Agent Workflow Memory](https://arxiv.org/abs/2409.07429) | 파일 처리·체험 실행·QA에서 반복되는 작업 | 검증된 파일 검사, 세션 초기화, API 오류 처리 절차를 재사용. 기억 버전과 기존 자산을 기록해 처음부터 만든 실행과 섞어 비교하지 않는다. |
| [Agentless](https://arxiv.org/abs/2407.01489) | 여러 역할을 가진 Ralph와 Replica 모두의 구조 비용 | 단순한 구현 baseline을 같은 도구·자료·예산으로 비교. 논문은 기존 저장소 수정 과제이므로 전체 제품 생성에서 단순 구조의 우월성을 증명하지는 않는다. |

S*의 후보 비교와 AFlow의 워크플로우 자동 탐색은 평가 기준·자원 계측·개발 과업이 안정된 다음 검토한다. 평가가 약한 상태에서 후보 수만 늘리면 ‘잘 통과하는 구현’의 선택 편향을 키울 수 있다. ACE를 추가할 때는 Agent Workflow Memory와 별도 기억 체계를 무조건 둘 필요 없이 현재 재사용 절차의 부족한 부분부터 확인한다. 기존 논문의 세부 링크는 11절에 있다.

### 12.6 비교 실험과 적용 우선순위

Ralph와 Replica 중 어느 제작 방식이 좋은지와, 기업 기능이 얼마나 재현 가능한지는 다른 질문이다. 다음 두 실험을 구분한다.

- **제작 방식 비교:** 동일한 기능 범위·원제품 접근·자료·개발 예산을 주고 Ralph와 초안 적용 Replica, 단순 구현 baseline을 비교한다. Ralph의 작은 PRD 항목 수를 Replica의 claim 수와 직접 비교하지 않고 같은 전체 업무 과업으로 평가한다. 모델·reasoning 설정을 통제한 실험과 실제 운영 설정의 비교를 구분한다.
- **대체 가능성 비교:** 원제품 접근이 가능하면 원제품, 복제품, 최소한의 범용 모델·도구 baseline을 동일한 대표 과업에서 비교한다. 공개 자료를 각 대체 구현에 동일하게 주고 필요한 파일 처리·도구도 명시한다. 원제품의 비공개 데이터는 통제할 수 없으므로 관측 결과의 격차만으로 그 원인을 데이터라고 확정하지 않는다.

모든 실행은 조사·준비·제작·검증·사람 투입과 복제품 운영 비용을 구분하고, 모델·버전·날짜·예산·기존 자산을 기록한다. 성공은 그 조건에서 가능한 구현 경로의 증거이고, 실패나 실행 차단은 기업의 모방 불가능성을 증명하지 않는다.

| 우선순위 | 해야 할 일 | 가장 직접적인 참고 |
|---|---|---|
| 1 | 초안의 파일·세션·배치 체험을 실제 업무 흐름대로 구현하고 필수 요구를 보존 | Ralph의 관찰·실제 백엔드 검사, PaperCompiler/ReproAgent |
| 1 | 완료 상태·핵심 품질·평가 불가를 구분하고 AI 판정자를 소규모로 검증 | τ-bench, PaperBench |
| 1 | 사람 투입·자원·실패 원인 기록 | AI Agents That Matter, MAST |
| 2 | 원본 접근 가능한 claim부터 동일 입력 비교와 별도 새 입력 확인 | SkillClone/RepoZero, CheckList/EvalPlus |
| 3 | 통제된 baseline 비교 후 검색·지시문·절차 재사용 최적화 | Agentless, Adaptive-RAG/CRAG, GEPA, Agent Workflow Memory |

이 순서는 초안을 구현한다는 조건에서 재정렬한 것이다. 일반적인 아키텍처 개선을 다룬 11절과 달리 상호작용 보존·평가 타당성을 먼저 확보한다. 리버스엔지니어링 연구에서는 원본의 내부 구조를 추정하는 의무보다 **관측 가능한 동작을 가설·시험·비교로 좁혀 가는 방법**을 가져오는 것이 이 목적에 맞는다.
