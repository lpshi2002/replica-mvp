# 비용·AI 사례 시연·된 것과 안 된 것: 구현 권고

## 토론 이후 사용자 정정 — 현재 적용할 기준

2026-10-05, 같은 대화에서 사용자가 다음과 같이 정정했다.

> 우리는 완전 자동화라 첫 기업 입력빼고 사람 안들어갈건데 마지막에 그냥 테스트 해볼수있는게 사람이 해볼수있는 정도로 나온다라는거지 중간에 사람이 개입한다는게 아닌데? 그리고 사람이 테스트 하는것도 그냥 시각적으로 직접 상호작용할수있도록 한다는거고 결국 이게 AI 테스터랑 같은거잖아

이 후속 사용자 요구가 아래의 이전 모델 간 합의보다 우선한다. [프로젝트 방향](../../project-direction.md)의 현재 기준도 함께 정정했다.

- **완전 자동화:** 기업 입력 이후 조사·사례와 기대 결과 작성·구현·AI 시험·비용 기록·보고서와 체험 생성까지 자동 수행한다. 계획 파일 작성, 자료 준비, 코드 수정, 판정이나 승인을 사람에게 맡기는 단계를 정상 경로로 두지 않는다.
- **비용:** 자동 실행의 모델/API/도구 사용량·시간·비용·재시도를 기록한다. 사람의 작업 시간·인건비와 완료 후 선택적 체험 시간은 기본 비용 항목에서 제외한다. 과거 사람 개입은 필요한 경우에만 과거 실행의 한계로 구분한다.
- **공통 체험:** 사람이 시각적으로 확인하고 직접 상호작용할 수 있는 복제품을 제공하고 AI 테스터도 같은 구현 버전·사용자 작업 경로를 사용한다. AI와 사람의 조작 도구는 달라도 된다. 최종 산출물에는 원시 엔진 JSON 호출만으로 대체할 수 없는 체험 인터페이스가 포함된다. 구체적인 UI 기술은 미정이다.
- **완료 기준:** AI가 시험·판정·보고를 마치면 자동 결과 제공이 완료된다. 사람의 실제 테스트나 `human_review: pending` 해소를 기다리지 않는다. 선택적 체험은 자동 실행의 완료 조건이 아니다.
- **이전 구현안에 미치는 영향:** `engine_json`만 실행하고 사람용 화면을 후속으로 미룬 003의 안은 계측·엔진 검증의 개발 중간 단계로만 사용할 수 있다. 요청한 결과물의 완료에는 공통 체험 경로와 그 경로에서의 AI 시험을 포함해야 한다. 사례 계획도 공개 조사 결과에서 자동으로 작성·고정해야 한다.

이 정정은 사용자의 명시적 요구를 기록한 것이며 Claude가 새 전제를 재검토했다는 뜻이 아니다. 001~004 의견은 당시 전제와 검토 경위를 보존한다. 아래 1~6절 중 사람 개입·필수 사람 검토·엔진만으로 완료하는 부분은 현행 권고에서 제외한다. 비용 영수증·미평가 구분·관측 근거·기존 결과 보존 등 충돌하지 않는 권고는 유지한다.

## 2. 첫 구현 범위와 실행 순서

첫 제품 코드 변경 범위는 신규 demo 모듈, 호출·영수증 helper, 기존 bundle_runtime의 선택적 연결점, CLI 명령, 관련 테스트다. 기존 자원 형식과 번들 실행·파일/상태 검사 함수를 재사용한다. 기존 completion·봉인 평가·harness·회사 집계·2차 Skill 변경은 첫 기술 검증 범위에서 뺀다.

1. **공개 자료로 두 사례를 고정한다.**
   - 공개·합성 연락처 준비 → 자연어 지시 등록 → 이벤트 → 승인 대기 조회 → 승인 또는 거절 → 저장 확인의 전체 단계를 유지한다.
   - 사례마다 기대 조건의 근거, 허용 사실, 작성자, 계획 고정 시각·해시, 후보 버전·해시, 시간·행동 수 상한을 기록한다.
   - 기존 구현을 본 뒤 작성한 사례는 retrospective로 표시한다. 기존 데모 대본·구현 manifest를 원제품의 정답 근거로 격상하지 않는다.
   - targeted_barrier는 공개 출처가 있는 장벽 또는 null과 미확인 사유다. Actions에서 장벽을 확인하지 못했다면 만들어 채우지 않는다. 두 사례만으로 장벽 검증을 완료했다고 하지 않는다.
2. **실행 전에 계측을 연결한다.**
   - 테스터·판정 호출과 복제품 실행에 고유 호출 ID, 부모 단계, 원시 출력, 자원 영수증을 남긴다.
   - 내부 Claude CLI 호출에는 후보 파일을 수정하지 않는 PATH 래퍼를 조건부 사용한다. 아래 투명성 검증을 먼저 통과해야 한다.
3. **AI가 기존 엔진을 실제로 여러 턴 호출한다.**
   - bundle_session으로 같은 사례의 상태를 유지한다. 사례 간 상태는 분리한다.
   - AI는 앞선 응답에서 pending_id 등 동적 값을 얻는다. 임의 ID나 대본 밖 사실을 만들지 않는다. 실행기는 허용 action·단계·사실 범위를 검증한다.
   - AI에게 임의 셸 실행·구현 수정 권한을 주지 않는다. 실패를 숨기거나 합격하도록 후보를 자동 수정하지 않는다.
   - interaction_surface는 engine_json이다. 사람용 play.py 화면이나 실제 이메일 발송을 검증했다고 표현하지 않는다.
4. **별도 판정으로 세 결과를 만든다.**
   - 파일·상태 조건은 코드로 확인하고, 의미 판단은 별도 호출에서 한다. 별도 세션이라는 사실만으로 독립 평가라고 부르지 않는다.
   - 새 경로는 실행 상태와 passed / failed / not_evaluated를 따로 계산한다. 기존 boolean 판정·완료 집계에 억지로 넣지 않는다.
   - 승인 시 outbox 내용과 상태 변화를 확인한다. 거절 시 검토 직전 대비 outbox·연락처에 불필요한 효과가 없는지 확인하되 pending 기록이 rejected로 바뀌는 정상 변화는 허용한다.

최소 산출물은 demo-plan.json, events.jsonl, receipts/<call_id>/, artifacts/, demo-result.json, report.md다. 새 실행 디렉터리에 저장한다. 보고서는 투입 자원 → 사례별 입력·과정·출력·판단 이유 → 된 것·안 된 것·미확인 → 다음 질문 순서로 읽히게 한다.

## 3. 비용 기록의 합의 사항

- 새 실행의 고유 호출 최종 영수증을 한 번씩 집계한다. 부모 단계 요약과 자식 호출을 다시 더하지 않는다. helper와 래퍼가 같은 호출을 봤다면 같은 ID로 묶는다.
- 원시 usage와 modelUsage를 둘 다 보존하되 둘을 합산하지 않는다. 첫 집계의 원본은 usage, modelUsage는 관측 모델과 모델별 설명 자료다.
- noncached input_tokens 값 자체가 틀렸다고 보지 않는다. 현재 코드가 캐시 필드를 제외하므로 이를 전체 입력 사용량으로 읽으면 누락된다. 캐시·생각 토큰의 포함 관계가 불분명하면 전체 토큰 합계를 만들지 않는다.
- 요청 모델과 관측 모델을 구분한다. 관측값이 없으면 미확인으로 남긴다. 실패·시간초과도 호출 시도로 남기고 사용량 영수증이 없으면 unknown이다.
- 영수증 없는 Builder 자기보고는 self_reported로 표시하며 실측 합계에 넣지 않는다. 사람 개입 기록이 없다는 사실도 개입 0을 뜻하지 않는다.
- CLI가 제공한 costBasis=list 환산액은 estimated로 별도 표시한다. 구독 사용의 실제 청구액이 아니며, 새 가격표 조회나 자체 환산은 첫 구현에 필요 없다.
- 보존된 Delphi 세션 전환 영수증은 과거 일부 작업의 자료다. 원래 기능 제작 전체 비용이나 새 시연 합계에 넣지 않는다. 현재 후보와의 버전 연결을 확인하지 못하면 그 한계도 남긴다.
- 과거 결과 파일은 이전 제출의 개발 기록을 반복 포함할 수 있다. 과거 폴더 전체를 합산하지 않는다. 최신 결과 하나만으로 모든 과거 평가 비용이 보존된다고도 가정하지 않는다.
- 전체 경과 시간과 호출 시간 합계를 구분한다. num_turns를 호출 수로 바꾸지 않는다. 추정액으로 실제 금액 상한을 집행하지 않는다. 실제 금액 상한이 요구되지만 계측할 수 없으면 budget_unverifiable이다. 첫 실행 제한은 시간·행동 수와 포착 가능한 호출 수다.

## 4. 계측 장치의 조건과 검증

PATH 래퍼는 후보의 내부 CLI 재시도와 병렬 호출을 관측할 수 있는 제안이다. 아직 실행으로 확인하지 않았다.

- PATH 변경 전에 실제 CLI 절대경로를 확정해 재귀 호출을 막는다. 전역 환경은 바꾸지 않고 실행 환경의 PATH만 바꾼다.
- 호출마다 별도 디렉터리에 시작·원시 stdout/stderr·종료 기록을 남긴다. 병렬 호출이 같은 파일에 동시에 쓰지 않게 한다.
- argv·stdin·cwd·출력 바이트·종료 상태를 보존한다. 현재 환경 필터에 없는 별도 환경변수 전달에 의존하지 않는다.
- 결정적 가짜 CLI로 직접 호출과 계측 호출을 비교한다. 성공·실패·병렬·시간초과·강제 종료·남은 프로세스를 확인한다. 이후 같은 후보·초기 상태·입력으로 실모델 실행의 의미·파일 효과를 대조한다.
- 특히 엔진이 래퍼 PID만 종료하고 실제 CLI 자식을 남기는 구조를 허용하지 않는다. 구현 방식은 위 조건을 만족하는 가장 단순한 것으로 선택한다. 단순히 그 구간을 계측 범위 밖이라고 쓰는 것만으로 동작 변경을 정당화할 수 없다.
- 투명성 검증이 실패하거나 영향이 불명확하면 래퍼를 끄고 새 상태에서 다시 실행한다. 그 실행의 내부 모델 비용은 unknown, 측정 범위는 partial이다. 문제 있는 계측 장치를 유지한 채 표기만 바꾸지 않는다.
- 절대경로 CLI·직접 HTTP는 이 방식으로 관측되지 않을 수 있다. path_resolved_claude_cli 범위와 끊긴 영수증·누락 구간을 명시한다.

이 조건은 003의 검증 실패 시 제외 방침과 004의 시간초과 지적을 함께 적용한 진행자의 정리다. 소스 해시 불변은 행동 불변의 증거가 아니다.

## 5. 완료 기준과 후속 범위

첫 기술 검증의 완료는 승인·거절 두 사례를 실제로 시도하고, 비용의 측정 범위와 원시 기록, AI가 선택한 턴, 파일 효과, 판정 이유, 된 것·안 된 것·미평가를 사람이 확인할 수 있게 제공하는 것이다. 사례가 모두 성공해야 한다는 뜻은 아니다. 실패도 원인과 근거가 남아야 한다.

구현 시 필요한 검증은 다음이다.

- 계측 helper와 래퍼의 전달 투명성·병렬·중단·프로세스 정리.
- AI의 동적 ID 처리와 다중 턴 상태 유지.
- 승인과 거절의 실제 파일 효과 및 금지된 부수효과.
- 판정 실패·시간초과 시 not_evaluated 유지, 누락 자원의 unknown 유지.
- 영수증 중복 방지와 과거 비용 분리.
- 기존 기본 runtime 동작에 대한 관련 테스트와 전체 unittest 회귀 검증, git diff --check.

그다음에는 선택한 기업의 모든 조사 주장에 새 결과 또는 미실행 사유를 연결한다. 새 결과의 후보 버전과 미평가 상태를 기존 재현 실패로 바꾸지 않고 보존한다. 회사 전체 결과물에는 필요한 장벽 겨냥 사례, 특허·규제 정리, 경쟁 사업 조사도 붙인다. 첫 기술 검증을 회사 완료로 표시하지 않는다.

공개 시연을 기본 운영 경로로 연결하는 계약·harness·완료 판정·Skill 정합화는 후속 통합 작업이다. 과거 봉인 자료를 공개 사례 작성에 사용하지 않고, 기존 결과를 덮어쓰지 않는다. 별도 봉인 입력 해시 검사도 첫 단계에는 추가하지 않는다. 이는 변형 사례의 유출을 보장해서 막지 못하고 불필요한 비공개 자료 의존을 만들기 때문이다.

첫 기업의 최종 선정과 운영 전환 범위는 아직 확정하지 않았다. 이것이 첫 기술 검증 설계를 마치는 데 필요한 추가 승인이라는 뜻은 아니다. 향후 사용자가 구현을 요청하면 그 범위의 일상적 선택은 자율적으로 진행하며, 단계마다 재승인 관문을 만들지 않는다.

- [003 Codex 수정](003-codex-revision.md): 범위 축소 수용, 토큰 해석·비용 집계 정정, 래퍼 검증/제외 조건, 봉인 해시 비교 기각.

소스·문서·보존된 JSON 영수증과 일부 파일 해시를 읽어 확인했다. 이번 토론에서는 제품 코드 수정, 제품 실행, 기업 기능 평가, 테스트 실행을 하지 않았다. 신규 helper·래퍼·AI 시연 루프의 작동은 위 실행 검증을 거쳐야 한다. 토론 문서만 작성했으며, 구현·기본 정책·대상 기업을 승인된 것으로 바꾸지 않았다.
