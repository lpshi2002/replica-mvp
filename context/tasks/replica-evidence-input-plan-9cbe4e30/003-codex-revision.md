## Codex 수정안 — `replica-evidence-input-plan`

**판단 기준:** 판정은 기록된 근거를 가리켜야 하고, 시험에 쓴 입력 바이트는 동결·재개·비교에서 같아야 합니다. 정상 제공 경로와 기존 업무 기준은 유지합니다. 아래는 코드와 토론 자료를 읽고 정리한 구현안이며, 아직 구현하거나 검증한 결과는 아닙니다.

### P1 / N1 — 판정 참조와 결정적 검사 근거

`_screen_evidence`가 관측마다 고유한 ID를 만들고, `_judge_prompt`가 그 ID와 사건 ID를 모두 판정자에게 전달합니다. `JUDGE_SCHEMA`와 `_evaluate_case`는 사건·관측·출력 파일·입력 파일 참조를 각각 확인합니다. 기존 `evidence_event_ids`는 호환성을 위해 유지하고, 관측 및 파일 참조 필드를 추가합니다.

`passed`나 `failed` 판정에 유효한 참조가 하나도 없으면 최종 상태는 `not_evaluated`로 바꿉니다. 판정자가 낸 원래 상태와 거부한 참조도 결과에 남깁니다. 참조가 실제로 존재한다는 사실과 그 의미가 판정 내용에 맞는다는 사실은 별도로 취급합니다.

결정적 검사는 판정자의 참조에 기대지 않습니다. `_deterministic` 결과에 검사 종류·glob·전후 일치 경로와 해시를 보존합니다. 특히 부재 검사는 빈 일치 목록과 당시 전체 `tree_after`, 변경 없음 검사는 전체 `tree_before/after` 비교를 남깁니다. 현재 저장되는 트리 스냅샷을 활용하되, 성공한 검사 결과에도 어떤 스냅샷으로 판정했는지 연결합니다. 미완료 사례의 부재·변경 없음이 `not_evaluated`가 되는 기존 규칙은 유지합니다. 관련 경로는 [`web_demo.py`](/Users/cho/replica-mvp/src/replica_mvp/web_demo.py:58)입니다.

### P2 — 제공 버전과 앱 표시

`company_features`를 공통 진입점으로 쓰고, 그 안에서 기존 `_validate_bound_artifact`로 묶인 후보 manifest의 경로와 SHA-256을 확인합니다. 실패한 기능만 제외하고 사유를 남깁니다. `_serve_company`는 자체 feature 순회 루프를 없애고 이 함수를 호출합니다. 새 상태 디렉터리에서도 검증이 먼저 적용됩니다. 새 작업 공간 복사는 기존 `copy_bundle`, 기존 상태 확인은 `_open_workspace`를 재사용합니다.

구현물이 묶여 있고 파일 검증을 통과하면 부분 재현·미평가 상태도 제공 대상입니다. 이 경로에 재현 상태 문구나 평가 UI를 추가하지 않습니다. 모든 기능이 제외된 경우는 현재의 명확한 실행 불가 처리를 유지합니다. 관련 경로는 [`company_app.py`](/Users/cho/replica-mvp/src/replica_mvp/company_app.py:147), [`cli.py`](/Users/cho/replica-mvp/src/replica_mvp/cli.py:532), [`agent_harness.py`](/Users/cho/replica-mvp/src/replica_mvp/agent_harness.py:1362)입니다.

### P3a — 업로드 원본 고정과 legacy 정책

`freeze_demo_plan`이 새 계획에 업로드별 SHA-256을 기록하고, `validate_demo_plan`이 선언된 해시를 대조합니다. 새 실행은 해시 없는 업로드 계획을 거부합니다. 과거 결과의 읽기·검증은 그대로 허용하지만, 해시 없는 legacy 업로드 계획으로 새 평가·재개·비교를 시작하지 않습니다. 해시를 뒤늦게 붙여 옛 입력이 동결돼 있었다고 간주하지 않습니다. 새 시도가 필요하면 구현 전에 새 입력과 계획을 동결합니다. 업로드가 없는 legacy 계획은 이 제한에 걸리지 않습니다.

### P3b — 실제 입력 보존·변형·판정

먼저 변형 여부와 관계없이 실행할 업로드 바이트를 `cases/<id>/inputs/`에 원본 그대로 저장합니다. 결과에는 원본 해시·실행 입력 해시·경로를 기록하고, 기존 `write_checkpoint`/`load_checkpoint`의 `evidence_sha256` 검증을 이용합니다. 재개와 `input_cases_from` 비교는 저장된 바이트를 복사해 해시를 확인한 뒤 다시 사용합니다. 새 관측이 필요해도 입력을 재생성하지 않습니다. 입력 파일이 없거나 해시가 다르면 실패 처리하며 다시 추첨하지 않습니다. [`web_checkpoint.py`](/Users/cho/replica-mvp/src/replica_mvp/web_checkpoint.py:35)의 기존 체크포인트·비교 검증을 확장합니다.

계획에서 업로드별 `vary: true`로 명시한 파일만 변형합니다. 첫 지원은 20KB 이하 UTF-8 TXT/CSV로 제한합니다. 새 생성 스키마 대신 기존 `INSTANCE_SCHEMA`, `_instance_prompt`, `_instance_case`와 `replacements`를 재사용하되, 치환은 한 번에 적용해 연쇄 치환을 막고 원문·사례 문구·기대 문구·검사 텍스트·파일 값이 같은 규칙으로 변했는지 검증합니다. 생성기가 독립적으로 바꾼 goal/steps/facts가 그 렌더 결과와 다르면 실행하지 않습니다.

CSV는 `csv` 모듈로 셀을 읽고 써서 인용·쉼표 때문에 열이 깨지지 않게 합니다. 기존 업무가 요구하는 구조와 기준은 그대로 둡니다. 변형으로 헤더나 행·열 구조가 깨지면 차단합니다. 기대값이 합계 같은 파생값이면 생성된 숫자를 정답으로 신뢰하지 않습니다. 판정자에게 실제 실행 CSV 전체와 해시를 보여 주고, 고정된 기준의 파생 관계를 그 입력에서 계산해 결과와 비교하게 합니다. 정확한 기존 기준과 근거는 유지합니다.

변형 선언이 있지만 형식 미지원, 크기 초과, 읽기 실패, 무변경, CSV 구조 오류가 발생하면 해당 실행은 `not_evaluated`로 남깁니다. 원본 파일을 대신 올리거나 재추첨하지 않습니다. 변형을 선언하지 않은 업로드는 계획대로 고정 입력으로 사용합니다.

### P4 — 순서와 부정 사례 검증안

1. **P1:** 가짜 참조만 있는 성공·실패, 유효/무효 참조 혼합, 사건 없는 시작 관측, 잘못된 파일 경로를 확인합니다. 부재·변경 없음 스냅샷 보존과 미완료 검사의 `not_evaluated`도 확인합니다.
2. **P2:** 묶인 manifest 변조와 해시 불일치는 해당 기능만 제외하고, 정상 부분·미평가 구현은 계속 제공되는지 확인합니다. 새 상태 경로로 검증을 우회할 수 없어야 합니다.
3. **P3a:** 동결 뒤 업로드 바이트 변경과 해시 없는 legacy 업로드의 새 실행·재개·비교가 거부되는지 확인합니다. legacy 결과 읽기는 유지합니다.
4. **P3b:** 유효 TXT/CSV 변형, 치환 불일치, 무변경, 미지원 형식, 크기 초과, 잘못된 인코딩, CSV 구조 손상, 입력 누락·변조를 확인합니다. 중단 뒤 재개와 비교가 같은 저장 바이트를 쓰고, 판정 프롬프트에 실제 입력이 포함되는지도 확인합니다.

**002에서 수정·기각한 점:** 원본 fallback은 변형 입력을 선언하고도 고정 예시를 시험하는 결과가 되어 기각합니다. 앱에 평가 상태를 표시하는 안도 앱 사용 경로와 보류된 평가 표시 범위를 넓히므로 제외합니다. 순차 문자열 치환과 CSV를 단순 텍스트로 다루는 안은 일관성·구조·파생값을 보장하지 못해 수정했습니다. renderer로 재개 때 다시 생성하는 안은 실제 입력 보존 요구에 맞지 않아 저장 바이트의 복사·해시 검증으로 바꿨습니다. 파일 판정자에게 입력을 보여 주는 일을 뒤로 미루지 않고, 첫 TXT/CSV 변형부터 포함했습니다.

이번 턴은 읽기 전용으로 진행했으며 제품 코드를 수정하거나 시험·기업 실행을 수행하지 않았습니다.
