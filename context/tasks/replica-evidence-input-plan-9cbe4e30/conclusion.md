# 기존 Replica의 판정·제공 버전·업로드 시험 구현안

2026-10-15 (Asia/Seoul). 현재 대화의 명시 제안(001)을 Claude가 검토(002)하고, Codex가 수정(003), 같은 Claude가 재검토(004)했다. 아래는 권고 구현안이다. 제품 코드 구현·테스트 통과·사용자 정책 승인으로 해석하지 않는다.

**기존 기업 앱·브라우저 시험·체험 상태 분리·개발 로그·비용 집계를 그대로 사용한다. 변경은 판정 근거 검사 → 제공 버전 검사 → 입력 파일 고정 → 업로드 변형 시험의 네 단위로 나눈다.** 첫 구현 범위는 앞의 두 결함 수정이며, 입력 보존을 붙인 뒤 파일 변형을 추가한다. 보고서 작성·개선·질문 생성·평가 UI는 보류한다.

## 1. 판정 근거 검사

대상: `web_demo.py`의 `JUDGE_SCHEMA`, `_judge_prompt`, `_evaluate_case`, `_deterministic`.

- 기존 `evidence_event_ids`를 유지하고 사건과 관측의 ID를 유효 참조로 인정한다. 출력 파일 참조 필드를 추가하되 실제 `file_changes` 안의 경로만 허용한다. 경로를 인용했다는 이유만으로 임의 파일을 읽지 않는다.
- 성공·실패 판정에는 실제 앱 관측 근거가 하나 이상 있어야 한다. 전부 무효이면 `not_evaluated`로 남기며 원판정과 거부한 참조를 기록한다. 유효·무효 참조가 섞이면 유효 참조를 보존하고 무효 참조를 별도로 기록한다.
- 실제 입력 파일 내용과 해시는 판정자의 맥락으로 제공한다. 입력 파일 자체를 앱의 성공·실패를 입증하는 참조로 세지 않는다. 사용자 입력을 이해한 것과 앱의 출력을 관측한 것은 구별한다.
- 결정적 검사에는 검사 종류·조건·일치 경로·해시 및 사용한 화면/트리 스냅샷을 연결한다. 파일 부재·변경 없음은 빈 목록만 내놓지 않고 기존 `tree_before/after`를 참조한다. 트리 전체를 기대 결과마다 중복 저장하지 않는다. 중단 사례의 부재를 실패로 보지 않는 기존 규칙을 유지한다.
- 관측의 새 전역 ID 체계는 만들지 않는다. 현재 `_screen_evidence`는 기존 ID를 사용하며 동일 ID에 여러 관측이 있을 수 있다. 참조는 그 관측 묶음을 가리키므로 순서와 모든 해당 관측을 보존한다. 이를 단일 시점이나 고유 관측으로 설명하지 않는다. 003의 고유 ID 표현은 신규 구현 요구로 채택하지 않는다.
- 참조가 실제 기록에 연결된다는 검증이며 의미상 정답을 보증하지 않는다. 버튼 조작 성공만으로 업무 결과 성공을 인정하지 않는 판정 지침을 유지한다.

완료 기준: 가짜 참조만 있는 성공/실패, 다른 사례의 참조, 존재하지 않는 출력 경로, 입력 파일만 인용한 성공을 차단한다. 사건 없는 초기 화면·계획 중단 관측과 정당한 파일 검사 근거는 유지한다. 파일 부재·변경 없음과 중단 사례 처리를 확인한다.

## 2. 제공 버전 검사

대상: `company_app.company_features`, `cli._serve_company`. 검증 함수는 기존 `agent_harness._validate_bound_artifact`를 재사용한다.

- `company_features`가 manifest를 읽기 전에 bound `candidate_path`·`candidate_sha256`를 기존 함수로 검사한다. 함수 내부 지연 import로 시작하며, 이 변경만을 위해 새 공통 모듈을 만들지 않는다.
- `_serve_company`의 중복 기능 순회 코드를 `company_features` 호출로 대체한다. 최종 앱 기동 점검과 사용자 제공이 같은 선택/검증을 사용한다.
- 해시 불일치·누락·잘못된 경로 등은 실제 이유를 남기고 해당 기능을 제외한다. 검증을 통과한 다른 기능은 제공하며 전부 제외되면 기존 실행 불가 처리를 유지한다.
- 파일 내용 검사와 상태 재개는 기존 `copy_bundle`·`_open_workspace`를 사용한다. 전체 구현 이력·영수증 검증을 serve 경로에 추가하지 않는다.
- 부분 재현·미평가를 이유로 제공을 차단하지 않는다. 앱 메뉴에 평가 상태 카드를 추가하지 않는다. 파일 동일성이 외부 모델·환경·사용자 상태·출력 동일성까지 보증한다고 하지 않는다.

완료 기준: 묶인 뒤 manifest와 파일을 함께 바꾸더라도 새 상태 디렉터리로 검증을 우회하지 못한다. 정상 기능은 계속 제공되고 제외 사유가 남는다. 정상 부분 재현·미평가 구현을 제공할 수 있다.

## 3. 입력 파일 고정과 재개

대상: `freeze_demo_plan`, `validate_demo_plan`, `run_web_demo`, `_run_case`, `web_checkpoint`.

1. 새 계획을 고정할 때 모든 업로드의 내용 해시를 계획에 넣는다. 실행 전에 원본 파일의 내용과 대조한다.
2. 실제로 올릴 최종 바이트를 `cases/<case-id>/inputs/`에 저장한다. 고정 입력이면 원본 바이트, 변형 입력이면 변형을 마친 바이트다. 출처 해시·사용 파일 해시·상대 경로를 기록하고 체크포인트를 마친 뒤 앱을 실행한다.
3. `_run_case`는 이 입력 디렉터리의 파일만 올린다. 기존 `cases/` 파일 해시 검증을 재사용한다. 파일 경로의 허용 범위와 심볼릭 링크도 기존 검사와 일관되게 다룬다.
4. 재개·`input_cases_from` 비교는 실제 저장한 파일을 복사해 해시를 확인한다. 새 관측이 필요한 실행에는 입력만 복사하고 과거 작업 공간·화면·판정을 가져오지 않는다. 기존 조건을 모두 만족하는 완료 사례의 근거 재사용 정책은 유지한다.
5. 앱 실행 전 중단된 사례도 이미 확정한 입력을 그대로 이어 쓴다. 확정된 입력 파일이 없거나 해시가 다르면 오류이며 재생성하지 않는다.

**생성 도중 중단의 경계:** 유효 치환 값이 저장됐다면 그 값을 사용해 아직 확정되지 않은 파일 작성만 마친다. 유효 값 자체를 얻기 전 제공자 중단이 났다면, 재개 시 생성 시도를 기록해 이어갈 수 있다. 같은 seed가 같은 바이트를 보장한다고 하지 않는다. 검증에서 탈락한 값을 통과할 때까지 다시 뽑지 않고 해당 사례를 미평가로 남긴다. 이미 확정·시험한 입력의 재생성은 금지한다.

**과거 기록:** 해시 없는 legacy 결과의 읽기·기존 결과 검증은 유지한다. 해시 없는 업로드 계획으로 새로운 엄격한 평가·재개·비교를 시작하지 않는다. 새 시도가 필요하면 구현 전에 새 계획·입력을 고정한다. 기존 계획/결과에 해시를 소급해 붙이지 않는다. 업로드 없는 legacy 계획에는 이 제한을 적용하지 않는다. 신규 실행 검증과 과거 결과 읽기 경로를 혼동하지 않는다.

완료 기준: 동결 뒤 원본 변조, 저장 입력 누락·변조, 재개/비교 시 입력 변경을 차단한다. 앱 시작 전 중단된 사례도 같은 저장 바이트를 사용한다. 새 평가기·설정으로 다시 관측하더라도 입력은 같고 과거 판정·앱 상태를 복사하지 않는다.

## 4. 업로드 변형 시험

기존 `INSTANCE_SCHEMA`와 값 생성 호출을 재사용한다. 최초 지원 범위는 20KB 이하 UTF-8 TXT/CSV로 닫는다. 이는 시험 자료 생성기의 범위이며 기업 기능이나 앱 입력 지원 범위를 줄이는 조건이 아니다.

- 업로드별 `vary: true`를 구현 전 계획에 명시한 파일만 바꾼다. 그 외 파일은 고정 입력으로 사용한다.
- vary 업로드 사례에서는 생성기가 만든 자유로운 goal/steps/facts 문장을 쓰지 않는다. 검증된 `replacements`를 동결한 원문·질문·사실·기대 문구·검사값·파일에 한 번에 적용한다. 업로드 변형이 없는 기존 variation 동작은 유지한다.
- 중복·겹치는 치환 키, 의도하지 않은 부분 값 치환, 무변경을 거부한다. CSV는 `csv` 모듈로 파싱/저장하고 셀 값에 적용한다. 헤더·행 수·열 수와 필요한 숫자 유형을 유지한다. 파일과 질문·검사값이 같은 치환 계약을 사용했는지 확인한다.
- 업로드 변형 사례의 기대 결과에는 입력과의 관계를 동결한다: `literal`(명시 값 대응), `derived`(계산되는 값), `none`(입력과 무관). 처음에는 명시 값 대응을 검증할 수 있는 사례부터 완성한다.
- 파생값을 LLM이 다시 계산한 것만으로 정확한 계산 검증을 완료했다고 하지 않는다. 첫 변형 범위에서 `derived` 조건은 기준을 보존한 채 미평가로 남긴다. 실제 계획에서 필요가 확인되면 작은 결정적 계산 지원을 추가한다. 그 조건이나 해당 업무를 삭제해 통과시키지 않는다.
- 판정자에게 실제 사용한 TXT/CSV 내용과 해시를 제공한다. 이를 앱 출력 근거와 함께 판단하도록 한다.
- 변형을 요구했지만 비지원 형식·크기 초과·잘못된 인코딩·무변경·구조 오류·일관성 오류가 있으면 사유를 남기고 해당 변형 시험을 미실행/미평가로 처리한다. 원본 파일로 대신 실행하거나 통과할 때까지 다시 뽑지 않는다. 이를 기업 기술 장벽이나 구현 제외 사유로 자동 해석하지 않는다.

완료 기준: 지원되는 새 TXT/CSV가 질문·검사값과 일관되게 생성되고 기존 웹 업로드부터 업무 결과까지 실행된다. 파생값·비지원·오류 처리가 정해진 범위를 넘는 성공으로 집계되지 않는다. 재개와 비교가 보존된 최종 입력을 쓴다.

## 변경 순서·검증·재사용 범위

1 → 2 → 3 → 4 순서로 구현한다. 1·2는 첫 결함 수정 묶음, 3·4는 입력 보존과 기능 확장 묶음이다. 각 단위는 관련 회귀 테스트를 수행하고 통합 완료 시 저장소 전체 테스트, `git diff --check`, 변경 파일 검토를 수행한다. 이것은 향후 구현 완료 기준이며 이번에 수행한 검증이 아니다.

helper는 우선 현재 책임을 가진 파일 안에 둔다. 별도 모듈로 분리한다면 그 모듈을 `evaluator_version`의 해시 대상에도 포함하고 버전 변경 검증을 추가한다. 수정 전 결과는 다시 쓰지 않는다.

변형 계약에 필요한 조사 작성 지침과 필드 설명은 구현 시 함께 보완한다. 새 제외 사유 플랫폼이나 질문 생성기를 만들지 않는다. 기존 `excluded_parts`·`alternatives`·`needs`의 실제 판단 재검토는 이 코드 변경과 별도이며, 이미 완료한 Delphi를 자동 재실행하지 않는다.

기업 앱 셸, 브라우저 테스터의 기본 반복, 사용자 체험 공간 분리, 개발 로그, 누적 모델 호출 비용과 조사/개발 사용량 집계는 재사용한다. 입력 변형의 모델 호출도 기존 영수증 경로로 계측한다. 앱 내부 평가 화면·보고서 서술 개선·질문 생성은 범위 밖이다.

## 토론에서 바뀐 안과 검증 범위

Claude의 최초 제안 중 원본 fallback, 앱 평가 표시, 재개 시 파일 재생성을 기각했고 재검토에서도 동의했다. 단순 순차 치환과 LLM 파생값 계산은 좁힌 변형 계약으로 대체했다. 입력 파일 참조만으로 성공할 수 있는 공백도 제거했다.

양측과 진행자는 관련 코드·기존 기록을 읽었다. 이번에는 테스트·회사 평가·앱 실행·제품 코드 변경을 수행하지 않았다. 이전 토론의 테스트 통과 기록을 이번 검증으로 합산하지 않는다. 문서 작성과 `git diff --check` 및 작업 트리 목록 확인만 수행했다. 구현 위험은 제안한 회귀 테스트와 새 별도 시험에서 확인해야 한다.

## 종료 직전 작업 트리 변화 확인

진행자가 마지막 파일 목록을 확인하는 동안 `tests/test_judge_evidence.py`, `tests/test_pipeline_efficiency.py`와 `web_demo.py`의 관측 전달 관련 추가 변경을 발견했다. 현재 읽은 코드에는 관측 순서/인덱스와 페이지 변화 복원, 텍스트 출력 전체 내용 전달을 보완하는 내용이 있다. 이 토론에서 작성하거나 테스트한 변경은 아니며 수정·되돌리지 않았다. 구현 시 해당 최신 변경을 재사용하고 기존 관측 전달 개선을 덮어쓰지 않는다. 다시 읽은 `_evaluate_case`에는 무효 참조를 지워도 원판정을 유지하는 처리가 여전히 있어 1번 참조 검증 변경은 필요하다. 새 파일의 테스트 통과 여부는 이번에 확인하지 않았다.
