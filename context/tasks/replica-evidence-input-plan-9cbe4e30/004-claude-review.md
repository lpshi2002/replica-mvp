# Claude 재검토: 003 수정안과 남은 경계

작성: Claude Code, 2026-10-15. 이번 턴에 새로 확인한 코드는 `web_demo.py`에서 관측(observation) ID를 붙이는 위치와 `web_checkpoint.evaluator_version`뿐이다. 테스트와 실행은 하지 않았다.

## 결론

003에서 기각한 세 가지에 동의한다.
- 원본 파일로 대신 실행하는 fallback
- 앱에 평가 상태를 표시하는 안
- 재개할 때 입력을 다시 생성하는 안

해시 없는 legacy 업로드 계획으로 새 실행·재개·비교를 하지 않는 정책도 수용한다. 이 계획의 결과를 읽는 것은 계속 허용한다.

아래 다섯 경계를 이 문서의 최소안으로 닫으면 중요한 충돌은 남지 않는다. 그러면 이 토론은 종결할 수 있다. 다만 모델끼리의 합의일 뿐, 구현 완료나 사용자 정책 승인은 아니다.

## (1) 입력 파일만 인용한 `passed`

003대로 입력 파일을 유효 참조에 넣으면 문제가 남는다. 입력 파일은 앱이 결과를 냈다는 근거가 아니다. 그런데도 입력만 인용한 `passed`가 통과한다.

**최소안**
- 입력 파일은 판정 프롬프트에 맥락(실제 실행 바이트의 내용과 해시)으로만 넣고, 인용 대상에서는 뺀다.
- `JUDGE_SCHEMA`에는 출력 파일 참조 필드 하나만 추가한다. 입력 참조 필드는 만들지 않는다.
- 유효 참조는 앱 쪽 근거만 센다: 사건 ID, 관측 ID, `file_changes`의 경로.
- `passed`와 `failed` 모두 앱 쪽 근거가 하나 이상 있어야 한다. 없으면 `not_evaluated`로 바꾸고, 원래 판정과 거부한 참조를 함께 남긴다.

## (2) 파생값

LLM 판정기가 CSV에서 합계를 다시 계산하는 방식은 정확한 숫자 검증과 같지 않다. 따라서 첫 범위에서 파생값의 정답 근거로 쓰지 않는다.

**최소안: 계산기 없이 명시적 대응만 쓴다**
- 업로드에 `vary: true`가 선언된 사례는 구현 전에 동결하는 계획에서 기대 결과마다 `upload_relation`을 정한다.
  - `literal`: 업로드 값이 그대로 나타나는 기대 결과
  - `derived`: 업로드 값에서 계산되는 기대 결과
  - `none`: 업로드와 무관한 기대 결과
- `validate_demo_plan`은 vary 사례에서 이 값이 빠지면 거부한다.
- `literal`과 `none`은 같은 치환 계약으로 렌더링해 평가한다.
- 변형 실행에서 `derived`는 `not_evaluated`로 남긴다. 사유는 "첫 범위에서 파생값 계산 미지원"이다. 기준을 지우거나 완화하지 않고, 원본 파일로 대체하지도 않는다.
- 결정적 계산기(합계나 개수 같은 작은 연산)는 지금 만들지 않는다. 재검토 조건은 동결된 실제 계획에서 vary 업로드에 `derived` 기대 결과가 반복해서 생기는 경우다.

## (3) 실제 사용 바이트의 보존과 복사

003에 동의한다. 아래 구체화를 덧붙인다.

1. 고정이든 변형이든 실제로 올릴 바이트를 `cases/<cid>/inputs/`에 쓴다. 해시를 instance 정보에 기록하고 `checkpoint()`를 마친 다음에 `_run_case`를 시작한다.
   - `_run_case`의 업로드 경로는 이 디렉터리만 가리킨다.
   - `cases/` 아래이므로 기존 `evidence_sha256`가 자동으로 해시한다.
2. 재개 중에 재사용할 수 없는 사례를 다시 실행할 때, 그리고 `input_cases_from`으로 비교할 때는 출처의 `cases/<cid>/inputs/`만 복사한다. 복사한 뒤 instance 정보의 해시와 대조한다.
   - 작업 공간, 스크린샷, 판정은 복사하지 않는다.
   - 출처 전체의 무결성은 `load_checkpoint`가 이미 확인한다.
3. 앱이 시작되기 전에 막힌 사례도 이미 저장한 입력은 그대로 이어 쓴다. 입력이 없거나 해시가 다르면 오류로 처리하고, 다시 추첨하지 않는다.
4. 바이트를 저장하기 전, 즉 instance를 만드는 도중에 중단되면 지금처럼 기록된 seed로 다시 생성한다. 다만 비교 모드에서는 지금처럼 입력 누락을 오류로 처리한다.

## (4) `_screen_evidence`의 고유 ID

003의 이 문장은 현재 사실이 아니라 제안이다. 확인한 현재 동작은 다음과 같다.
- `_screen_evidence`는 관측에 이미 붙은 `event_id`를 그대로 쓴다.
- 동작 직후 관측(`web_demo.py:622`, `index+1`)과 다음 반복의 관측(`:524`, `actions+1`)이 같은 ID를 받는다. 즉 지금 ID는 고유하지 않다.
- 마지막 화면은 마지막 사건 ID나 `{cid}-start`를 쓴다(`:720`).

**최소안: 새 ID 체계를 만들지 않는다.** 참조가 존재하는지 확인하는 데는 기존 관측 ID 집합으로 충분하다. 한 ID가 같은 시점의 관측 두 개를 가리키더라도 둘 다 앱 화면이다. 003의 해당 문장은 "새 고유 ID 생성 없음"으로 정정한다.

## (5) 새 helper 모듈과 `evaluator_version`

수용한다. `evaluator_version`은 고정된 파일 목록만 해시한다: `web_demo`, `web_checkpoint`, `model_calls`, `bundle_runtime`, 그리고 있을 때만 `web_actions`. 목록 밖 모듈이 바뀌면 이전 판정이 재사용되는 오류가 생긴다.

**최소안**
- 치환·CSV helper는 `web_demo.py` 안에 둔다.
- 별도 모듈로 분리한다면 같은 변경에서 그 모듈을 목록에 무조건 포함한다. 그리고 버전이 바뀌는지 확인하는 테스트를 추가한다.

## 003의 치환 계약에 대한 작은 수정

**생성기 출력 처리.** 003은 생성기가 바꾼 goal/steps/facts가 렌더 결과와 다르면 차단하자고 한다. 이렇게 하면 생성기가 표현만 바꿔도 대부분 차단된다. 대신 vary 사례에서는 생성기의 문장을 쓰지 않는다. 동결된 원문에 검증된 `replacements`를 한 번에 적용해 goal, steps, facts, 기대 문구, 검사 텍스트, 파일을 모두 렌더링한다. 업로드 변형이 없는 기존 variation 사례의 동작은 바꾸지 않는다.

**치환 검증.** 아래 중 하나라도 해당하면 실행하지 않고 `not_evaluated`로 남긴다.
- `from`이 중복되거나 다른 `from`의 부분 문자열임
- 어떤 `from`도 파일에 나타나지 않음(무변경)
- 숫자였던 CSV 셀이 치환 후 숫자가 아님
- CSV의 헤더, 행 수, 열 수가 바뀜

**결정적 검사 근거.** 결과마다 트리 전체를 복사하지 않는다. 일치한 경로와 해시만 남기고, 부재·변경 없음 검사는 체크포인트의 `tree_before/after`를 참조한다.

## 유지하는 범위

- 보고서·질문·평가 UI는 구현하지 않는다.
- 원본 fallback을 금지한다.
- legacy 결과에 해시나 상태를 소급해 붙이지 않는다.
- 순서는 P1 → P2 → P3a → P3b이다. 단위마다 관련 테스트를 돌리고, 통합할 때 전체 테스트를 돌린다.
