# 001 Claude 제안: 1차·2차 분리 유지, 2차를 조사와 설계로 분리, 제외 결정에 대안 조사 기록 의무화

이 제안은 진행자(Claude Code) 대화에서 사용자에게 이미 제시한 판단을 정리한 것이다. 사용자는 아직 확정하지 않았다.

## Q1. 1차·2차 분리는 유지한다

- 근거(사실): Delphi 1차에서 다섯 범위 작업자의 후보가 최종 3개 claim으로 합쳐졌고, claim-001에만 후보 7개가 병합됐다(`work/delphi-ai-v2/research.json`의 `merged_from`). 16건이 제외됐다. 1차 없이 바로 심층 조사했다면 같은 워크플로를 여러 번 조사했을 것이다(추론).
- 회사 결과(`company-claims.json`)는 1차가 확정한 claim 목록을 분모로 쓴다. 목록 확정 후에야 claim별 병렬 작업이 가능하다.
- 분리 이유는 단위 차이(회사 전체 vs claim 하나)다. Q2의 분리 이유(역할 차이)와 다르다.
- 약점(사실): 1차→2차 인계에서 정보가 빠진다. 1차는 경계 조건을 기록하지 않아 2차가 같은 출처를 다시 연다. claim별 검색 이름 목록이 없어 진행자가 URL 조각에서 뽑았고 `overview` 같은 잡음이 섞였다. 1차 `routing`은 19개 중 17개가 같아 쓸 수 없다(SKILL.md 334~341행).
- 보완: 1차가 이미 읽은 출처에서 조건 문구와 claim별 고유명사를 함께 저장한다. 단계 통합은 하지 않는다.
- 미측정: v2에 `agent_sessions`가 없어 1차 비용은 모른다. "비용 대비 효과"는 중복 제거 건수 근거일 뿐이다.

## Q2. 2차를 조사와 설계로 나눈다

- 현재 2차 작업자 한 명이 조사(근거·경계·6개 bucket), 설계(시나리오·단계별 구현/제외), 시험(JSON tests, 봉인 평가 데이터, demo_plan, 업로드 합성)을 모두 맡는다(`agents/replica-second-pass.md`).
- 사용자 지적대로 "추정 아키텍처"는 결국 공개 주장으로부터 우리가 어떻게 만들지의 설계도이며 Ralph의 Architecture와 같은 산출물이다. 구성요소마다 기업이 공개한 것인지 우리가 고른 것인지만 표시한다.
- 제안 구조: 1차(목록) → 2차 조사(claim별 자료와 단계별 경로 후보) → 설계(단계별 아키텍처, 경로 선택, 제외 결정, 계약, 시연 계획·시험) → 구현(단일 구현자) → 시험(웹 시연·코드 검사).
- 설계를 구현자에게 맡기지 않는 이유: 구현자가 범위를 정하면 어려운 단계를 빼서 통과하려는 유인이 생긴다. 시험을 구현 전 고정하는 것과 같은 이유다.
- 비용 최소화안: 조각 파일 형식은 유지하고 두 작업자가 나눠 채운다(조사 작업자: findings·readiness, 설계 작업자: contract·step별 아키텍처). 파서·하네스 변경을 줄인다. 대가: claim당 에이전트 1개 추가, 인계 손실 위험.
- 로드맵 단계 1(`docs/pass2-interaction-redesign.md`)과 함께 정리해야 한다.

## Q3. 2차가 경로를 못 찾는 원인 (사례: Delphi claim-001 step 4)

사실: claim-001 작업자는 `oss_papers_patents`(depth=deep)에서 검색용 OSS만 찾았고 음성 복제·말하는 얼굴 OSS는 검색하지 않았다(조각에 관련 이름 없음). 제외 사유는 "창작자 샘플 없음, Tavus·ElevenLabs 유료 키 없음, 로컬 CLI가 음성·영상 합성 불가"였다. 같은 작업자가 텍스트 입력은 가상 코치 자료로 합성 대체했다.

원인 후보(하나로 단정하지 않는다):
1. 지침 문구: `replica-second-pass.md` 136~141행 "선택된 런타임이 못 하는 음성·영상 의존성은 명시적으로 남겨라"가 "런타임이 못 하면 뺀다"로 읽힐 수 있다(추론).
2. 제외 검증 부재: `excluded`는 사유 문자열만 있으면 통과한다. 찾아본 대안을 요구하지 않는다(`second_pass.py`의 step_coverage 검사).
3. 깊이 할당 단위: `bucket_depth`는 bucket 단위다. 단계별로 경로를 찾았는지 강제하지 않아 한 bucket을 한 단계(검색) 위주로 채워도 `filled`가 된다.
4. 역할 과다: 시험 9개, 시연 5개, 업로드 합성까지 한 작업자가 했다. 인과는 사례 하나로 단정할 수 없다.
5. 검색어 구성: brief의 `search_names`는 회사 고유명 중심이다. "open source voice cloning" 같은 기능 일반 검색어는 brief에 없다.
6. "Do not try to win" 규칙이 대체 경로 탐색을 소극적으로 만들 수 있다(추론, 약함).

대책:
- 지침: 런타임이 못 한다는 것만으로는 제외 근거가 아니다. 단계마다 OSS·API·합성 대체 경로를 찾고, 샘플이 없으면 합성 대체를 쓴다.
- 제외 기록: `excluded`·`external_dependency`에 찾아본 대안과 막힌 이유, 하려면 필요한 것(경로·자원·비용)을 필수로 하고 파서가 검사한다.
- 구조: Q2의 설계 단계가 단계별 경로를 결정하므로 단계 누락이 드러난다.

## Q4. 설계도 + 실측 상태 보고서

- 설계 단계가 단계별 설계도(구성요소, 공개/추론 표시, 택한 경로, 제외 시 대안·막힌 이유·필요한 것)를 만든다.
- 구현 후 상태는 새 판단 없이 기존 기록에서 채운다: 시연 사례별 결과·`covers_steps`, `uncovered_steps`, `excluded_steps`, 코드 검사.
- 상태는 네 가지: 시연으로 확인 / 구현했지만 시연 미통과 / 설계만 / 불가(이유). 재현 판정에는 실측만 쓴다. "설계상 가능"을 결과로 세지 않는다.
- 사용자 요구대로 못 한 것과 이유를 보고서에 표로 남긴다.
