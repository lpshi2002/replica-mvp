# 결론: 1차·2차 분리 유지, 2차는 작업자를 늘리기 전에 순서·기록·검증부터 보강

종료 사유: resolved. 제안 001(Claude, 진행자 세션 작성)과 검토 002(Codex)를 거쳤고, 진행자가 검토 지적을 대부분 수용했다. 모델 간 합의는 사용자 승인이 아니다. 아래는 권고이며 아무것도 반영하지 않았다.

## 합의한 권고

1. **1차·2차 분리 유지.** 이유: 회사 전체 주장 정규화와 claim별 재현 준비는 단위·문맥이 다르다. Delphi에서 후보가 3개 claim으로 합쳐졌고(claim-001에 7개 병합) 16건이 제외됐다. 더 중요한 이유는 구현 용이성이 주장 발견의 선정 기준으로 들어가지 않게 해 어려운 기능도 분모에 남기는 것이다. 보완: 1차가 이미 읽은 자료의 고유명사·조건 문구를 보존한다(별도 심층 조사 없이). 이것으로 2차의 경계 확인을 대신하지 않는다.
   - 사용자가 말한 논문은 논문 모음 5절의 VeriScore가 가장 유력하다(확정은 아님). 주장 추출과 검증의 구분, 조건을 잃지 않는 인계를 지지하지만 작업자 수 결정의 직접 근거는 아니다. 같은 절 AVeriTeC(주장 → 질문 → 근거)는 2차의 미해결 항목을 검색 질문으로 만드는 데 더 가깝다.
2. **2차: 조사와 설계의 책임은 구분하되, 지금은 같은 작업자 안에서 순서로 나눈다.** 전체 워크플로·입출력 변형 보존 → 단계별 구현 후보와 조건 조사 → 선택·제외 이유와 고객이 잃는 기능 기록 → 계약·시연 계획 작성과 범위 일관성 검증. 작업자 추가는 이 구조에서도 누락이 반복될 때 같은 자료·모델·예산으로 비교한 뒤 정한다. 분리한다면 같은 파일을 둘이 채우는 방식보다 조사·설계 파일을 나누고 기존 조각으로 조립하는 방식이 낫다(원조사 보존, 책임 추적).
   - 부담의 일부는 역할 수보다 과도기 계약 중복이다: 웹 경로는 `demo_plan`으로 평가하는데 파서는 JSON 시험을 계속 요구한다(`src/replica_mvp/second_pass.py:497`). 이 중복 정리가 먼저다.
3. **2차가 경로를 못 찾는 원인은 여럿이며, 확인된 것과 가설을 나눈다.**
   - 확인: 제외 사유의 타당성·대안 조사 근거를 검사하지 않음(Q3-2), `filled`가 모든 단계의 대안 탐색을 보장하지 않음(Q3-3), brief의 요약 주장이 전체 workflow보다 좁음(Q3-7), 원제품 의존성(Tavus·ElevenLabs·샘플)을 대체 구현의 필수 조건으로 일반화함(Q3-8), **큰 단계 안의 하위 기능 제외가 상태에 드러나지 않음(Q3-9: step 1이 `implemented`인데 음성·영상·URL·피드 수집은 `out_of_scope`로만 빠져 `whole_workflow`로 판정)**, 탐색 실패를 진단할 기록 부족(Q3-11).
   - 부분 확인: 기능 일반 검색어가 brief에 없음(Q3-5, 다만 `voice`·`Tavus`는 있음). 출처 이동·접근 제한(Q3-10).
   - 인과 미확인: 런타임 지침 문구(Q3-1), 역할 과다(Q3-4), "Do not try to win"(Q3-6).
   - 사례 서술 정정: claim-001 작업자가 "검색하지 않았다"가 아니라 "음성·영상 대안 조사 근거가 산출물에 없다"(검색 로그 미확인).
   - 대책: 제외·외부 의존 단계에 단계 성격에 맞는 후보, 확인 근거, 선택·기각 이유, 남은 제약과 필요한 자원을 기록하고 검증한다(모든 단계에 OSS·API·합성을 기계적으로 요구하지 않음). 주요 하위 동작·입력 변형을 단계에 연결해 부분 구현을 표시한다. "로컬 CLI의 한계는 전체 앱의 한계가 아니다"를 지침에 명시한다. 합성 자료는 조건부: 입력 처리·일반 동작은 시험하되 특정 인물 음성 유사도 같은 것은 미평가로 남긴다. `external_dependency`는 실제 사용하는 서비스에만 쓴다.
4. **보고서의 설계도는 계획 축과 실행 관측 축을 나눈다.** 계획: 직접 구현 예정 / 외부 서비스 사용 / 제외 / 미확인과 이유·대안·필요 자원, 그리고 구성요소의 출처 구분(원기업 공개 / 우리 선택 / 미확인). 관측: 제출 여부, 코드 검사, 통과·실패·미평가, 중단 사유. "불가" 같은 단일 상태는 본질적 불가로 읽히므로 쓰지 않는다. 설계상 경로는 실측 성공에 넣지 않는다. 현재 `uncovered_steps`는 계획 기준이므로 단계별 실측 표시는 단계에 연결된 관측·기대 결과가 있을 때만 한다. 사례 전체 실패를 포함 단계 전부의 실패로 전파하지 않는다. 설계도는 2차의 계약 작성 구간에서 만들고 결과 보고 단계가 평가 기록을 연결한다.

## 기각·수정된 대안
- 지금 즉시 설계 작업자 추가: 효과 미측정, 인계 비용·판정 덮어쓰기 위험 → 보류.
- 같은 조각을 두 작업자가 채우는 분리: 책임 경계가 엇갈림(`ready`는 경로·평가 자산이 있어야 하므로 조사자가 먼저 확정하기 어려움) → 비권장.
- 네 가지 단일 상태 보고: 미평가·부분 통과·실행 중단 구분 불가 → 두 축으로 대체.

## 검증 상태
- Codex: 지침·코드·Delphi v3 조각 읽기, v3 `research.json` 파싱(3개 claim 수용), 메모리 복사본으로 `_step_coverage`가 근거 없는 제외 사유를 받고 단계 상태만 바꾸면 `whole_workflow`가 됨을 확인, VeriScore·AVeriTeC 원문 확인. 전체 테스트·기업 재실행·OSS 실행 가능성·작업자 분리 비교는 하지 않음.
- 진행자: 논문 모음 5절의 VeriScore 행, claim-001의 `out_of_scope`와 step 1 상태를 직접 확인.

## 사용자 결정이 필요한 사항
1. 권고 2·3·4를 지침·파서에 반영할지, 그 순서(과도기 JSON 시험 중복 정리 포함 여부).
2. 작업자 분리 비교 실험을 할지(비용 발생).
3. Delphi claim-001을 보강된 지침으로 다시 돌릴지.
