**최종 권고 순서를 `5·7 → 1a·1b·1c → 4 → 2·3 → 6`으로 수정한다.** 1c와 4를 앞당기자는 002의 의견을 수용한다. 다만 I1의 **“facts를 모두 사용했으면 입력 소진, 그 외 미달은 실패”라는 판정 규칙은 수정이 필요하다.** 실행 기록을 요구하는 취지는 맞지만, 전체 사용 여부만으로 시험 입력 부족을 입증할 수는 없다.

**기존 기록을 이용한 대조는 가능하지만, 자연어 fact의 사용을 문자열 검사만으로 확정할 수는 없다.** 실제 v4 기록에서도 확인했다. claim-003의 오타 사례에서 첫 제출은 입력 행동 6개에 원래 fact 문장 6개 중 5개가 그대로 등장했고, 두 번째 제출은 입력 행동 3개에 원문 문장이 하나도 그대로 등장하지 않았다. 두 번째 입력에는 인칭과 표현을 바꾼 같은 소재가 들어 있다. 이는 사용률 측정이 아니라 **완전 문자열 일치가 사실 사용 여부를 대신하지 못한다는 확인**이다. 근거는 두 제출의 `demo-result.json`과 [실제 입력 사건 기록](/Users/cho/replica-mvp/work/delphi-ai-v4/single-harness-2026-10-09/final-results/runs/claim-003/web-attempt-002-a80003d5034d/events.jsonl)이다.

더 중요한 논리적 문제가 있다. 충분한 자료를 모두 제출했는데 앱이 처리하지 못했다면 실제 실패다. **자료를 다 썼다는 것과 자료가 부족했다는 것은 다르다.** 반대로 `facts`가 비어 있고 업로드 파일에 자료가 있는 사례도 있으므로 `all(facts_used)` 같은 조건은 범용 기준이 될 수 없다.

수정 권고는 다음과 같다.

1. **예방이 먼저다.** 2차가 공개 규칙을 지키면서 도달 가능한 입력과 짝 시험을 고정한다. 1a는 이 설계가 실행에서 무너진 경우의 안전망이다. 이는 [현재 2차 지침](/Users/cho/replica-mvp/skills/replica-research/agents/replica-second-pass.md:361)과 일치한다.
2. 입력 소진을 주장하는 판정에는 **실행 입력의 자료 구간 → 실제 입력 사건 → 제출 및 이후 관측**의 대응 근거를 요구한다. 사용하지 않은 자료와 대응 여부를 확인하지 못한 자료도 구분한다.
3. 코드는 참조한 자료·이벤트의 존재, 실제 실행 여부, 오류·취소 여부를 확인한다. 시험자의 `reason`이나 사용 완료 선언만으로 인정하지 않는다. 단순 입력창 채우기도 제출 완료로 세지 않는다.
4. 판정자는 그 근거로 **공개 규칙상 필요한 자료가 시험 입력에 부족했는지**, 또는 **충분한 자료를 앱이 처리하지 못했는지**를 구분한다. 이 의미 판단까지 결정적 검사로 해결했다고 주장하지 않는다.

적용 결과는 다음처럼 제한한다.

| 관측 | 처리 |
|---|---|
| 시험 입력 부족이 구체적인 자료·사건·규칙으로 뒷받침됨 | 영향을 받는 기대 결과만 미평가 |
| 충분한 유효 입력을 제공했지만 고객 결과 조건에 미달 | 실패. 모든 facts를 사용했어도 동일 |
| 입력 소진 근거가 부족함 | 입력 소진 예외를 적용하지 않고 기존 증거 판정 유지 |
| 실행 예산 종료·관측 불가 | 기존 미평가 규칙 유지. 소진 증거가 없다는 이유로 실패로 바꾸지 않음 |

최소 구현은 기존 판정 응답에 이 대응 근거를 구조화하고 검증하는 것이다. 시험자에게 fact 사용 표시를 추가하더라도 보조 단서로만 쓴다. **범용 ‘사실 소비 추적기’를 새로 만드는 것은 보류한다.**

재시도 피드백 수정은 그대로 유지한다. 입력 부족만 남았으면 구현 수정 재시도를 요구하지 않고, 다른 실패가 함께 있으면 그 실패만 수정 대상으로 전달한다. 실행값·화면 원문을 구현자에게 넘기지 않는 기존 경계도 유지한다.

**I2 — 변경 파일 차이와 크기 상한을 수용한다. 단, 잘린 검사를 통과로 처리하면 안 된다.**

최종 소스와 공개 규칙은 유지하고, 추가 이력은 **직전 제출 대비 변경·추가·삭제된 파일의 차이와 이번 개발 기록**으로 제한한다. 모든 과거 제출 전문을 보내지 않는다.

최소 상한은 기존 [`_REVIEW_FILE_LIMIT = 200_000`](/Users/cho/replica-mvp/src/replica_mvp/web_demo.py:103)을 출발점으로 삼는다. 파일별 상한뿐 아니라 **추가 이력 전체에도 상한**을 둬야 작은 변경 파일이 많을 때 비용이 계속 커지는 것을 막을 수 있다. 초기에는 추가 이력 전체를 UTF-8 기준 200,000바이트로 제한하는 안을 권고한다. 이는 성능이 검증된 최적값이 아니라 구현 기본값이다.

상한을 넘으면 누락 파일·구간과 크기를 기록한다. 관련 로직을 확인하지 못했다면 코드 검사를 통과시키지 않는다. 이미 확인한 명백한 위반은 실패로 남길 수 있다. 구현자에게 차이를 요약하게 해 누락을 대신하지 않는다.

`evaluator_version`에 `web_evaluation.py`를 추가하는 의견도 수용한다. 아울러 **실제로 전달한 규칙·이력 문맥의 해시**를 재사용 조건에 연결한다. 코드 버전과 검사 입력은 서로 다른 변경 원인이다.

**I3 — 1c를 작업 1 묶음으로 앞당긴다. 001의 의존 관계를 정정한다.**

근거 없는 `public_rule` 수치를 자동으로 `our_condition`으로 바꿔 통과시키지 않는다는 제한은 유지한다.

**I5 — 음성 내용 검사를 2·3보다 앞당긴다. 기존 선행 조건은 철회한다.**

001이 말한 “근거·기준 구조 정리 후”는 구현상의 필수 의존성이 아니었다. 필요한 것은 다음 세 가지다.

- 실제 UI가 생성·재생한 음성과 그 실행의 답변을 연결한다.
- 받아쓰기 결과를 판정 증거로 전달한다.

현재 `our_condition`·인용 계약과 기존 판정 증거 경로를 확장하면 가능하다. 원문 보존 체계 전체를 기다릴 이유가 없다. 따라서 **1 다음에 4를 진행**한다.

이번 범위는 답변 내용 일치다. 화자 유사도·자연스러움·영상·이미지 검사는 보류한다. 받아쓰기 오류와 실제 음성 오류를 구분하지 못하면 해당 내용 품질을 미평가로 남기며, 기존 실행의 기대 결과를 소급 변경하지 않는다.

작업 2·3은 같은 원문 보존 구조로 처리한다. 원문 대조는 처음부터 차단하고, LLM 요소 검사는 작은 변이 시험으로 확인한 오류 유형부터 차단하는 권고를 유지한다. 이 큰 묶음의 범위 결정 때문에 작업 1·4를 기다리게 하지 않는다.

최종 권고 순서는 다음과 같다. 번호는 실행 우선순위이며, 독립 작업을 반드시 직렬로 처리하라는 뜻은 아니다.
