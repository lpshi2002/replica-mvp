제품 코드 수정·유료 평가·앱 실행 없이 기존 영수증과 CLI 도움말을 읽었다.

## 캐시 비용·경계

Actions attempt-002 `demo-result.json`의 tester receipts를 합산하면 `usage.cache_creation.ephemeral_1h_input_tokens=759313`, `ephemeral_5m_input_tokens=0`이다. 따라서 Claude 리뷰의 "5분 캐시 + Sonnet $3/$15"는 기록과 맞지 않는 가정이다.

현재 공식 https://platform.claude.com/docs/en/models/sonnet-5-5/overview 의 단가는 입력 $2, 출력 $10, 5분 쓰기 $2.50, 1시간 쓰기 $4, 읽기 $0.10 / 백만 토큰이다(2026-10-12 조회). 기록된 CLI 추정액 $3.404307은 입력2·출력10·1h쓰기4·읽기0.20을 적용하면 정확히 맞는다. 공식 읽기0.10으로 다시 환산하면 $3.3673995다. 이는 가격표와 CLI 계산의 차이이며 이번에 기록 총액을 바꾸지 않는다.

1h 쓰기분 $3.037252가 기록 총액에서 약89.2%이므로 쓰기량을 줄일 가치가 있다는 방향은 유효하다. 다만 캐시 비중이 크다는 사실은 고정 본문을 system으로 옮기면 재사용된다는 증명이 아니다. `claude --help`에서 `--append-system-prompt` 지원만 확인했다. 실제 캐시 경계·재사용·TTL을 변경할 수 있는지는 유료 실측하지 않았다. 기존14% 절감 추정은 보류해야 한다.

O6 검토 시 고정 지침/도구 설명과 실행값·화면·외부 문장을 구분하라. 연구에서 넘어온 사실과 앱 화면을 캐시 목적으로 시스템 지시 권한으로 승격하지 않는다. 전체 case를 system으로 옮기는 제안은 그대로 채택할 수 없다. CLI 설정과 세션 경계를 바꾸어 테스트 사이 격리를 깨지 않는다.

## O1 반론과 잠재량 집계

기존 401행동에서 같은 URL의 fill/check/uncheck/select만 묶으면 cap3에서21회, cap5에서22회가 후보다. 마지막 button click까지 포함한 cap5는95회(23.7%)가 후보다. JSON 두 파일에 조건과 그룹을 보존했다. 이는 실제 DOM 안정성·같은 폼 여부나 새 모델의 행동을 검증한 상한이 아니라, 관측된 특정 패턴을 묶을 경우의 잠재 호출 수다. 비용 절감률과도 다르다.

Claude 리뷰의 "관측 재번호를 하지 않으면 ref가 일관된다"는 말은 기존 DOM 노드가 유지될 때만 맞는다. count()==1과 보이는 요소 개수만으로 같은 요소임을 보장하지 못한다(같은 개수로 교체, 같은 ref를 복사, 선택지·레이블 변경). 중간 관측 자체를 생략하면 결과 증거가 사라진다. 번호를 재부여하지 않는 관측과 실제 노드 동일성 확인 등 최소 안전 설계가 필요하다. 최종 click이 결과를 만든 직후에는 반드시 다시 관측하고 재판단해야 한다.

## O3/O4/O5/O7 정정할 범위

- O3: 이력 value 200자 절단은 과거에 입력한 긴 정정문/승인 편집문을 잃는다. 원본 파일 보관만으로 현재 모델이 이를 다시 읽을 수 있는 것은 아니다. 현행 read는 현재 editable field만 읽는다. 무조건 자르지 말고 먼저 중복 키/장황한 이유 축소를 검토한다.
- O4: 작은 상태 검사의 일부 활용은 기존 선택적 check와 정책상 가능하다. JSON-only 실행 경로 제거가 웹 평가의 보조 결정적 검사를 금지한 것은 아니다. 일부 코드 검사는 Judge 호출 수보다 입력량·판정 신뢰성에 이득이 있을 수 있으므로 "모든 조건을 코드화할 사례가 있어야 재검토"는 과도하다. 이번 비용 최적화 우선순위를 낮추는 데는 동의한다.
- O5: guide의 선택 개발 시험과 최종 전체 검증은 이미 있다. 과거 전체 개발 시연이 지침 위반이었다고 결론 내릴 수 없다(당시 코드/지침·수정 범위를 확인하지 않음). 자동 영향 추론 엔진은 만들지 않는다.
- O7: $10.08은 평가기/설정이 바뀐 뒤 관측을 다시 얻은 실행의 총액이지 회피 가능했던 낭비의 실측값이 아니다. 필요한 검증도 포함되므로 통째로 절감 가능 비용으로 빼지 않는다. 정상 실행 중 설정을 고정하되 평가기 버그 수정이 필요하면 버전 변경과 새 근거 수집을 명시한다. A/B에서는 최적화된 평가기 버전이 의도적으로 달라지므로 "같은 평가기"라는 표현 대신 앱·사례·입력·모델·예산을 고정하고 대상 변경만 다르게 한다.

유료 브라우저 확인과 실제 구현은 이번 토론 범위 밖이다. 토론의 미실측 조건을 추가 사용자 승인 항목 여러 개로 바꾸지 말고 다음 구현 작업의 검증 조건으로 정리한다.
