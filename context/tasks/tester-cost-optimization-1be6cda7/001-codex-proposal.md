# 기존 대화의 최적화 제안 구체화 — Codex

이는 진행자가 방금 사용자에게 제시한 제안을 보존한 문서다. 제품 구현·유료 재시험은 하지 않았다. 근거는 brief의 현재 코드와 Delphi 기록이다.

## O1 — 현재 화면에서 가능한 짧은 행동 묶음

현재 `_tester_prompt`는 exactly one action, `TESTER_SCHEMA`는 단일 action/ref/value/reason, `_run_case`는 조작마다 tester 호출을 한다. 첫 변경은 한 화면의 fill/check/uncheck/select와 마지막 submit까지 작은 배열로 받는 것이다. 초안 상한 3~5개는 설계 가정이며 측정 전 고정 정책으로 보지 않는다.

현재 DOM ref는 `_OBSERVE_SCRIPT` 실행 때 재번호가 매겨진다. 따라서 이전 관측의 숫자 ref를 새 관측에서 그대로 사용하면 안 된다. 계획 시점에 관측한 요소의 식별·상태를 확인하고 유일하게 매칭되지 않으면 묶음을 중단한다. 과도한 범용 locator 복구 엔진보다 보수적인 실행 중단을 우선한다.

각 원자 행동의 이벤트 ID·화면·입력·관측 결과는 계속 저장한다. 한 모델 호출 ID가 여러 행동에 연결될 수 있다. URL 이동, 요소 교체·소실, 비동기 결과로 다음 선택이 달라지는 시점, 오류가 나오면 계획의 나머지를 버리고 재관측한다. 새 화면을 추측해 넘어가거나 인터뷰 다음 답변을 미리 고정하지 않는다. 재전송·승인 같은 효과를 자동 반복하지 않는다.

`max_actions_per_case`는 원자 행동 수로 유지한다. 배치 한 번을 행동 하나로 세어 예산과 품질을 부풀리지 않는다. batch/done/give_up, 잘못된 ref, 부분 실패의 기록 규칙은 검토로 좁힐 항목이다.

## O2 — 묶음의 기계적인 사후조건과 대기

`wait_for`와 명시적 check/uncheck는 이미 있다. 새 작업은 O1에서 코드가 각 입력의 값, 체크 상태, 실행 가능 조건을 확인하고 정해진 UI 조건까지 기다린 뒤 진행하게 하는 것이다. 애매한 로딩 상태나 비즈니스 성공을 코드가 임의로 추론하지 않는다.

코드 확인으로 정상 후속 조작이 가능하면 모델에 다시 묻지 않는다. 반면 실패한 submit의 결과가 불명확하면 재클릭하지 않고 상태를 관측해 모델에 돌린다. 내부 데이터 직접 조작·API 호출은 최종 UI 행동을 대체하지 않는다.

## O3 — 문맥 축소는 관측 손실을 만들지 않는 범위

전체 사건 이력·화면 캡처는 보존하고 모델 입력만 줄인다. 현재 recent actions 15개와 화면 text/element/value를 반복 보낸다. 고정 지침과 사례 설명을 안정적인 앞부분에 유지하고, 현재 관측과 진행 상태를 간결하게 제공한다.

처음부터 모든 화면을 delta-only로 바꾸거나 LLM으로 매번 요약하면 오히려 오류·비용이 생길 수 있다. 같은 URL·관측에서 중복 텍스트와 이미 제공한 반복 기록을 줄이는 최소안부터 검증한다. 목표 관련 장문·오류는 `read`로 원문을 읽을 수 있어야 한다. 단계 완료는 테스터의 주장만으로 저장하지 않고 실제 수행 기록에 연결한다. 현재 8,000자 본문·200자 필드 제한을 더 낮추는 것으로 비용을 줄이지 않는다.

## O4 — 결정적 검사와 의미 판정 분리

현재도 `_deterministic`이 있지만 이번 85조건은 전부 Judge를 사용한다. Judge는 이미 사례별로 여러 조건을 한 호출에 묶으므로, 조건 하나를 코드로 바꿔도 Judge 호출이 바로 하나 줄지는 않는다.

새 연구 계획에서 기계적으로 정의되는 조건에 검사 정보를 함께 작성하고, 구현과 독립적으로 고정한다. UI에 나타나야 하는 결과와 내부 저장 사실을 구분한다. 단순 파일 존재·문구 발견으로 실제 전송·권한 제한·업무 완료를 대체하지 않는다. 새 검사에서 false pass를 만들지 않는 검증이 선행되어야 한다.

현재 존재하는 검사만으로 개수·JSON 상태·동적 ID 등까지 보장할 수 있는지, 앱 저장 구조를 구현 전에 모르는 문제를 어떻게 단순히 해결할지는 미해결이다. 결정적 검사 전체를 새 DSL/플러그인 엔진으로 키우기보다 가능한 UI 속성 몇 개만 추가하는 안을 검토한다. 기존 동결 기대 결과는 이번 비용 논의로 수정하지 않는다.

## O5 — 개발 선택 시험과 최종 전체 검증 경계

선택 사례 실행과 체크포인트는 이미 있다. 개발 중은 구현자가 관련 사례부터 확인하고 전체 AI 시연은 제출 준비가 됐을 때 사용한다. 작은 수정마다 전체 브라우저 평가를 기본으로 하는 지침·호출 경로가 남았는지 먼저 확인한다. 이미 지침이 있으면 새 기능 구현보다 적용 여부 계측이 맞다.

최종 새 후보는 동결된 전체 사례를 실행한다. 같은 후보·평가기·설정·입력에서 중단한 경우에만 검증된 완료 증거 재사용을 허용한다. 후보가 바뀐 뒤 이전 통과를 비용 절감 목적으로 승계하지 않는다. 관련 사례를 자동 추론하는 복잡한 영향 그래프는 현재 우선순위가 아니다.

## 검증과 순서 제안

최초 순서는 O1+O2 → O3 → O4 → O5 적용 점검이다. O1 난도가 예상보다 높거나 묶을 행동이 적다면 순서를 바꾸는 것이 가능하다.

비용 결과를 내기 전에 로컬 가짜 앱으로 DOM 교체·동일 라벨·체크 실패·리다이렉트·모달·중복 submit·행동 상한·캡처 누락 같은 실패를 확인한다. 이후 같은 앱 버전, 사례·생성 입력·모델·예산을 맞춘 브라우저 A/B로 전체 비용, tester/Judge 입력·출력·호출, 원자 행동 수, 완료/미평가, 잘못된 통과·놓친 오류를 비교한다. 현재 Judge 결과를 무조건 정답으로 삼지 않고 알려진 실패를 따로 확인한다. 한 번의 절감 관측을 일반 절감률로 확대하지 않는다.

테스터와 보고서가 실행·관측되지 않은 결과를 통과 처리하는 기존 문제는 비용과 별도로 기록한다. 이번 토론의 범위를 복제품 전체 재작성이나 일반 운영 품질 감사로 넓히지 않는다.
