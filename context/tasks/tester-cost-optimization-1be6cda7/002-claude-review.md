# Claude 검토: 001-codex-proposal O1–O5 (tester 비용 최적화)

## 결론

- O1(행동 묶음)은 **수정 채택**한다. 다만 절감 상한이 tester 호출의 10–30%로 측정되어 첫 순위가 아니다.
- O2는 **기각**하되 O1의 중단 조건으로 흡수한다. 독립 항목으로 둘 만큼 새 기능이 없다.
- O3(입력 축소)는 **수정 채택**한다. 화면 중복 제거 대신 이력 압축을 먼저 한다.
- O4(결정적 검사)는 **보류**한다. 스키마가 이미 지원하고 절감 경로가 좁다.
- O5(개발 선택 실행)는 **기각**한다(이미 구현됨). 다만 실제 개발 실행은 전체 케이스였다(아래 사실).
- 신규 **O6**(프롬프트 캐시 배치)을 첫 순위로 제안한다. tester 비용의 84%가 매 호출 새로 쓰는 캐시 쓰기다.
- 신규 **O7**: $44.29 기준선의 23%는 평가기 변경 때문에 같은 후보를 다시 돈 비용이다. 이 비용은 호출 효율 문제가 아니므로 기준선에서 분리한다.
- 권장 순서: O7(측정 규칙) → O6 → O3 → O1. O4는 보류하고 O5는 종료한다.

## O1 행동 묶음 — 수정 채택 (3순위)

근거
- 사실: `_OBSERVE_SCRIPT`(`web_demo.py:91-122`)는 매번 `data-replica-ref`를 지우고 번호를 다시 매긴다. 속성은 다음 observe 전까지 남는다.
  - 따라서 **한 번의 관찰에 대해 묶음을 끝까지 실행하고 중간에 observe를 다시 부르지 않으면** ref가 일관된다.
  - 안정 id(tag+label)는 필요 없다. label은 중복되거나 비어 있을 수 있어서 오히려 위험하다.
- 사실: 절감 상한은 위 4번처럼 10–30%다. O6/O3보다 효과는 비슷하거나 작고, tester 행동을 바꾸는 위험은 크다.

해결해야 할 반론
1. **DOM 교체**: React류 재렌더가 속성을 지우면 locator가 10초 timeout까지 기다린다(`_perform`).
   - 묶음 안에서는 각 행동 전에 `count()==1`을 확인한다. 아니면 즉시 중단한다.
2. **숨은 필드 노출**: check가 새 필드를 드러내도 ref 누락만으로는 감지되지 않는다.
   - 각 행동 뒤에 **속성을 바꾸지 않는** 스크립트로 보이는 상호작용 요소 수와 URL을 비교한다. 바뀌면 남은 행동을 버리고 모델로 돌아간다.
3. **중간 증거 손실**: 지금은 행동마다 행동 전 관찰이 `record["observations"]`에 남고, 이것이 Judge의 `_screen_evidence` 입력이 된다.
   - 제출 후 폼이 초기화되면 입력값의 증거가 사라진다.
   - 제출 click 직전에 **모델 호출 없는 observe**를 한 번 남긴다. 행동별 event와 스크린샷은 지금처럼 유지한다.
4. **중복 실행**: 묶음에서 click/press/upload는 마지막 1개만 허용한다. 실패하면 남은 행동은 실행하지 않는다.
   - 실행된 접두부와 오류를 이력에 남긴다. 자동 재시도는 하지 않는다.
5. **예산**: `max_actions_per_case`와 `remaining_actions`는 원자 행동 수로 센다. Codex 안과 같다.

최소 구현 순서
1. `TESTER_SCHEMA`에 `actions` 배열을 추가한다. 상한은 5로 두는데, 관찰된 최장 묶음이 fill×3+check+click이기 때문이다.
2. `_run_case`에서 배열을 원자 행동별 event로 펼친다. 같은 `tester_call_id`를 공유한다.
3. 위 1–3 중단 검사를 넣는다.
4. 제출 전 무호출 observe를 넣는다.

검증 조건
- 가짜 로컬 앱 단위 테스트(무료)로 다음을 확인한다.
  - (a) 재렌더로 ref가 사라지면 즉시 중단하고 10초 대기가 없다.
  - (b) 조건부 필드가 나타나면 중단한다.
  - (c) 제출이 두 번 실행되지 않는다.
  - (d) 묶음 안 행동별 event와 스크린샷이 남는다.
  - (e) 입력값이 Judge 증거에 남는다.
- 유료 A/B는 O6/O3 이후에 같은 후보·케이스로 한다.

## O2 사후조건·대기 — 기각 (O1로 흡수)

- 사실: `wait_for`(`_wait_on_screen`), `_settle`(networkidle+0.2초), Playwright `set_checked`의 상태 확인, `fill`의 값 대체가 이미 있다.

## O3 모델 입력 축소 — 수정 채택 (2순위)

근거
- 사실: 이력 15개(약 3,700자)가 호출당 쓰기 토큰의 약 22%로 추정된다.
  - 이력 항목마다 element 사전과 긴 reason이 들어간다(`_tester_prompt`의 `history[-15:]`).
- page는 현재 화면 전체라서 tester가 ref를 고르려면 필요하다.
  - 화면 중복 제거나 델타 입력은 직전 화면에 의존하게 만든다. 그러면 관찰을 놓칠 위험이 가장 크다.
  - Judge 쪽 `_screen_evidence`는 이미 중복을 제거한다. tester에 같은 방식을 쓰는 것은 다른 문제다.

해결해야 할 반론
- 이력 **개수**를 줄이면 긴 케이스(milestone-approval 40행동)에서 어느 단계까지 했는지를 잃을 수 있다. 개수는 유지하고 **항목을 압축**한다.
  - 남기는 필드: action, label, value(200자), error.
  - reason은 80자로 자른다. element의 tag/type은 뺀다.
- 8000자 page와 200자 값 한도는 낮추지 않는다. Codex 안과 같다.

검증 조건: 같은 후보·같은 케이스 1–2개에서 다음을 비교한다.
- 호출당 `cache_creation_input_tokens`
- 행동 수
- 케이스 완료율
- give_up 사유

## O4 계획 시점 결정적 검사 — 보류

- 사실: `validate_demo_plan`은 이미 expectation의 선택적 `check`(`CHECK_TYPES` 5종)를 받는다. `freeze_demo_plan`은 구현 전에 그것을 동결한다. 따라서 "계획 시점에 정의하고 동결"은 새 기능이 아니다.
- 사실: `_evaluate_case`는 의미 expectation이 하나라도 있으면 케이스당 Judge를 1회 부른다. 일부 조건을 검사로 바꿔도 Judge 호출 수는 그대로다.
  - Judge 등록 비용은 $6.33(14%)다. 85개 조건이 모두 Judge를 썼다는 것은 Codex 집계이며, 이번에 다시 세지 않았다.
- 반론
  - `page_contains`는 최종 화면만 본다.
  - 파일 검사는 구현 전에 저장 구조를 알 수 없다.
  - 잘못된 검사는 잘못된 통과를 만든다.
  - 방향 문서 §5도 JSON 경로 검사를 계약 기준에서 뺐다.
- 재검토 조건: 한 케이스의 모든 expectation을 화면 문구만으로 판정할 수 있는 계획이 실제로 나오는 경우.

- 관찰: 그런데도 개발 데모 4건 중 3건은 전체 케이스였다(사실 7).

## O6 (신규) 고정부를 캐시되는 시스템 프롬프트로 이동 — 채택 제안 (1순위)

- 사실: 고정 지시·actions 사전·케이스가 매 호출 user 메시지에 들어가 캐시 쓰기 단가로 과금된다(사실 1–3).
- 제안: Claude 경로에서 instruction+actions+case를 `--append-system-prompt`(또는 `--system-prompt`)로 옮긴다. stdin에는 이력·page·remaining만 남긴다.
  - 케이스 안의 호출 약 26회 동안 고정부가 캐시 읽기(0.1배)로 바뀐다.
- 추정 효과: 쓰기 토큰의 약 18% × (1−0.1/1.25) ≈ 쓰기 비용의 16.5%이고, tester 비용의 **약 14%**다(추론, 미측정).
- 미확인
  - (a) `--safe-mode --tools ""`와 함께 쓸 때 추가 시스템 프롬프트가 캐시 경계 안에 들어가는지
  - (b) 지시 위치가 바뀌면 tester 행동이 달라지는지
  - (c) Codex(`codex exec`) 경로에 대응 수단이 있는지. 이 제안은 Claude 경로 전용이다.
- 검증: 같은 케이스 1개를 2회 실행해 첫 호출 뒤 `cache_read_input_tokens`가 고정부만큼 늘고 `cache_creation`이 줄어드는지 receipt로 확인한다. 유료 호출이 필요하므로 사용자 승인이 있어야 한다.

## O7 (신규) 기준선 분리와 평가기 고정 — 채택 (측정 규칙, 코드 없음)

- 사실: 같은 후보를 두 번 전체 재실행한 비용 $10.08은 평가기·설정 변경 때문이었다(사실 6).
  - 같은 identity였다면 기존 체크포인트가 claim-001의 완료된 5케이스를 재사용했을 것이다.
- 추론: 정상 운영(회사 실행 중 평가기 고정)에서는 이 비용이 반복되지 않는다. $44.29를 개선 기준선으로 쓰면 절감률이 부풀려진다.
- 제안
  - O1/O3/O6의 효과는 "같은 후보·같은 케이스·같은 평가기에서의 호출당 쓰기 토큰과 호출 수"로만 보고한다.
  - 한 회사 실행 안에서는 평가기·모델 설정을 바꾸지 않는다.
  - 사용량 한도로 미완료된 실행은 같은 identity의 `--resume-from`으로 잇는다.

## 개발과 최종 평가의 경계

- 동의: 개발 중 실행은 선택 케이스와 implementer 몫이다. 최종 평가는 implementer와 분리된 동결 전체 세트다.
  - O1/O3/O6은 tester 내부 효율만 바꾸고 이 경계를 건드리지 않는다.
- 주의: O1/O3/O6은 모두 `evaluator_version()`을 바꾼다. 따라서 적용 직후에는 이전 증거를 재사용할 수 없다. 회사 실행 사이에만 적용해야 한다(O7).
