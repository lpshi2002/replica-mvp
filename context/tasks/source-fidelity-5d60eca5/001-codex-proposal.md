# source-fidelity — Codex 첫 제안

**핵심 제안:** 출처 수를 늘리는 것보다, 출처를 고정하고 그 안의 조건을 정확히 뽑아 시험 기준까지 보존하는 흐름을 먼저 만든다. 검색은 자료를 찾는 데 쓰고, 인용은 원문에서 결정적으로 추출한다. 의미 해석은 별도로 검증하며, 공개되지 않은 조건은 시험 규칙으로 만들지 않는다.

아래는 검토 전 제안이다. 기업 입력 이후 자동 완료라는 제약을 유지한다. 자동으로 판단할 근거가 부족하면 사람 검토를 기다리는 대신 `불명확` 또는 `미평가`로 남긴다.

## 질문 1 — 의미가 달라지는 지점과 관측된 빈도

| 쟁점 | 현재 근거와 관측 | 빈도·영향 판단 |
|---|---|---|
| **I1 — 출처 선택과 제품·시점 확인** | 2차 조사 세션 6개가 WebSearch, WebFetch, `curl`을 섞어 썼다. 회사 공식 문서·블로그·사례·보관본이 함께 쓰인다. 1차 세션의 도구 기록은 확인되지 않았다. | 잘못된 제품 버전이나 홍보 문구를 기능 규칙으로 고르는 비율은 **측정되지 않았다**. 발생 시 조사 전체와 시험 목표를 바꿀 수 있다. |
| **I2 — 원문 수집과 발췌** | 148개 URL–발췌 쌍 중 약 125개는 공백·문장부호를 정규화한 뒤 맞았다. 5개는 서식 차이, 2개는 떨어진 문장 결합, 2개는 단어 누락, 1개는 현재 페이지에서 찾지 못했다. 13개는 404·403·JS 렌더링·로그인 등으로 확인할 수 없었다. | 확인된 135개 중 결합·누락·현재 페이지 부재는 5개다. 이 중 일부는 의미를 바꿀 수 있지만, 전부가 의미 변경이라고 볼 수는 없다. 현재 페이지에서 보이지 않는다는 사실도 당시 발췌가 틀렸다는 증거는 아니다. |
| **I3 — 인용 범위와 문맥** | 두 문장을 이어 붙이거나 조건어를 빼면 인용 문자열 자체가 부정확해진다. 예를 들어 Save & Exit 발췌에서 `or`가 빠졌다. 현재 검사는 작성자가 기록한 발췌 안에 문자열이 있는지 확인할 뿐, 원문 문단의 조건·예외까지 보존했는지는 판정하지 않는다. | v4에서 확인된 결합·단어 누락은 각각 2개다. 부정, `or/and`, 한도, 적용 조건이 걸리면 작은 누락도 시험 기대 결과를 바꿀 수 있다. |
| **I4 — 발췌를 회사 주장으로 해석** | Interviewer 안내는 100% 달성 때 새 주제가 생긴다고 했다. 같은 결과의 `boundaries`는 몇 번의 답변으로 100%에 도달하는지는 공개되지 않았다고 적었고, 경계는 “무제한 주제”라고 했다. 그런데 6번의 답변을 시험 실행 한도로 정한 뒤, 6번 안에 100%가 안 되면 실패라는 조건을 `public_rule`로 넣었다. ([v4 시험 기준](/Users/cho/replica-mvp/work/delphi-ai-v4/second_pass/creator-interview-to-mind-snippets.json:809), [사후 검토](/Users/cho/replica-mvp/tmp/reviews/delphi-v4-postrun-review-2026-10-12.md)) | **적어도 한 건의 중대한 의미 오류가 확인됐다.** 전체 해석 오류율은 전수 표본과 정답 라벨이 없어 산출할 수 없다. 영향은 높다. 구현자가 근거 없는 상한에 맞춰 동작을 조정할 수 있다. |
| **I5 — 페이지 변경과 버전** | 한 발췌는 현재 페이지에서 발견되지 않았고 13개는 현재 접근 불가였다. 일부 자료는 보관본이다. | 확인 불가와 시간에 따른 변경을 구분할 자료가 부족하다. 현재 URL만 저장하면, 조사 당시의 정답 기준을 나중에 재현하지 못할 수 있다. |
| **I6 — 조사 결과를 시험 기준으로 변환** | v4는 인용의 존재보다 해석 오류가 치명적이었다. 기존 검사도 정확한 문자열이 기록된 발췌 안에 있는지를 주로 확인한다. 새 지침은 공개 규칙·관측·독립 검증·자체 조건을 구분하고 실행 한도를 기능 규칙과 분리하도록 보완했다. ([검사 코드](/Users/cho/replica-mvp/src/replica_mvp/project.py:449), [2차 지침](/Users/cho/replica-mvp/skills/replica-research/agents/replica-second-pass.md:305)) | 오류 빈도는 측정되지 않았다. 한 번 잘못 변환되면 시험 기준 고정 이후 구현·평가·보고서까지 전파되므로 영향은 높다. |
| **I7 — 자동 판정기의 오류** | 기존 평가에서는 63회 판정 모델 호출이 약 $6.33이었다. 그러나 출처 의미 판정의 오합격·오탈락률은 기록되어 있지 않다. | 모델 호출 수나 링크 유효성이 정확성의 대리 지표가 되지 않는다. 현재 오판율은 미측정이다. |

Ralph-to-Ralph는 대상 문서 사이트를 먼저 결정적으로 수집하고, 에이전트가 직접 스크래핑하지 않게 하는 구조로 기록되어 있다. 문서가 많은 SaaS의 조사 공간을 안정적으로 줄이는 장점은 있다. 다만 인계 조사에 따르면 수집 문서를 `docs-extract.md`로 요약하고 인용 검증은 하지 않는다. 원제품 QA가 별도 안전망이 된다. 따라서 이 방식은 **문서 사이트의 검색·수집 안정화**에는 참고할 수 있지만, 블로그·보관본·도움말·기사 등 여러 웹사이트에서 출처를 모아 시험 정답을 만드는 문제까지 해결하지는 않는다. ## 질문 2 — 장치 비교와 선택

외부 방법론은 한 가지 방식에 몰리지 말고, 각 단계에서 막을 수 있는 오류를 나눠 적용한다.

| 쟁점 | 비교할 방법 | 제안 |
|---|---|---|
| **I1 — 출처 찾기** | 검색 결과만 읽으면 빠르지만, 검색 요약은 맥락·최신성을 보장하지 않는다. 반대로 문서 사이트 전체를 크롤링하면 문서형 SaaS에는 유용하지만 검색할 곳이 분산된 회사 자료에는 비용이 크고, 전체 수집 자체가 올바른 출처 선택을 보장하지 않는다. | **검색으로 후보를 찾고, 선택한 원문만 직접 가져오는 혼합 방식**을 쓴다. 회사·제품·기능·문서 날짜를 확인하고 공식 자료와 독립 자료를 구분한다. 문서가 잘 구조화된 SaaS일 때만 Ralph형 사이트 수집을 선택적으로 적용한다. |
| **I2 — 원문 확보** | WebFetch처럼 LLM이 발췌를 반환하면 동적 페이지 처리에 편하지만, 지시해도 생략·요약·문장 결합이 생길 수 있다. HTTP·HTML·PDF·브라우저 DOM에서 직접 가져오면 재현성이 높지만, 로그인·JS·표·PDF에는 별도 처리기가 필요하다. | 먼저 원문 콘텐츠를 저장하고 결정적으로 텍스트를 추출한다. 페이지가 동적이면 브라우저 DOM, PDF면 페이지 위치 등 입력 유형에 맞춰 대체한다. LLM은 발췌 후보를 찾는 보조 수단으로 두고, 최종 인용은 원문 위치로 다시 확인한다. |
| **I3 — 발췌와 문맥** | 정규화 후 문자열 일치는 인용의 존재를 싸게 확인하지만, 인용이 그 해석을 뒷받침하는지는 모른다. LLM 의미 검사는 맥락을 볼 수 있지만 원문에 없는 규칙을 추론할 수 있다. | 두 검사를 순차 적용한다. 정확한 원문 구간과 앞뒤 문맥을 보존하고, 매칭 실패는 자동 합격시키지 않는다. 그 다음에만 의미 검사를 한다. 퍼지 매칭은 후보 위치를 찾는 데 쓰고, 불일치 발췌를 유효 인용으로 통과시키는 데 쓰지 않는다. |
| **I4 — 의미 해석** | 조사 에이전트가 스스로 재검토하면 싸고 빠르지만, 첫 해석의 전제를 반복할 수 있다. 독립 이중 추출은 비용이 늘지만 첫 추출의 오류를 찾을 가능성이 있다. | 테스트 기대 결과·`boundaries`처럼 구현에 직접 영향을 주는 항목은 **별도 검증자가 먼저 원문과 주변 문맥만 보고 규칙을 추출**한 뒤 기존 해석과 비교한다. 먼저 작성된 결과를 보여주지 않아 편향을 줄인다. Cochrane은 주관적 해석이나 결과 해석에 중요한 데이터를 독립적으로 두 번 추출하라고 권하며, 한 사람의 추출을 다른 사람이 사후 확인하는 것보다 독립 추출이 오류를 줄였다는 간접 근거도 든다. 이는 사람 연구의 방법을 참고하는 것이며 두 LLM의 독립성이나 Replica에서의 효과를 입증하지는 않는다. ([Cochrane Handbook, Chapter 5](https://training.cochrane.org/handbook/current/chapter-05)) |
| **I5 — 시간에 따른 변경** | 실행 때 매번 현재 URL만 다시 읽으면 신선하지만 과거 판단 기준을 재현하기 어렵다. 보관본만 쓰면 기준 시점은 고정되지만 보관되지 않은 자료나 현재 동작을 놓칠 수 있다. | 사용한 각 URL의 본문·수집 시각·정규 URL·해시·문서 위치를 저장한다. Wayback 등 보관본은 현재 자료가 사라졌거나 기준 시점이 중요한 경우 대체로 사용하고, 현재 자료와 섞이면 버전을 분리한다. |
| **I6 — 시험 기준 만들기** | 문장 하나를 바로 테스트로 바꾸면 예시·실행 예산이 제품 규칙으로 격상될 수 있다. 기준을 무조건 약하게 두면 실제 공개 동작을 놓칠 수 있다. | 기준을 작은 주장으로 분해하고 각 기준에 출처와 근거 유형을 연결한다. 회사가 명시한 동작, 직접 관측, 별도 검증, 우리 자체 조건을 구분한다. 공개되지 않은 숫자·한도는 `undisclosed`로 두고, 실행 시간·답변 수는 시험 실행 한도로 관리한다. 복합 주장 분해와 원문 근거 수집을 별도 단계로 둔 NAACL 연구도 이 구조와 맞지만, 그 연구는 정치 주장 검증이므로 Replica 기능 계약에 대한 직접 검증은 아니다. ([Complex Claim Verification with Evidence Retrieved in the Wild](https://aclanthology.org/2024.naacl-long.196/)) |
| **I7 — 검증기 운영** | 한 모델만 쓰면 비용은 낮지만 편향을 측정하기 어렵다. 다수 모델 투표는 비용을 늘리고, 같은 오류를 공유하면 투표가 오류를 제거하지 못한다. | 모델 개수보다 **정답 라벨에 대한 오합격률과 불명확 판정률**을 먼저 측정한다. 검증 결과는 `지원됨 / 모순됨 / 근거 부족 / 애매함`으로 나눠 반환한다. 검증기가 애매하다고 판정하면 자동으로 합격시키지 않고 제한·미평가로 기록한다. |

**전문가 근거의 적용 한계:** Cited but Not Verified는 인용을 링크 접근성·주제 관련성·사실 일치로 나눠 평가했다. 논문 초록에서 강한 모델도 링크·관련성보다 사실 정확도가 크게 낮았고, 일부 모델은 도구 호출이 2회에서 150회로 늘어날 때 사실 확인 정확도가 약 42% 감소했다. 이 연구는 딥리서치 보고서를 평가한 것이며 Replica의 오류율을 예측하지는 않는다. 다만 검색 횟수나 인용 유무만 늘리는 것으로 의미 정확성을 보장할 수 없다는 근거다. ([Cited but Not Verified](https://arxiv.org/abs/2605.06635))

AVeriTeC은 검증 결과를 맞혔더라도 근거 품질이 기준에 못 미치면 정확한 검증으로 보지 않는다. 인용 존재와 근거의 충분성을 함께 봐야 한다는 제안과 맞는다. ([AVeriTeC shared task](https://aclanthology.org/2024.fever-1.1/)) FActScore는 긴 문장을 원자적 사실로 나눠 사실별 지원 여부를 보지만, 특정 인물 소개·지식원 과제에서의 성능을 공개 기능 조사 정확도 보장으로 옮겨올 수는 없다. ([FActScore](https://aclanthology.org/2023.emnlp-main.741/))

## 질문 3 — 검사 범위, 비용, 자동화 오류 통제

**검사 범위는 두 층으로 나눈다.**

- **I2·I3 — 148개 인용 쌍:** 모든 인용의 URL 상태, 저장된 원문에서의 정확한 구간, 전후 문맥을 결정적으로 확인한다. brief에는 기능별 출처 페이지가 8·8·3개로 기록되어 있으므로, 중복 URL을 제거하면 최대 19개 기능별 페이지 사용분을 한 번씩 가져오는 규모다. 페이지 수는 세 기능 간 중복 제거 전 실제 URL 수와 같다고 단정할 수 없다.
- **I4·I6 — 65개 기대 결과:** 기능별 21·26·18개 기대 결과를 근거와 대조한다. 같은 공개 규칙을 여러 사례에서 반복 사용한다면 `출처 + 원자적 규칙` 단위로 묶어 검증 호출을 줄인다. 출처가 구현 시험 정답에 직접 영향을 주므로, 일반 설명문보다 우선 검증한다.
- **I1·I5 — 상충·취약 자료:** 공식 문서와 사례 페이지가 충돌하거나, 자료가 보관본·로그인·JS 페이지이거나, 한도·부정·예외 조건이 포함되면 독립 검토 대상으로 올린다. 저위험 설명문까지 모두 여러 모델에 반복 제출하지 않는다.

**v4 크기에 맞춘 비용 추정:** 실제 v4 판정 모델은 63회 약 $6.33이므로 호출당 약 $0.10을 단순 참고값으로 쓴다. 출처 검증 호출은 문맥 길이가 다르므로 실비 견적이 아니다.

| 추가 작업 | 추정 |
|---|---:|
| 148개 발췌의 정규화·원문 위치 확인 | LLM 호출 없이 가능. 원문 가져오기와 파서 개발·실행 비용은 별도 |
| 기대 결과 65개를 별도 검증자 1회씩 확인 | 약 **$6.50 추가** |
| 65개를 독립 추출 두 번으로 모두 확인 | 총 약 **$13 추가**의 호출 규모 |
| 148개 발췌–주장 쌍 전체를 LLM 1회씩 검토 | 약 **$14.90** |
| 148개 쌍 전체를 LLM 이중 검토 | 약 **$29.80** |

위 값은 `실측 평균 약 $0.10/호출 × 가정한 호출 수`다. 입력 길이·모델·호출 묶음 방식에 따라 달라진다. 따라서 첫 구현은 **모든 인용의 결정적 검증 + 기대 결과에 대한 별도 의미 검증**으로 제한하는 편이 낫다. 이 정도면 v4의 최종 판정 모델 비용과 비슷한 추가 예산 안에서 우선순위가 높은 의미 오류를 겨냥한다. 사후 리뷰는 같은 실행의 브라우저 테스터 비용을 약 $31.14로 환산했지만, 이는 실제 청구액이 아닌 기록 기반 추정치다. 자동 검증기를 통제하는 방법은 다음과 같다.

- **I7 — 개발 단계에서 정답 묶음 구성:** v4의 발췌 불일치 사례와 “6번 안에 100%” 오류를 포함하고, 정확한 대조군도 넣는다. 별도 평가자가 `지원 / 반박 / 근거 부족 / 과잉 해석`을 독립적으로 라벨링한 후 검증기의 오합격률과 불명확률을 잰다. 이는 회사별 실행마다 사람 승인을 기다리는 관문이 아니다.
- **I7 — 특히 오합격을 측정:** “지원됨”이라고 판정한 규칙 중 실제 원문과 불일치한 비율을 핵심 지표로 둔다. 신뢰도 점수만으로 합격시키지 않는다. 작은 v4 표본에서 통과율 하나를 일반 정확도로 보고하지 않는다.
- **I4·I6 — 불명확하면 합격 대신 제한:** 공개 출처가 시험 규칙을 충분히 뒷받침하지 않으면 기능 실패로 판정하지 않는다. 조건을 확인할 수 없거나 시험 범위가 불완전한 것으로 기록한다. 자동 완료는 유지하되 정답으로 가장하지 않는다.

## 질문 4 — 먼저 넣을 최소 구성

1. **I2·I3 — 모든 인용을 원문에 고정:** URL, 제품·문서 버전, 수집 시각, 해시, 추출기, 페이지·문단 위치, 정확한 발췌와 주변 문맥을 함께 저장한다. 인용은 검색 도구가 반환한 요약이 아니라 저장된 원문 구간으로 확인한다.
2. **I4·I6 — 시험 기준에만 독립 의미 검증:** 기대 결과와 `boundaries`는 출처 원문에서 별도로 규칙을 추출해 대조한다. 숫자·부정·예외·조건·기간이 새로 추가되었는지 집중 검사한다. `public_rule`이 근거 없이 확장되면 자동 승인하지 않는다.
3. **I4 — 기준 유형과 불확실성 보존:** 회사 공개 규칙, 직접 관측, 별도 검증, 우리 자체 조건을 구분한다. 출처가 충분하지 않으면 `not_evaluated` 또는 `undisclosed`로 남긴다. 현재 2차 지침의 혼합 기준 분리·실행 한도 분리를 이 흐름의 기준으로 삼는다.
4. **I7 — 오류표로 먼저 보정:** v4의 148개 인용 대조 결과와 65개 기대 결과를 개발용 검증 자료로 정리한다. 의미 라벨이 없는 사례는 정답셋으로 취급하지 않는다. 소수 표본으로 정확도가 확립됐다고 주장하지 않는다.
5. **I1·I5 — 보완은 실패 유형을 본 뒤:** 전 사이트 크롤링, 인용마다 다중 LLM 토론, 모든 링크의 반복 재검증, 20페이지 최소 수집 관문은 먼저 넣지 않는다. 문서 사이트가 구조화되어 있고 검색 누락이 반복되면 선택적으로 크롤러를 확대한다. 특정 유형의 페이지가 반복해서 접근 불가하거나 버전 변경으로 시험 기준이 바뀌면 보관·재수집 경로를 강화한다.

**제안의 우선순위:** 첫 단계의 품질 지표는 “인용이 저장된 발췌 안에 있는가”가 아니라 **시험 기준의 조건·한도·예외가 실제 출처의 의미를 넘지 않는가**다. v4에서 가장 큰 오류는 인용 부재가 아니라 한 실행 한도를 공개 기능 규칙으로 바꾼 해석이었다. 이 부분을 먼저 잡는 것이 출처 수를 늘리거나 모든 페이지를 LLM으로 재검토하는 것보다 목표에 가깝다. ([v4 조사 기록](/Users/cho/replica-mvp/context/tasks/source-fidelity-5d60eca5/brief.md:30))
