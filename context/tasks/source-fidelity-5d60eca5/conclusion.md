# source-fidelity — 결론

종료: resolved (2026-10-16). 의견: [001 Codex 제안](001-codex-proposal.md), [002 Claude 검토](002-claude-review.md), [003 Codex 수정안](003-codex-revision.md), [004 Claude 확인](004-claude-verification.md).

**검증 범위의 한계:** Claude 쪽은 Orca 전용 세션 생성 실패(`consumer_fenced`, effectsApplied false)로 진행자 세션이 겸했다. 독립된 두 번째 검토가 아니다. 이번 토론은 설계 권고이며 제품 코드·지침은 수정하지 않았고 구현·시험도 실행하지 않았다. 사용자 승인 전에는 방향으로 확정하지 않는다.

## 핵심 판단

1. **목표 지표는 "인용이 있는가"가 아니라 "시험 기준의 조건·한도·예외가 원문의 의미를 넘거나 빠뜨리지 않았는가"다.** v4의 치명 오류는 인용이 정확한 상태에서 원문에 없는 한도("6번 안에")를 공개 규칙으로 만든 해석 오류였다.
2. **원문을 정확히 가져오는 것은 의미 검사의 전제다.** WebFetch는 작은 모델이 프롬프트에 답한 결과를 돌려주는 도구여서 "그대로 인용"을 지시해도 보장되지 않는다. v4에서 문장 이어붙이기 2건, 조건어(`or`) 누락 등이 관측됐다. 원문을 저장해야 의미 검사에 앞뒤 문맥을 줄 수 있다.
3. **검사 노력은 시험 정답이 되는 인용에 집중한다.** 임상시험의 위험 기반 원자료 검증처럼, 결정적 검사는 전체에 싸게, LLM 의미 검사는 기대 결과·`boundaries`에만 둔다.
4. **"다시 읽기"에 기대지 않는다.** 사람의 이중 추출도 오류를 줄이지만 많이 남긴다(2025 RCT: 교차 확인 후 연구 단위 오류율 약 40~45%). 그래서 구조적 보장(원문 고정, 결정적 대조)과 오류 유형을 지정한 표적 검사를 쓴다.

## 권장 구성 (도입 순서)

| 순서 | 장치 | 막는 의미 오류 | v4 규모 비용(추정) | 방식 |
|---|---|---|---|---|
| 1 | **원문 고정**: 1·2차 지침에서 WebFetch·WebSearch는 찾기 전용. 선택한 출처는 HTTP·Playwright(이미 평가에 사용)·보관본 중 실패 원인에 맞는 방법으로 저장하고 URL·날짜·수집 시각·해시를 기록. 인용은 저장 원문에서만 잘라 오고 결정적으로 구간 확인 | 요약·재서술, 문장 이어붙이기, 조건어 누락, 시점 혼합의 추적 불가 | LLM 0회. 기업당 고유 페이지 약 19개 이하 수집 | 시험 기준 인용 불일치는 **고정 차단**, 배경 인용은 기록 |
| 2 | **양방향 요소-구간 대응 검증**: 기대 결과를 주체·행동, 조건·트리거, 수치·한도, 부정, 범위·양화, 순서·시간 요소로만 나눠 각 요소에 원문 구간 대응(검증자의 구간도 결정적 확인). 역방향으로 인용한 규칙(같은 문장·목록 항목)의 조건이 빠지지 않았는지 확인. 고위험 수치·부정은 원문 단독 추출 추가. 숫자 요소와 `undisclosed`의 충돌은 코드로 검사 | 근거 없는 추가 조건(v4 "6번"), 조건 누락, 부정·범위 변경 | 출처 페이지 단위 묶음 약 19회, 약 $1.90(상한: 기대 결과별 65회 약 $6.50). 호출당 $0.10은 v4 최종 판정 평균을 쓴 단순 추정 | 근거 부족·모순 기준은 **고정 전 되돌림** |
| 3 | **제한 재시도**: 요소 단위 지적을 2차 작업자에게 최대 2회(발췌 수정 1, 대체 출처 1). 자동 `our_condition` 전환 금지 | 같은 오류 반복 | 오류 난 기준만 | 남은 기준은 `basis_unsupported` → `not_evaluated`로 기록. 기존 판정 코드가 완전 재현을 막음(`web_demo.py:908-918`) |
| 4 | **변이 회귀 시험**: 원문 쌍(양성)과 통제된 의미 변경(한도 추가, `or/and`, 조건 삭제, 부정 반전, 범위 확대, 순서 변경, 실행 한도 격상, 문장 결합)으로 검증기 검출률·오탈락률 측정. v4 실제 오류 사례를 고정 사례로 포함 | 검증기의 알려진 맹점 | 개발 시 1회. v4 관측 유형 위주 소규모로 시작(전체 390건이면 약 $39) | 실패한 변이 유형은 그 유형의 자동 "지원됨" 판정 보류. 실제 오류율 추정으로 쓰지 않음 |

`undisclosed`는 "확인한 자료에서 찾지 못함"으로 표현하고 조회한 출처·시점을 남긴다.

## 기각·보류한 대안과 재검토 조건

- **전면 독립 재추출(두 번 읽고 비교):** 기각. 비교 자체가 또 하나의 판정이고 수정 지시가 나오지 않는다. 고위험 요소에만 남김.
- **모든 인용(148쌍)의 LLM 검토·이중 검토:** 보류. 비용 대비 근거 없음. 배경 인용 오류가 판정을 바꾼 사례가 나오면 재검토.
- **Ralph식 문서 사이트 전체 수집:** 선택 적용. 공식 문서가 구조화된 SaaS(llms.txt·sitemap)이고 검색 누락이 반복되면 확대. Ralph도 의미 검증은 없고 원제품 QA로 보완하는데, Replica는 원제품 접근이 없는 경우가 많아 그대로 따를 수 없음.
- **Anthropic Citations API:** 보류. 인용 위치를 구조적으로 보장한다는 공급사 설명이 있으나, 조사 작업자가 CLI 런타임에서 돌아 직접 쓸 수 없고 결정적 대조가 같은 보장을 비용 없이 준다. 검증기를 API로 옮길 때 재검토.
- **MiniCheck 등 소형 검증 모델:** 보류. 약 400배 저비용이지만 기업당 수십 건이라 비용이 병목이 아니고, 요소 단위 수정 지시를 내지 못한다. 검증량이 크게 늘거나 다른 계열의 두 번째 판정기가 필요할 때 재검토.
- **주장 전면 원자 분해(FActScore식):** 기각. MiniCheck에서 명시적 분해가 정확도를 일관되게 올리지 못하고 비용을 2~4배 늘렸다. 분해는 6개 요소로 한정하고 수정 지시 생성 용도로만 쓴다.
- **버전 혼합 검사:** 보류. 날짜 기록만 먼저 넣고, 다른 시점 출처가 한 기대 결과에 섞인 오류가 실제로 나오면 검사 추가.

## 사용자 결정이 필요한 사항

1. 이 구성을 지침·코드에 반영할지, 반영한다면 1번(원문 고정)만 먼저 할지, 1·2번을 함께 할지.
2. 2번 의미 검증을 처음부터 고정 차단 관문으로 둘지, 4번 변이 시험으로 검출률을 확인할 때까지 경고로만 운영할지. 권고: 1번은 처음부터 관문, 2번은 변이 시험 통과 후 관문.
