첫 작업은 **기존 평가 근거를 안전하게 읽어 기업 앱의 설명·한계·체험과 연결하는 것**으로 좁히는 것을 권고한다. 체험 상태 분리는 재사용한다. `evaluation_only → built_unevaluated` 강제 전환과 비공개 시험자료 도입은 기각한다.

아래는 수정 제안이며, 사용자 승인이나 구현 완료를 뜻하지 않는다. 전문가·원제품·숨긴 시험·사람의 검토를 자동 실행의 선행조건으로 추가하지 않는다.

**I1 — 수정 수용: 체험 제공과 사용 검증을 구별한다.**

평가 작업 공간과 사용자 체험 공간은 이미 분리돼 있다. `serve-company`는 별도 상태 디렉터리를 사용하고, 재개할 때 구현 파일과 manifest를 검사한다. 이 장치를 다시 만들 필요가 없다. [체험 실행 코드](/Users/cho/replica-mvp/src/replica_mvp/cli.py:532), [기존 상태 검사](/Users/cho/replica-mvp/src/replica_mvp/bundle_runtime.py:264)

‘실제 사용 가능’의 근거는 다음을 구별해 남긴다.

- **제공 범위:** 이번 구현에서 사용자가 입력하고 받을 수 있는 결과.
- **관측 범위:** AI가 같은 웹 화면에서 실제로 수행한 작업과 확인한 결과.
- **새 입력 확인:** 공개 변형 규칙으로 만든 자료를 넣어 입력부터 결과까지 수행한 기록.

첫 화면 로드는 기동 근거다. 초기 화면의 내용은 그 화면에 관한 기대 결과의 근거가 될 수 있지만, 전체 업무 수행을 입증하지 않는다. 현재 `check_company_app`도 기동 점검이라고 명시한다. [점검 코드](/Users/cho/replica-mvp/src/replica_mvp/company_app.py:166)

첫 구현에서는 이 구별을 화면에 반영한다. 새 자료를 사용하는 전체 작업 검증은 후속 작업으로 남기며, 아직 수행하지 않았다면 그대로 표시한다. 사람의 직접 사용은 선택이다.

**I2 — 원칙 수용, 강제 구현은 기각한다.**

평가 도구의 한계만으로 기능을 제외하는 문제는 맞다. 그러나 `evaluation_only`라는 분류는 구현 가능성이나 구현 완료의 증거가 아니다.

수정 규칙은 다음과 같다.

| 확인된 상황 | 처리 |
|---|---|
| 구현 경로·접근 조건·예산이 확인됨 | 해당 범위를 구현하고 가능한 평가를 수행 |
| 실제 구현을 제출했으나 일부 품질을 평가하지 못함 | 구현 근거와 미평가 범위를 함께 기록 |
| 구현 가능성이 불명확하거나 예산·접근이 부족함 | 미구현 또는 가능성 미확인으로 남기고 대안·필요조건 기록 |
| 평가 도구 제약만 제외 이유로 적혀 있음 | 조사 근거를 보완할 대상으로 처리. 자동 구현 완료 처리 금지 |

`built_unevaluated`는 사용하더라도 **실제 제출된 구현의 사후 설명**이어야 한다. 조사 단계의 `implemented` 계획이나 “가능해 보인다”는 문장에서 생성하면 안 된다. 현재 설계도 코드도 계획과 관측을 구별하고, 계획된 경로를 실측 성공으로 세지 않는다. [설계도 생성 코드](/Users/cho/replica-mvp/src/replica_mvp/agent_harness.py:1785)

완료된 결과를 다시 분류해 성공으로 올리지 않는다. 제외 범위를 복구하려면 실제 구현 변경과 새 실행 근거가 필요하다. 이번 토론은 기존 Delphi 실행을 재개할 이유가 아니다.

**I3 — 근거 검증은 수용하되, 이벤트 ID만 요구하는 설계는 수정한다.**

현재 코드는 유효하지 않은 이벤트 ID를 제거하면서 `passed`·`failed`를 유지한다. 반면 판정자에게 제공하는 자료에는 화면 관측과 파일 변화도 포함된다. 따라서 “실제 이벤트 ID가 하나 이상”이라는 조건만 추가하면 정당한 파일·초기 화면 근거를 버릴 수 있다. [판정 처리](/Users/cho/replica-mvp/src/replica_mvp/web_demo.py:735), [판정자에게 제공하는 근거](/Users/cho/replica-mvp/src/replica_mvp/web_demo.py:364)

새 결과부터 다음과 같이 처리한다.

| 근거 종류 | 보존·참조할 내용 |
|---|---|
| 화면 관측 | 초기·중간·최종 화면의 관측 ID, 텍스트·필드값, 해당 스크린샷 |
| 행동과 그 결과 | 이벤트 및 연결된 실제 관측. 클릭 성공만으로 업무 성공을 인정하지 않음 |
| 파일 내용·변화 | 실행 당시 파일 내용 또는 발췌, 파일 해시, 전후 변화 |
| 결정적 검사 | 검사 조건, 실제 비교값·일치 파일 목록, 사용한 화면 또는 파일 기록 |

파일 부재·변경 없음 검사는 존재하지 않는 파일을 참조할 수 없다. 검사 시점의 파일 목록과 전후 상태를 근거로 삼는다. 중단된 사례에서 아직 나오지 않은 결과를 실패로 판정하지 않는 기존 규칙도 유지한다. [결정적 검사](/Users/cho/replica-mvp/src/replica_mvp/web_demo.py:258)

`judge`의 충족·불충족 판정은 같은 실행·사례의 보존된 근거로 해석 가능한 참조를 요구한다. 모두 무효하면 `not_evaluated`로 처리하고 원응답과 차단 이유를 보존한다. 결정적 검사에는 행동 이벤트 ID를 강제하지 않고 실제 검사 근거를 연결한다.

여기서 보장하는 것은 **참조 무결성과 추적 가능성**이다. 관련 없는 장면을 인용한 AI 판단까지 자동으로 올바르게 만드는 것은 아니다. 화면에는 검사 방식, 판정 이유, 해당 관측을 함께 제시한다. 사람이 읽을 수 있다는 사실도 의미 검증 완료를 뜻하지 않는다.

이번에 기존 Delphi 기록을 읽어 확인한 결과, 참조 64개는 모두 해당 사례의 이벤트에 존재했고 빈 참조도 없었다. 따라서 확인한 참조 누락 결함은 이 기록에서 발견되지 않았다. **35개 판단의 의미상 정확성까지 검증했다는 결론은 보류한다.**

과거 기록과 신규 실행의 호환은 다음으로 정한다.

- 기존 결과는 수정하지 않는다. 근거가 누락됐다면 조회 화면에 ‘기록상 판정’과 ‘근거 확인 불가’를 구별한다.
- 과거 업로드에 해시가 없으면 **‘평가 당시 입력 내용의 동일성 미확인’**으로 표시한다. 지금 계산한 해시를 당시 동결 근거로 사용하지 않는다.
- 신규 계획은 고정 업로드의 내용 해시를 기록하고, 실행 전에 검사한다. 생성 자료는 생성 직후 내용을 보존하고 해시를 기록한다.
- 입력 식별 정보를 재개·캐시 판단에도 연결한다. 입력이 달라졌는데 과거 판정을 재사용하면 안 된다.
- 평가 버전 변경 시 기존 결과를 재표기하지 않는다. 현재도 평가기·설정이 달라지면 판정을 재사용하지 않는 구조가 있다. [재개 검증](/Users/cho/replica-mvp/src/replica_mvp/web_checkpoint.py:34)

**I4 — 수정 수용: 기본 화면은 역할·사용법·관측·한계·체험을 중심으로 한다.**

기업 앱 메뉴와 읽기 전용 결과 페이지를 연결한다. 별도 기술평가 앱 전체 통합은 뒤로 둔다.

기능 카드의 최소 내용은 다음과 같다.

- 무엇을 하는 기능인지, 어떤 자료를 넣고 무엇을 받는지.
- 시작하는 방법과 **직접 사용** 링크.
- AI 평가 기록의 요약과 **근거 보기** 링크.
- 구현에서 제외한 범위와 관측하지 못한 범위.

예를 들어 현재 Delphi는 “평가한 10개 사례의 35개 조건 충족, 전체 기능은 부분 재현”으로 보여야 한다. 사례 조건 충족을 기능 전체 성공으로 바꾸지 않는다. [보존된 기업 결과](/Users/cho/replica-mvp/work/delphi-ai-v4/claim-001-cost-comparison-2026-10-13/final-results/company-claims.json)

결과 페이지에는 기대 결과·판정 방식·이유·화면 및 파일 근거를 연결한다. 해시와 기술 경로는 필요한 세부 근거에 둔다. 기본 카드에 manifest 해시를 노출하자는 Claude 제안은 기각한다.

평가 대상과 현재 실행할 구현의 동일성은 기존 manifest·파일 검사로 확인해 사용자에게 이해하기 쉬운 문장으로 표시한다. 같은 구현이라는 사실과 같은 사용자 상태라는 사실은 구별한다. 메뉴는 현재 제목 중심이며 `summary` 전달도 빠져 있어, 이 연결이 실제 공백이다. [메뉴와 기능 선택 코드](/Users/cho/replica-mvp/src/replica_mvp/company_app.py:43)

**I5 — 일부 수용: 미확인 목록은 재사용하고, 직접 확인 안내는 선별한다.**

모든 기대 결과를 “직접 확인해 보세요”로 바꾸는 제안은 기각한다. 안내는 다음 조건을 충족하는 경우에만 만든다.

- 현재 구현에 해당 작업 경로가 있다.
- 관측 기록에 구체적인 불확실성이 있다.
- 사용자가 그 앱에서 결과를 직접 확인할 수 있다.

예를 들어 다른 자료의 동작이 미확인이고 업로드·인용 확인 기능이 구현돼 있다면 “다른 자료를 올리고 답변의 인용 부분을 원문과 대조”하는 안내가 가능하다. 구현하지 않은 양방향 음성이나 원제품 동등성을 체험으로 확인하라고 안내하면 안 된다.

첫 작업에서는 기존 `not_evaluated`, 제외 범위, 계획상 미검증 범위를 설명한다. `uncovered_steps`는 **계획된 사례의 범위 정보**이며 실제 조작이 해당 단계를 통과했는지 증명하지 않는다는 설명도 유지한다. [범위 산출 코드](/Users/cho/replica-mvp/src/replica_mvp/agent_harness.py:1011)

기업 질문은 원제품 접근 없이도 만들 수 있다. 주장 조건의 누락, 재현에서 막힌 지점, 필요한 자료를 질문으로 표현하면 된다. 다만 답을 확보하거나 원제품과 비교하는 데 추가 자료가 필요할 수 있다. 따라서 Claude의 “추가 자료가 없어서 질문 생성이 불가능하다”는 전제는 기각하고, 우선순위가 뒤라는 판단은 수용한다. 질문 생성·저장까지만 제안하며 외부 전송은 범위 밖이다.

**I7 — 문제 제기는 수용, 단일 blocker와 resource 우선 규칙은 기각한다.**

제약은 경로별 목록으로 보존한다. 구현·평가 중 어디에 영향을 주는지, 확인된 사실인지 불확실성인지, 대안과 예산 근거가 무엇인지 구별한다. 기존 `alternatives`·`needs`를 버리지 않는다. [현재 제외 검증](/Users/cho/replica-mvp/src/replica_mvp/second_pass.py:441)

실제 기록에는 단일 분류로 처리하기 어려운 반대 근거가 있다.

- 사이트 크롤링 대안에는 결과 변동성뿐 아니라 스케줄러 추가와 미확인 비용이 적혀 있다. 평가 제약을 제거했다고 예산 내 구현 가능성이 확정되지는 않는다.
- 다화자 분리에는 접근 승인이 필요한 pyannote 외에, 승인 없이 사용할 수 있다고 기록된 SpeechBrain 대안이 있다. 그 대안의 제외 이유에는 단일 화자 데모에 비해 분할·임계값 조정이 필요하다는 판단이 섞여 있다.
- 양방향 음성에는 테스터 제약과 실제 지연 성능의 불확실성이 함께 있다.

따라서 한 대안에 자원 제약이 있다는 이유로 기능 전체의 제외를 자동 유지할 수 없다. 반대로 대안 이름이 존재한다는 이유로 복구를 강제할 수도 없다. 여기서 확인한 것은 **보존된 조사 기록의 내용**이며, 대안의 현재 실행 가능성을 새로 시험한 것은 아니다.

집계는 기대 결과 수와 기능 범위를 분리한다. 미평가 부분을 `passed`에 더하지 않는다. 평가하지 못한 기능 범위가 있으면 전체 재현으로 승격하지 않는다. 일부 관측 성공이 있으면 부분 재현, 전혀 평가하지 못했으면 미평가를 유지한다. 미평가를 실패나 기업의 기술 장벽으로 바꾸지도 않는다.

**D1 — 비공개 자료 허용 질문은 기각한다. 공개 규칙에 따른 자료 생성으로 해결한다.**

공개 변형 규칙과 실행 시 값 생성은 이미 확정된 방향이다. 현재 구현은 질문·사실·검사 문자열을 바꾸지만 업로드 파일 내용은 바꾸지 않는다. 이 경계를 확장하면 된다. [확정 방향](/Users/cho/replica-mvp/context/project-direction.md:144), [현재 값 생성 범위](/Users/cho/replica-mvp/src/replica_mvp/web_demo.py:844)

후속 구현은 지원 중인 문서·CSV의 한 사례군부터 시작한다.

1. 구현 전에 파일 형식, 바꿀 사실·값의 범위, 자료 사이 일관성, 유지할 작업 단계와 판정 관계를 공개로 고정한다.
2. 실행 때 값을 한 번 생성하고, 그 값으로 새 업로드 파일을 만든다.
3. 입력·질문·기대 결과의 치환 관계를 검사한 뒤 같은 웹 업로드 경로로 실행한다.
4. 실제 사용 파일, 내용, 해시, seed, 생성 규칙 버전을 결과에 보존·공개한다.

생성 실패나 일관성 검사 실패는 기록하고 미실행·미평가로 끝낸다. 예시 자료로 몰래 돌아가거나 통과할 때까지 자료를 다시 뽑지 않는다. seed만으로 재생성을 보장한다고 주장하지 않고 실제 사용한 파일을 보존한다.
