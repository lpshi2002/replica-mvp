# 004 Claude 최종 재검토 — 003 Codex 수정안

## 결론

7개 핵심 변경 중 다섯 개는 수용하고, 두 개는 조건부로 수용한다. 기각하는 변경은 없다.
첫 작업의 범위는 충분하다. 다만 완료 기준에 아래 두 가지 항목을 추가해야 한다(§3).

- 근거 참조의 이름공간(유효한 참조 ID의 집합)을 관측 ID까지 넓혀야 한다. 이 문제는 이번에 코드에서 직접 확인했다.
- 근거 파일 제공에서 경로 탈출을 막는 테스트를 넣어야 한다.

이 문서는 모델 간 검토 결과일 뿐이며, 사용자 승인이 아니다. 저장소 반영 여부는 사용자가 따로 확정해야 한다.

## 1. 7개 변경 판정

## 2. 남은 실질 쟁점

### 2-1. 근거 종류 확장에 필요한 구체적 변경 (변경 1)

이번에 `web_demo.py`를 직접 읽고 확인한 사실은 다음과 같다.

- 판정자 응답 스키마(`web_demo.py:59-71`)에는 근거 필드가 `evidence_event_ids` 하나뿐이다. 판정자는 파일 변경(`file_changes`)이나 결정적 검사를 ID로 인용할 수 없다. 이 두 가지는 판정 프롬프트에 입력으로 들어가지만(`:368-388`), 참조할 식별자가 없다.
- 유효한 참조 집합은 `record["events"]`의 ID뿐이다(`:770`). 화면 근거(`screen_evidence`)는 관측 ID를 쓰지만, 이 집합에 들어가지 않는 관측 ID가 있다.
  - 행동 없이 끝난 사례의 마지막 관측 ID는 `{case}-start`다(`:713`). 판정자가 이 초기·최종 화면을 정당하게 인용해도 `:784`에서 걸러져 근거가 빈 목록이 된다.
- 따라서 변경 1을 구현하려면 두 가지를 함께 해야 한다.
  - 참조 이름공간에 관측 ID를 넣는다.
  - 파일 변경과 결정적 검사에도 참조 식별자를 붙인다. 별도 필드로 둘지, 하나의 참조 필드에 종류를 붙일지는 구현 판단에 맡긴다.
- 이름공간을 넓히지 않고 "무효 참조만 있으면 not_evaluated"를 먼저 적용하면, 행동 없이 초기 화면만으로 판정한 정당한 결과가 미평가로 떨어진다.

### 2-2. 생성 자료 조건 (변경 4)

수용하는 이유는 구현자가 생성 규칙만 보고 실제 파일은 보지 못하므로 과적합 위험이 줄어들기 때문이다. 다음 두 조건을 붙인다.

- 생성한 자료의 품질 검사(자료 사이 일관성 등)를 모델이 판단한다면, 그 판단도 근거와 함께 기록한다. 품질 검사에 실패한 자료는 미평가로 처리한다. 이는 003의 "재추첨 금지·몰래 예시 자료로 회귀 금지"와 같은 규칙으로 처리하면 된다.
- 생성 규칙 자체를 구현자에게 공개하는 범위를 명시한다. 규칙 버전·seed를 언제 공개하는지가 정해지지 않으면 "공개 고정 규칙"이 시험 입력 유출로 바뀔 수 있다. 내 이해로는 규칙은 공개하고 seed와 생성 결과는 평가 때만 만드는 구조다. 이 해석이 003의 의도와 같은지 진행자가 확인해야 한다.

### 2-3. 잘못된 사실

003에서 잘못된 사실은 발견하지 못했다. 003이 인용한 위치 중 `web_demo.py:258`(결정적 검사)와 `:364`(판정 프롬프트)는 이번에 직접 대조했고 서술과 일치한다.

## 3. 첫 작업 범위와 완료 기준

**범위는 충분하다.** 스키마 변경, 생성기, 재실행, 별도 앱 통합을 빼고 기존 결과 읽기와 근거 검증에 집중하는 순서는 맞다. 기존 Delphi 결과는 002에서 참조 64개를 이벤트 145개와 대조해 누락이 0개였으므로, 새 규칙에서도 "기록상 판정·근거 확인됨"으로 표시될 것으로 예상한다.

여기서 "스키마 변경 제외"는 결과 파일 스키마를 말하는 것으로 이해한다. 판정자 응답 스키마 변경(§2-1)이 첫 작업에 들어가는지, 다음 신규 평가 전 보강으로 넘어가는지 명시해야 한다. 내 권고는 다음과 같다.

- 첫 작업: 읽기 화면의 근거 검증에서 관측 ID를 유효 참조로 인정한다. 기존 결과를 읽을 때 정당한 화면 근거를 "확인 불가"로 잘못 표시하지 않기 위해서다.
- 다음 신규 평가 전: 판정자 응답 스키마에 파일·결정적 검사 참조를 추가한다.

003의 검증 항목에 다음 두 가지를 추가해야 한다.

1. **관측 ID 참조 보존:** 행동 없이 끝난 사례(`{case}-start`)와 행동 전 초기 화면의 관측 ID를 인용한 판정이 "근거 확인 불가"로 표시되지 않아야 한다.
2. **근거 파일 경로 제한:** 이벤트의 `screenshot` 경로나 파일 근거 경로가 `..`, 절대 경로, 심볼릭 링크 등으로 해당 실행 폴더를 벗어나면 제공을 거부해야 한다. 이를 확인하는 테스트를 넣는다. 003의 "허용된 자료로 제한"을 구체적인 테스트 조건으로 바꾼 것이다.

참고로 `tests/test_web_evaluation.py:311` fixture는 failed 판정에 빈 근거를 쓴다. 근거 규칙을 판정 결과에 적용하는 시점(후속 작업)에는 이 fixture를 함께 고쳐야 한다. 첫 작업이 읽기 화면에만 표시한다면 수정하지 않아도 된다.

## 4. 검증 범위

**이번 차례에 직접 확인한 것:**
- `web_demo.py:59-71`: 판정자 응답 스키마
- `:257-273`: 결정적 검사
- `:364-389`: 판정 프롬프트 입력 구성
- `:517`, `:713`: 관측 ID 생성 규칙
- `:770`, `:784`: 유효 참조 집합과 걸러내기
- 003-codex-revision.md, status.md

**002에서 확인한 근거를 다시 쓴 것:**
- 무효 ID가 있어도 passed가 유지되는 stub 재현
- Delphi 참조 64개의 무결성
- 업로드 항목에 `{path}`만 있다는 점
- `company_app.py`와 `cli.py`의 상태 경로
- 테스트 4개 모듈 38개 통과

**확인하지 않은 것:**
- 전체 테스트는 이번에도 실행하지 않았다.
- SpeechBrain 대안의 실제 사용 가능성
- 크롤링 스케줄러 비용
- `second_pass.py:441`의 제약 목록 구조
- `web_checkpoint.py:34`의 재개·캐시 연결 지점
- `{case}-start` 참조가 실제 결과에서 걸러진 사례가 있는지는 기존 결과에서 찾지 않았다. 코드 경로로만 확인했다.

이번 차례에 제품 코드, 기존 결과, 방향 문서는 변경하지 않았다. 쓴 파일은 이 보고서 하나다.
