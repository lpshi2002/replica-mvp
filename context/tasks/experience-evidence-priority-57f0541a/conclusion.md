# Replica 체험·평가 근거 우선순위 토론 결론

2026-10-14. Codex 제안 → Claude 검토 → Codex 수정 → 같은 Claude 재검토를 마쳤다. 이번 결과는 제품 변경을 위한 권고안이며 사용자 승인이나 구현 완료를 뜻하지 않는다. 코드·완료된 실행 결과·공유 방향 문서는 변경하지 않았다.

**제품의 중심은 “사용 가능한 복제품 + 같은 웹 작업에서 나온 AI 평가 근거 + 선택적인 직접 체험”으로 두는 것이 타당하다. 실험과 질문은 그 과정에서 발견한 불확실성을 좁히는 기능으로 발전시킨다.** 전문가·원제품·공개 정답 시험을 자동 완료의 선행 조건으로 요구하지 않는다.

## 현재 기반과 공백

| 영역 | 확인한 현재 기반 | 남은 공백 |
|---|---|---|
| 실제 웹 앱 | 기업 앱에서 기능 앱을 제공하고 사용자가 입력할 수 있음. AI도 웹 화면에서 작업 | 기업 앱 기동 성공은 전체 작업의 사용성을 입증하지 않음. 역할·사용법·관측 범위와 한계 안내가 약함 |
| 체험 상태 | 평가 작업 공간과 사용자 체험 공간 분리, 구현 파일 검사와 상태 재개 | 새로 만들 필요 없음. 평가 대상과 체험 대상이 같은 구현인지 사용자에게 설명하는 연결이 필요 |
| AI 평가 | 사례별 기대 결과·판정·이벤트·화면·비용·제외 범위를 보존 | 앱에서 평가와 실제 근거를 찾아가기 어려움. 유효하지 않은 참조를 지워도 판정을 유지하는 처리 결함 존재 |
| 새로운 입력 | 공개 계획에 따라 실행 때 질문·사실·검사 문자열을 바꾸는 장치 | 업로드 자료 내용은 기존 합성 자료에 의존. 기존 업로드에는 평가 당시 내용 해시가 없어 동일성 증명에 한계 |
| 구현·평가 범위 | 계획, 제외 범위, 대안과 필요조건, 부분 재현 집계 | 구현 제약과 평가 도구 제약이 섞인 제외 사유. 계획을 실제 구현 완료로 오해하지 않도록 더 분명한 표현 필요 |
| 질문·검토 | 별도 검토 앱에 질문·검토 이력 기반이 있음 | 현재 실행 결과와 직접 연결되지 않음. 통합보다 현재 기업 앱의 결과 연결이 우선 |

최신 Delphi 기록은 **10개 사례의 35개 조건 충족, 전체 기능은 부분 재현**이다. 35개 충족을 기능 전체나 원제품 동등성의 증거로 확대하지 않는다. HTTP 기동 점검, 조건 충족, 전체 구현 범위는 각각 표시한다.

## 토론에서 바뀐 판단

- 체험 공간 분리를 새로 만드는 제안은 철회한다. 이미 있는 장치를 재사용한다.
- “평가 도구가 확인 못함”을 이유로 기능을 자동 제외해서도, 자동 구현 완료로 승격해서도 안 된다. 실제 구현 경로·접근 조건·예산·제출된 구현을 각각 확인한다.
- 자원 제약 하나로 제외를 유지하는 규칙은 기각한다. 한 경로가 막혔어도 다른 대안이 있을 수 있다. 반대로 대안 이름만으로 실행 가능성을 확정하지 않는다.
- 근거를 행동 이벤트로만 제한하지 않는다. 초기·중간·최종 화면, 파일 내용과 변화, 결정적 검사도 참조할 수 있어야 한다.
- 비공개 정답 자료 도입 승인을 요청하지 않는다. 공개로 고정한 생성 규칙을 이용해 구현 고정 후 실행 때 새 자료를 만들고 실제 사용 파일을 결과에 보존한다.
- 원제품 없이도 질문을 만들 수 있다. 주장에 빠진 조건, 재현에서 막힌 지점, 필요한 추가 자료를 질문으로 표현하면 된다. 질문에 대한 답을 얻는 일과 질문을 만드는 일은 구별한다.
- 해시·원시 경로는 기본 기능 카드가 아니라 상세 근거에 둔다. 기본 화면은 기능·사용법·관측·한계·직접 사용을 설명한다.

Claude는 004에서 중요한 수정 방향을 수용했고, 관측 참조·자료 생성·파일 제공의 완료 조건을 보완했다. 002의 질문 생성에 관한 표현은 “불가능” 단정이 아니라 추가 자료 필요성에 근거한 후순위 제안이었다. 이 차이는 보존하되, 추가 자료 없이도 질문 초안을 만들 수 있다는 결론은 같다.

## 권고 우선순위

### 첫 작업: 근거 검증과 기존 결과·체험 연결

기업 앱의 기능 카드에서 다음 흐름을 제공한다.

**무엇을 하는가 → 무엇을 넣고 무엇을 받는가 → 직접 사용 → AI가 어디까지 확인했는가 → 근거 보기 → 제외·미확인 범위**

기존 실행 결과를 읽는 결과 페이지에 기대 결과, 판정 방식, 이유, 해당 화면·파일 근거를 연결한다. 별도 검토 앱 전체 통합, 신규 기업 실험, 조사 스키마 개편, 자료 생성기는 첫 작업에서 제외한다.

동시에 새 판정의 근거 검증을 고친다. 올바른 초기 화면 참조를 삭제하지 않도록 참조 종류와 식별자를 먼저 확장하고, 같은 실행·사례의 보존된 근거에 연결되지 않는 AI 충족·불충족 판정을 차단한다. 모두 무효하면 미평가로 남기고 원응답·차단 이유를 보존한다. 결정적 검사에는 행동 ID를 강제하지 않고 실제 조건·비교값·파일 목록 등을 남긴다.

**004의 범위 해석은 다음과 같이 해소한다.** 003이 제외한 것은 조사 스키마 변경이다. 판정 응답 형식과 신규 근거 기록에 필요한 호환 가능한 변경은 첫 작업에 포함한다. 형식 확장과 차단을 서로 다른 배포로 나누어 정당한 판정이 미평가로 떨어지게 하지 않는다. 기존 결과의 재작성·승격은 하지 않는다.

완료 기준:

1. 없는 참조와 다른 사례의 참조를 거부한다. 행동 없는 초기 화면 `{case}-start`의 정당한 참조는 보존한다.
2. 화면·파일·결정적 검사 근거, 파일 부재 검사, 중단 사례를 구별한다. 참조가 존재한다는 사실을 판단 정확성으로 표현하지 않는다.
3. 기존 수치·판정·입력 파일은 변경하지 않는다. 과거 근거·입력 해시가 없으면 기록상 결과와 확인 불가 범위를 구별한다.
4. 카드·결과·근거·체험 링크가 연결된다. 기존 Delphi는 읽기 전용으로 확인하고 별도 테스트 앱으로 동작을 검증한다.
5. 파일 제공은 허용된 실행 자료로 제한한다. 상대 경로·절대 경로·심볼릭 링크를 해석한 최종 위치가 허용 범위 밖이면 거부하는 테스트를 둔다.
6. 관련 회귀 테스트·저장소 전체 테스트·변경 파일 검토를 통과한다. 이 항목들은 향후 구현 완료 기준이며 이번에 완료한 작업이 아니다.

### 후속 1: 실제로 새로운 자료를 사용한 작업 검증

다음 신규 평가 전에 업로드의 내용·해시를 실행과 재개 판단에 연결한다. 지원 중인 문서·CSV 사례부터 공개 변형 규칙에 따라 새 파일을 만들고 같은 웹 업로드 경로로 실행한다.

규칙·형식·변형 범위는 구현 전에 공개 고정한다. seed와 구체적인 값·파일은 구현 고정 후 평가 때 생성하고, 실제 사용 파일·해시·생성 규칙 버전·검사 결과를 평가 기록에 보존·공개한다. 모델로 자료 일관성을 검사한다면 그 판단과 근거도 남긴다. 생성·검사 실패는 미실행·미평가로 남기며 통과할 때까지 재추첨하거나 기존 예시로 몰래 대체하지 않는다. seed만으로 재생성이 보장된다고 주장하지 않는다.

이는 정답이 숨겨진 비공개 시험을 새로 도입하는 것이 아니다. 공개 규칙 안에서 새 입력을 사용했는지 확인하는 것이다. 규칙 자체에 맞춘 구현이나 실제 고객 자료의 다양성 문제까지 해결했다고 주장하지 않는다.

### 후속 2: 구현 가능성과 평가 가능성 분리

제약을 경로별로 기록하고 구현·평가 중 영향을 받는 단계, 대안, 필요조건, 예산 근거를 남긴다. 실제 구현을 제출했지만 평가하지 못한 범위는 미평가로 표시한다. 미구현·가능성 미확인을 구현 완료와 섞지 않고, 미평가를 성공·실패·기업의 기술 장벽으로 바꾸지 않는다. 완료된 Delphi의 제외 기능을 이 토론만으로 복구하지 않는다.

### 후속 3: 관측에서 직접 확인 안내·기업 질문 생성

현재 구현된 경로와 구체적인 불확실성에 연결된 안내만 만든다. 예를 들어 업로드·인용 기능이 있다면 다른 자료를 넣고 인용을 원문과 대조하도록 안내할 수 있다. 구현되지 않은 음성 기능이나 원제품 동등성을 체험으로 확인하라고 안내하지 않는다.

기업 질문은 어떤 주장에 어떤 조건·자료가 빠졌는지, 우리가 어디서 무엇을 확인하지 못했는지에 연결한다. 질문 초안 생성·저장이 범위이며 외부 발송은 포함하지 않는다. 사람의 체험·피드백은 선택이다.

## 차별화와 보류할 결론

제품 방향으로는 “공개 주장 → 작동하는 구현 → 실제 입력과 관측 → AI 해석과 한계 → 사람이 다시 확인할 수 있는 경로”의 연결이 중요하다. 질문 생성 기능이나 근거 화면 하나만으로 복제하기 어려운 경쟁력이 생긴다고 보지는 않는다.

진행자의 전략적 판단으로는, 여러 실행에서 축적한 유용한 실험 설계·실패 유형·근거를 사용자가 확인하고 재사용할 수 있는 품질이 경쟁력 후보가 된다. **이 토론은 독점성·평가 정확성·사용자의 신뢰·시장 경쟁력을 입증하지 않았다.** 원제품 비교는 같은 입력의 원제품 출력을 얻었을 때, 외부 전문가 점검은 실제 오류를 검토할 자료·협력이 생겼을 때, 다중 구현 비교는 구체적인 비교 질문과 예산이 생겼을 때 다시 검토한다.

## 실제 검증 범위

- Claude 002: 유효하지 않은 ID를 제거해도 passed가 유지되는 stub 재현. 보존된 Delphi 참조 64개와 이벤트 145개 대조, 누락 0. 관련 네 테스트 모듈 38개 통과.
- Codex 003: 해당 사례에 대한 참조 연결, 실제 제외 사유와 대안, 구현·평가 코드 확인. 별도 테스트나 기업 실행 없음.
- Claude 004: 판정 응답 형식, 판정 프롬프트, 결정적 검사, 초기 관측 ID와 유효 참조 집합을 직접 대조. 초기 화면 참조가 누락될 수 있는 코드 경로 확인; 실제 운영 사례 발생 여부는 미확인.
- 진행자: 최종 문서와 쟁점 대조. git diff --check 통과, staged 파일 없음, 기존 변경 목록 보존 확인. 제품 코드·기존 결과·방향 문서 변경 없음.
- 전체 저장소 테스트, 실제 사용자 체험, 35개 AI 판단의 의미상 정확성, 대안 모델의 현재 실행 가능성은 이번 토론에서 검증하지 않았다.
