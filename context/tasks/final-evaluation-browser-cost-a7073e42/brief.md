# 최종 평가 자체의 큰 비용 절감: 브라우저 실행 방식 재검토

2026-10-13. 기존 두 토론은 closed이므로 이번 명시적 후속 요청을 새 작업으로 연결한다. 기존 결론을 확정 설계로 가정하지 않는다.

## 사용자 원문과 범위
현재 대화: “그러면 테스트 범위랑 판정 품질은 유지하면서 최종평가 비용 자체를 크게 줄이는 방향으로 클로드랑 다시 토론해봐 브라우저 사용 비용을 줄이는 방향은 굉장히 많을거 같은데 이미 적용을 한것도 있을거고”

직전 지적은 재실행을 제외해도 최종 평가가 구현비에 비해 비싸다는 것이다. 이번 목표는 **한 번의 최종 평가 총비용**을 줄이는 설계다. 재실행/한도 복구도 포함해 정리하지만 그것만으로 답하지 않는다. 토론·읽기 전용 분석·필요한 무모델 임시 실험만 수행한다. 제품/복제품/동결 사례 변경, 실제 유료 테스터 A/B, 새 API 공급자/키 설정, 회사 재평가는 이번 범위가 아니다. 토론 에이전트 호출은 사용자가 요청했다.

## 확정 제약
- 사람이 사용하는 같은 웹 화면에서 실제 입력·클릭·업로드와 결과를 검증한다. backend/API만 직접 시험해 UI 시험을 대체하지 않는다.
- 기업 입력 이후 무인 실행, 구현자와 최종 판정자 분리, 동결 사례·기대조건·변형 범위 유지. 스텁/내부기록만으로 실제 외부 효과를 충족 처리하지 않는다.
- 모든 원자 행동의 입력·화면·중간 상태·오류·결과 증거 보존. 판정 품질 유지란 이전Judge와 같은 답만 내는 것이 아니라 알려진 실패를 놓치지 않는 것을 포함한다.
- 이전의 “최대2행동”, “TTL부터”는 이전 토론의 최소 변경 제안이다. 사용자 확정 요구나 이번 탐색의 상한이 아니다. 넓은 대안을 실제 효율·복잡성·검증 가능성으로 비교하고 재검토하라.

## 이번 토론에서 비교할 대안군 (진행자 탐색 요청이며 채택안 아님)
1. 다중 행동/폼 채우기+제출/조건부 실행 중단: 2개를 넘어서는 것이 실제로 가치 있는가.
2. 단계별 계획 후 코드 실행, 관측된 UI의 재사용 가능한 조작 절차/선택자 캐시: 준비 비용을 포함해 언제 이득인가. 결과·판정 재사용과 구별.
3. 관측 전송의 차이분/안정된 부분 분리/관련 화면 조각/중복 필드 제거: 모델이 놓칠 정보 없이 줄일 수 있는가.
4. 코드 대기·이벤트·입력 사후조건/동일 화면 반복 억제: 이미 된 것과 추가 호출을 없앨 부분 구분.
5. 기존 제공자 내 역할 모델/추론 강도/단순 조작과 어려운 분기의 처리: 불필요한 라우터 LLM을 만들지 말 것.
6. 캐시 TTL/고정 지침/CLI 부가 문맥: 큰 구조 변경을 막는 소규모 실험으로만 끝내지 말 것.
7. 판정·코드 검사 단계의 증거 정리·중복 평가·준비 호출: tester 외40%도 보되 독립성과 실패 탐지 유지.
8. 불필요한 재실행/복구/버전 고정: 한 번의 평가 절감과 누적 비용 절감을 분리.
9. 스크린샷 축소/병렬화/도구 변경/대규모 브라우저 프레임워크 도입 등 흔한 권고가 실제 LLM 비용을 줄이는지 검증. 이미 구현된 기능을 새 절감으로 세지 말 것.

Playwright, browser-use, Stagehand 등 관련 1차 문서에서 현재 가능한 방식을 필요하면 조사하되 도구 교체를 목적화하지 않는다. 외부 성능 수치를 이 프로젝트 절감률로 옮기지 않는다.

## 완료 기준
제안→Claude의 근거 있는 반론→수정→재검토로 중요한 쟁점을 다룬다. 최종 결과는:
- 이미 적용/부분 적용/미적용 방법의 근거 있는 목록
- 단일평가 총비용에 큰 영향을 줄 구조안과 구현순서, 보류·기각 이유
- 비용 효과의 근거/가정/미측정 구분. 예컨대 tester만50%줄여도 총비용은약30%줄 뿐이다. 절감률을 단순 합산하지 않는다.
- 조작 절차 생성·복구·실패·fallback을 포함하는 최소 검증 설계, 동일 범위/오류 탐지 기준
- 구현 가능한 작은 첫 단계와, 큰 절감이 불가능하다면 그 한계를 솔직히 제시
