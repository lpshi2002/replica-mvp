**2. B1 — 단계 계획과 코드 실행을 중심안으로 채택**

| 대안 | 비용을 줄이는 방식 | 판단 |
|---|---|---|

| 관측된 폼 전체 계획 | 여러 필드·선택·업로드·제출을 한 호출로 결정 | **우선 권고.** 반복 사용 없이 첫 실행부터 이득 가능 |
| 단계별 절차 실행 | 이미 관측한 조작과 명시적 대기 조건을 코드로 수행 | **중심 구조.** 새 화면·의미 판단에서 모델 복귀 |

실행기는 자유 Python/JavaScript 대신 **허용된 UI 행동 목록과 사전·사후조건**을 받는다. 모델은 작업 목적을 판단하고, 실행기는 `_perform`·대기·기록 기능을 재사용한다. 계획 생성용 모델을 기존 tester 앞에 추가하지 말고, 기존 tester 응답 자체를 단계 계획으로 바꾼다.

안전 경계는 행동 개수보다 **새 판단의 필요성**으로 정한다.

- 현재 관측으로 입력값·대상·순서를 결정할 수 있는 행동은 여러 개 수행한다.
- 새로운 질문, 조건부 필드, 선택지 변경, 오류, 예상 밖 이동에서는 남은 절차를 중단한다.
- 제출 뒤에는 결과를 관측한다. 새 답변의 의미에 따라 다음 입력을 만들어야 한다면 모델을 호출한다.
- 원자 행동마다 입력·오류·화면·중간 상태를 저장한다. 증거 저장 실패도 중단 조건이다.
- 모델 호출 수와 원자 행동 수를 별도로 제한한다. 실행 전 거절과 복구 호출도 예산에 포함한다.
- 제출 결과가 불명확하면 자동 재제출하지 않는다.

현재 관측기는 매번 ref를 다시 매긴다. 따라서 관측과 대상 바인딩을 분리해야 한다. 단계 안에서는 실제 노드·폼 동일성을 확인하고, 재관측 후 오래된 숫자 ref를 재사용하지 않는다. Playwright의 자동 대기는 클릭 가능성을 검사하지만 업무상 올바른 대상·결과까지 보장하지 않는다. [공식 자동 대기 문서](https://playwright.dev/docs/actionability)

**3. B2 — 안전한 조작 절차 재사용**

첫 사례에서 관측·실행한 절차를 후속 사례에서 재사용한다. 별도의 탐색 실행을 먼저 요구하지 않아 준비 비용을 제한한다.

재사용 대상은 **입력 슬롯, 대상 식별 규칙, 조작 순서, 중단 조건**이다. 과거 입력값·출력·합격 판정은 재사용하지 않는다. 이번 사례의 생성 값을 넣고, 모든 UI 행동과 결과 관측을 새로 수행한다.

절차는 후보·평가기 버전과 연결하고, 실행 때 현재 화면에서 대상의 유일성·폼·유형·상태를 다시 확인한다. 불일치하면 부분 실행 위치와 현재 화면을 모델에 돌려준다. 사례 사이 앱 상태는 기존처럼 분리한다. 답변 내용에 따라 갈리는 대화는 고정 절차로 만들지 않는다.

Stagehand도 관측 결과를 실행 가능한 행동으로 반환하고 재사용하는 방식을 문서화한다. 이는 설계 가능성의 근거이며, 프레임워크 교체나 해당 도구의 성능 수치를 가져올 근거는 아니다. [공식 Observe 문서](https://docs.stagehand.dev/v3/basics/observe)

손익분기는 다음으로 판단한다.

`재사용으로 없앤 계획 비용 > 절차 생성·검증 비용 + 추가 실행 비용 + 실패·복구 비용`

한 번만 등장하는 화면에는 B1이, 반복되는 화면에는 B2가 유리할 가능성이 있다. 현재 기록만으로 안전한 재사용 횟수를 확정할 수 없다.

**4. O2/O3/O6/O8 및 B3 — 작은 절감의 역할**

- **대기:** 최신 표본에는 `wait_for` 48회와 `wait` 23회가 있지만, 모두 제거 가능한 호출은 아니다. 이미 로컬 polling을 한다. 앞선 계획에서 정할 수 있는 대기를 흡수하는 것이 추가 절감이다. 단순 `networkidle` 단축은 주로 시간 개선이다.
- **관측 압축:** 현재 CLI는 호출마다 새로 시작한다. 이전 화면 없이 차이분만 보내는 안은 기각한다. 우선 한 요청 안의 중복 필드·텍스트를 줄이고, 필요 정보가 복원되는 표현을 사용한다.
- **관련 화면 조각:** 관련 영역만 보내더라도 전역 오류·대화상자·이동·새 필드의 변화는 알려야 한다. 화면이 같다는 이유만으로 다음 판단을 생략하면 실패한 클릭이나 진행 정지를 놓칠 수 있다.
- **지속 세션:** 기준 화면 뒤에 차이분을 누적하는 방식은 별도 후보다. 이력 증가·복구·캐시 읽기까지 비교해야 하며, 현재 구조에 차이분만 붙이는 작은 변경은 아니다.
- **TTL·CLI 문맥:** 작은 독립 실험으로 유지하되 B1의 선행 관문으로 두지 않는다. 공식 문서는 `-p`의 TTL 선택과 디렉터리 문맥의 캐시 영향을 설명한다. 현재 safe-mode 조합에서의 절감은 미확인이다. [Claude Code 캐시 문서](https://code.claude.com/docs/en/prompt-caching)
- **모델:** 기존 제공자 안에서 역할별 모델을 명시한다. 어려운 분기의 승격은 관측된 실패·모호성에 따른 코드 규칙으로 제한하고, 라우터 LLM은 추가하지 않는다. 추론 강도 변경은 현재 래퍼 지원부터 확인해야 한다.

스크린샷은 현재 모델 입력이 아니므로 해상도를 낮춰도 직접적인 LLM 토큰 절감은 없다. 병렬화는 기본적으로 지연시간 개선이다. 일반 API 교체·대규모 브라우저 프레임워크 도입은 이번 권고에서 제외한다.

**6. O7 — 총비용과 검증 기준**

단일 평가의 총비용은 다음처럼 계산한다.

`C평가 = Ctester + Cjudge + C코드검사 + C입력생성 + C앱내부 + C기타외부 + C브라우저·저장`

각 역할에는 성공뿐 아니라 준비·거절·실패·복구·fallback 호출을 포함한다. 계획 생성은 tester에 포함해 중복 계산하지 않는다. 미측정 비용은 0으로 놓지 않는다.

각 호출의 모델 비용은 모델·가격표 날짜별로 다음 항목을 합산한다.

`일반 입력×단가 + 캐시 읽기×단가 + TTL별 캐시 쓰기×단가 + 출력×단가`

CLI 추정액, 별도 가격 환산, 실제 청구액은 구분한다. tester만 절반으로 줄인다는 **가정**에서도 총액 감소는 약 30%다. 여러 개선의 절감률을 더하지 않는다.

권고 구현·검증 순서는 다음과 같다.

1. **첫 변경:** 기존 tester 응답을 관측된 폼의 여러 행동으로 확장하고, 원자별 기록·중단·예산을 구현한다. 첫 범위부터 다중 입력을 허용하되 새 화면의 분기를 미리 실행하지 않는다.
2. **무모델 검사:** 노드 교체, ref 복사, 조건부 필드, 긴 값·업로드, 부분 실패, 중복 제출, 증거 저장 실패, 예산 종료를 로컬 fixture로 확인한다.
3. **반복 절차 추가:** 첫 실행에서 생성한 절차의 후속 재사용을 검증한다. 캐시가 비어 있는 단일 평가 전체 비용과 재사용 구간 비용을 함께 보고한다.
4. **후속 유료 검증이 허용될 때:** 같은 후보·동결 사례·생성 입력·모델·예산으로 기존 방식과 비교한다. 실제 UI를 양쪽에서 실행하고 모델 변경·TTL 변경은 분리한다.
5. **채택 기준:** 전체 기대조건·변형 범위 유지, 원자별 증거 누락 없음, 알려진 실패를 새로 통과시키지 않음, 완료율·미평가율 퇴행 없음, 준비·fallback 포함 총비용 감소를 함께 충족한다. 기존 Judge와의 일치만으로 품질을 인정하지 않는다.

기존의 잘못된 단가 환산·캐시 추정·인접 행동 수를 절감률로 쓰지 않는 판단은 유지한다. 반면 **“2행동까지만”, “TTL부터”, “범용 계획은 후순위”는 이번 큰 절감 목표에서 재검토해야 한다.** 절차 재사용이 적거나 의미 판단이 대부분이면 큰 절감이 어려울 수 있으며, 그 한계도 측정 결과로 받아들여야 한다.

이번 턴에는 코드·기존 집계·1차 문서만 읽고 비용을 재집계했다. 제품 변경, 파일 작성, 테스트 실행, 유료 평가·회사 재평가는 수행하지 않았다.
