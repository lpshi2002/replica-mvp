# Claude 리뷰: 남은 tester 최적화(O1·O6, O2·O4·O5·O7)

## 핵심 결론

이번에 새로 확인한 사실은 tester 비용의 대부분이 **재사용되지 않는 1시간 캐시 쓰기**라는 점입니다. 그래서 이전 결론보다 O6의 우선순위를 높이고, 새 항목 O8을 제안합니다. O1은 범위를 더 좁힌 채로 유지하고 순서를 뒤로 미룹니다.

## 새 근거: 호출별 캐시 기록 (읽기 전용으로 측정)

측정 방법은 다음과 같습니다. delphi-ai-v4 `web-attempt-002` 세 claim의 `receipts/`에서 완료된 tester 호출 427건을 골라 `replica_mvp.model_calls.read_receipt`로 읽었습니다.
- 대상 경로: `work/delphi-ai-v4/single-harness-2026-10-09/final-results/runs/claim-00{1,2,3}/web-attempt-002-*/receipts/`

| 항목 | 값 |
|---|---|
| 호출 1건당 1h 캐시 쓰기 | 중앙값 2,964–4,154 토큰, 최소 1,553 / 최대 7,373 |
| 호출 1건당 캐시 읽기 | 모든 호출에서 1,977 또는 1,995로 **고정**(첫 호출만 0) |
| 합계 | 쓰기 1,556,529 / 읽기 845,532 / 출력 83,357 / 비캐시 입력 854 |

- **해석(추론)**: 캐시 읽기가 호출마다 같습니다. 따라서 재사용되는 부분은 CLI의 고정 시스템 프롬프트뿐입니다. `_tester_prompt`가 만드는 사용자 메시지는 매번 1h 캐시로 쓰이지만, 다음 호출에서 한 번도 읽히지 않습니다. 원인은 프롬프트가 JSON 텍스트 블록 하나이고, 앞부분에 `remaining_actions`처럼 매번 바뀌는 값이 들어 있기 때문으로 보입니다. 이 부분은 아직 확인하지 않았습니다.
- **비용 비중**: coordinator가 확인한 2026-10-12 공식 단가(쓰기 1h $4, 읽기 $0.10, 출력 $10/MTok)로 계산했습니다. 세 run의 tester 비용 약 $7.15 중 1h 쓰기가 $6.23(87%)입니다. CLI가 기록한 `cost_usd` 합계는 $10.96이라 공식 단가 계산과 다릅니다. 그래서 아래 비교는 모두 공식 단가 기준의 **비율**로만 적습니다.
- 출처 코드:

  - 프롬프트 구성: `src/replica_mvp/web_demo.py:287-316`

## O6 — 우선순위를 올린 실험으로 수정 (기존 "실험 후보")

- **결론**: 채택합니다. 고정 지시문과 행동 설명만 `--append-system-prompt`로 옮기는 실험을 O1보다 먼저 합니다. case·facts·화면·이력은 사용자 메시지에 그대로 두어 격리를 유지합니다.
- **이유**: 위 기록대로 지금은 고정 지시문(JSON 기준 1,666자)도 매 호출 1h 쓰기로 과금됩니다. 시스템 프롬프트 쪽 캐시 접두부에 들어가면 쓰기 $4 대신 읽기 $0.10으로 바뀝니다.
- **기대 효과(추정)**: 1,666자를 약 400토큰으로 가정하면 427건에서 약 $0.67, 즉 tester 비용의 약 9%입니다. 토큰 수와 캐시 경계는 측정하지 않았습니다.
- **미검증 사항**:
  1. `--append-system-prompt`로 넣은 문구가 캐시 경계 **안쪽**에 놓이는지
  2. 1h TTL과 모델별 최소 캐시 길이가 맞는지
- **채택 조건**: 같은 앱·같은 case·같은 모델로 2건 이상 호출해 receipts에서 다음 두 가지를 모두 확인합니다.
  1. 두 번째 호출부터 `cache_read_input_tokens`가 약 1,977에서 고정 지시문 크기만큼 늘어납니다.
  2. 그만큼 `ephemeral_1h_input_tokens`가 줄어듭니다.

  이어서 선택한 case를 돌려 행동 품질에 퇴행이 없는지 봅니다. 확인 항목은 완료 여부, 같은 단계에서 나온 행동, give_up 비율입니다.
- **기각 조건**: 읽기 토큰이 늘지 않으면 기각합니다. 그 경우 CLI가 append 이후에 캐시 경계를 두지 않는다는 뜻입니다.

## O8 (신규) — 재사용되지 않는 캐시 쓰기 제거 또는 축소

- **결론**: 새 항목으로 제안합니다. 다만 CLI에서 제어할 수 있는지 아직 확인하지 않았으므로 판단을 보류합니다.
- **이유**: 사용자 메시지 쓰기는 재사용되지 않으므로, 기준 입력 단가($2)보다 비싼 쓰기 단가($4)를 낭비하고 있습니다. 같은 427건을 공식 단가로 다시 계산하면 다음과 같습니다(동작과 품질은 그대로라고 가정한 산술 계산).

| 방식 | 비용 | 변화 |
|---|---|---|
| 현재(1h 쓰기) | 약 $7.15 | 기준 |
| 5분 TTL 쓰기($2.50) | 약 $4.81 | −33% |
| 캐싱 전부 끔(시스템 1,977토큰도 $2) | 약 $5.64 | −21% |
| 이상적: 고정 접두부만 캐시, 사용자 메시지는 쓰지 않음 | 약 $4.0 | −44% |

- **확인할 것**:
  1. `claude --help`와 Claude Code 공식 문서에서 캐싱이나 TTL을 끄거나 바꾸는 방법(환경 변수 포함)이 지원되는지 확인합니다. 지원된다고 단정하지 않습니다.
  2. 지원된다면 O6과 같은 2건짜리 receipts 실험으로 쓰기·읽기·비용을 비교합니다.
  3. 제어할 수 없다면 O8은 기각하고 O6만 남깁니다.

  어떤 경우에도 새 모델 provider나 API 직접 호출로 바꾸지 않습니다.
- **O1과의 관계**: 호출 1건의 비용은 대부분 프롬프트 전체 쓰기입니다. 따라서 O8로 쓰기 단가를 낮추면 O1로 호출 수를 줄였을 때 얻는 절감액도 함께 줄어듭니다. 그래서 순서는 O6·O8을 먼저 하고 O1은 그다음에 둡니다.

## O1 — 제한된 폼 배치 유지, 범위는 더 좁힘

- **결론**: 계획을 먼저 세우고 코드가 실행하는 넓은 방식은 기각합니다. 제한 배치도 O6·O8 측정 뒤로 미룹니다.
- **넓은 방식을 기각하는 이유**:
  - 계획한 뒤 코드가 연속 실행하려면 중간 화면의 분기, 대화형 앱의 다음 입력, DOM 변경을 코드가 판단해야 합니다. 이 판단은 "모델이 새 화면을 보고 다시 판단한다"는 원칙과 충돌합니다.
  - 절감 후보 95건 중 상당수는 `fill → click "Send"` 패턴입니다. 이 경우 응답 화면을 본 다음 단계에서 어차피 모델의 판단이 필요합니다.
- **같은 URL이라고 안전한 배치는 아닙니다(미검증 전제 반박)**:
  - `_OBSERVE_SCRIPT`(`web_demo.py:91`)는 관측할 때마다 모든 `data-replica-ref`를 지우고 번호를 다시 매깁니다. 폼 소속이나 노드 정체성 정보도 기록하지 않습니다.
  - 따라서 URL이 같고 ref 번호가 같아도 같은 요소라는 보장이 없습니다. 배치 도중에 기존 관측 스크립트를 다시 부르면 남은 ref가 깨집니다.
- **최소 범위**:
  - **입력**: 현재 관측에 있는 ref에 대한 `fill/check/uncheck/select`의 순서 목록과, 마지막에 선택적으로 붙는 click 1개입니다.
  - **실행 중 기록**: 코드는 각 행동마다 지금처럼 event·스크린샷·`url_after`를 남깁니다.
  - **즉시 중단 조건**: 대상의 tag·type·label이 관측 당시와 다름, 대상이 disabled이거나 hidden, 오류 발생, URL 변화 중 하나라도 있으면 남은 행동을 멈춥니다. 이 대조에는 번호를 다시 매기지 않는 별도 읽기 함수를 씁니다.
  - **종료 후**: 마지막 click 다음에는 반드시 다시 관측하고 모델이 판단합니다.
  - **예산**: `max_actions_per_case` 예산은 원자 행동 단위로 계속 차감합니다.
- **효과 상한**: 95/401(23.7%)은 인접한 행동 수일 뿐 절감액이 아닙니다. 배치 응답은 출력이 길어지고 실패하면 폴백 호출이 생기므로, 실제 절감은 이보다 작습니다.
- **확인할 것**:
  1. 가짜 앱 테스트: 이전 결론의 8개 시나리오 + 관측 사이 ref 재번호화
  2. 같은 조건 A/B: 호출 수, 쓰기·읽기 토큰, 공식 단가 비용, case 완료율, 판정 일치
